C. The research plan

C1. Explain your research in one minute.

Developers write rules for coding agents in files like CLAUDE.md and AGENTS.md. I want to know which of these rules agents actually follow, what makes a rule work, and whether a rule changes the quality of the code. I take one real rule at a time from a real file, remove it or reword it, and run Claude Code and Codex on real tasks from the same repository. Small scripts check whether the rule was followed, and I also measure tests, complexity and static analysis warnings. A smaller second study looks at real pull requests to see whether the results hold in real projects.

Key point: For a 3 minute version, add Fig. 1 and one example rule (see 01_proposal_explained_simply.md, Sections 4 and 5). Past exams often opened with "explain your essay in 3 minutes".

C2. What problem does this solve, and who cares?

Developers keep adding rules to these files, and there is little evidence on which single rules work. Your Agent READMEs paper found that the files grow mainly through small additions, not deletions, and Gloaguen et al. found that context files add over 20% to inference cost on average. Your EASE 2026 paper found that humans made 83.21% of the later commits on files that agents created, so when an agent ignores a project rule, a person pays for it later. My results would tell developers which rules to keep, which to reword, and which to move into a linter or a test.

C3. What do you mean by an "effective" rule?

I call a rule effective if agents follow it more often when it is in the file than when it is removed. That is different from compliance. If agents put new tests in the tests folder anyway, the rule is followed but not effective. Harness-IF starts from the same problem: when an agent obeys a rule, it may simply have been going to do that anyway.

Key point: "Followed" and "effective" are different. This one idea answers many attacks.

C4. RQ1: what is it, and why remove a rule instead of adding one?

RQ1 asks whether removing one real rule changes how often agents follow it in their code. I remove rather than add, because the rules already exist in real files, so taking one out is a clean leave-one-out test. Everything else in the file stays the same, so a difference comes from that rule. It also matches a real decision developers face: can I delete this rule?

C5. RQ2: why these three properties?

RQ2 asks which properties make a rule more effective: its wording, its specificity, and whether the project's linter already enforces it. Each comes from earlier work. In Guardrails, the three rules whose removal lowered the pass rate were all "do not" rules. In Agent Skill Evolution, rules that named a command or path new to the file had the largest effect. And Santos et al. flagged rules that a linter already checks in 62 of 100 files.

Key point: Wording is tested directly, because I reword the same rule. Specificity and linter coverage differ between rules, so those results are associations.

C6. RQ3: what is it, and why only warnings the rule does not check?

RQ3 asks whether keeping a rule, instead of removing it, changes the quality of the code: hidden test results, cyclomatic complexity and static analysis warnings. I leave out any warning that encodes the rule itself, because otherwise I would count the rule twice. For example, if the rule is about line length, the line length warning is not part of the quality count. The question is whether a rule has side effects on the rest of the code, good or bad.

C7. What are your variables?

No file shows what the agent does by default, which tells me how much room the rule has to matter, and it links my results to the no-file setting in Gloaguen et al.

Key point: Know it as a table: V1 original, V2 removed, V3 reworded, V4 neutral sentence, V5 no file. Contrasts: V1 vs V2 = the rule's effect (RQ1); V1 vs V3 = wording (RQ2); V1 vs V4 = the rule's content at the same length; V4 vs V2 = just having extra text.

C18. How exactly do you measure compliance?

D. Technical knowledge

D1. How does a coding agent work?

A coding agent is a language model inside a loop. The model reads its context and asks for an action, such as reading a file, editing lines or running pytest. The harness runs that tool and puts the result back into the context, and this repeats until the model decides the task is done. Everything it sees, including the context file, has to fit in a limited context window. In Yuki I saw that a local 7B model picked the right tool much more often when I gave it only the relevant tools.

D2. How do Claude Code and Codex read context files?

Claude Code reads CLAUDE.md at the start of a session, and its documentation says the content is delivered as a user message after the system prompt, with no guarantee of strict compliance. Newer versions read AGENTS.md only when there is no CLAUDE.md. Codex reads AGENTS.md files from the repository root down, plus a global one in its home folder, up to 32 KiB by default. For my study this matters: I must not use Claude Code's bare mode, because it skips CLAUDE.md, and I must keep my own global files out of the runs.

Key point: Tool details change often. Say "as of the version I checked" and re-check before the interview.

D3. What do developers put in context files?

In your Agent READMEs paper, the most common categories were Testing at 75.9%, Implementation Details at 70.8% and Architecture at 68.1%, with Build and Run at 63.0%. Security and performance were rare, at 14.8% and 14.5%. In the earlier Manifests paper on CLAUDE.md only, Build and Run was the top category at 77.1%. The files are long, a median of 485 words for Claude Code, and score as hard to read on the Flesch scale, though the paper notes this partly reflects technical vocabulary.

D4. What is mining software repositories?

It means studying how software is built from the data projects already leave behind: commits, pull requests, reviews, issues and CI logs. A typical study selects repositories, collects data with the GitHub API or git, cleans it, labels a sample with two raters, measures, and analyses with tests and effect sizes. The common traps are inactive or toy repositories, tangled commits, squash merges that change commit IDs, and not knowing who wrote a commit. Results are associations unless the design adds a comparison.

D5. What is AIDev?

AIDev is a public dataset of pull requests opened by coding agents on GitHub, built by Hao Li, Haoxiang Zhang and Ahmed Hassan at Queen's University. The version in the MSR 2026 paper has 932,791 pull requests from five agents, Codex, Devin, Copilot, Cursor and Claude Code, in 116,211 repositories, up to 1 August 2025. Repositories with more than 100 stars have richer data, such as reviews, commits and file diffs. It has no context file table and no full repository history, and newer, larger releases exist, so I always name the version I quote.

D6. What is SWE-bench, and what is pass@k?

SWE-bench turns real GitHub issues from popular Python projects into tasks: the agent gets the code before the fix, and the real pull request's tests decide whether it solved the task. SWE-bench Verified is a subset of 500 tasks checked by people. pass@k is the chance that at least one of k attempts passes. For a project rule I care more about reliability, so I would also report whether all three runs follow the rule.

D7. Explain logistic regression and an odds ratio simply.

Logistic regression is regression for yes or no outcomes. It models the log of the odds, where the odds are p divided by 1 minus p, so its predictions stay between 0 and 1. An odds ratio compares the odds in two conditions, and 1 means no difference. For example, if compliance is 80% with the rule, the odds are 4, and if it is 50% without it, the odds are 1, so the odds ratio is 4.

D8. What is the difference between fixed and random effects?

Fixed effects are things I choose and want to estimate, like the file version and the agent. Random effects are things I sampled from a bigger group, like tasks and rules, and each one gets its own baseline. This handles the fact that runs on the same task are similar, and it lets my conclusion speak about tasks and rules in general, not only the ones I picked.

D9. What are a p-value, a confidence interval and an effect size?

A p-value is the chance of seeing a result at least this extreme if there were really no effect. It does not tell you how big the effect is. A confidence interval gives a range of plausible values for the effect, and an effect size says whether the difference matters in practice. For example, Gloaguen et al. report +2.4% task success for developer files with p = 0.21, so they cannot rule out no effect. With a large sample even a tiny difference can be significant, so I will always report effect sizes with intervals.

D10. What are association, causation, a confounder and regression to the mean?

Association means two things change together; causation means one makes the other change. A confounder is a third factor that affects both, for example a project adding a rule and a new linter on the same day. Regression to the mean means that after an unusually bad period, things often improve by themselves, which matters because rules are often added right after an agent makes mistakes. A controlled experiment avoids these problems by changing one thing and holding the rest fixed.

D11. What are difference-in-differences and interrupted time series?

Difference-in-differences compares the before and after change in a treated group with the same change in a comparison group. In my case, agent pull requests are the treated group, and human pull requests in the same repository are the comparison. The file is not written for people, although they may read it too, so this comparison is imperfect and tends to hide differences. Interrupted time series looks at a trend over many months and checks for a jump or a change in slope at the rule date. Both are still observational, so I report them as associations.

D12. What is cyclomatic complexity?

Cyclomatic complexity counts the independent paths through a function, roughly the number of decisions plus one. A function with one if statement and one for loop has a complexity of 3. Higher numbers mean more paths to test and understand. I would compute it with radon, which your readability paper also used.

D13. What are static analysis, linters and the Maintainability Index?

Static analysis checks code without running it, and a linter is one kind that reports style problems and simple bugs, such as an unused import. Ruff is a fast Python linter, and pylint is an older, stricter one. The Maintainability Index combines lines of code, cyclomatic complexity and Halstead metrics into one score. I would report it only as a secondary measure, because your readability paper found it fell in 56.1% of commits that aimed to improve readability.

D14. Which statistical tests does the lab use, and what do they do?

Mann-Whitney U compares two groups without assuming normal data, and Cliff's delta says how often a value from one group is larger than a value from the other. Kruskal-Wallis does the same kind of comparison for three or more groups. Cohen's kappa measures agreement between two raters, corrected for chance. Your Agent READMEs paper used Mann-Whitney with Cliff's delta, and the Voria et al. plan uses Kruskal-Wallis, Cliff's delta and Holm-Bonferroni.

D15. What is a flaky test, and why does it matter to you?

A flaky test sometimes passes and sometimes fails on the same code. In my study a flaky hidden test could look like a difference between file versions when there is none. So I would run each task's tests several times on the merged code before I use the task, and drop tasks with flaky tests.

D16. What is a registered report?

It is a paper whose plan is reviewed and accepted before the data are collected; Stage 1 is the plan, and Stage 2 reports the results. The Voria et al. study with Assoc. Prof. Kashiwa is a Stage 1 report at ICSME 2026, with Stage 2 going to the EMSE journal. It protects against changing the analysis after seeing the data, and I think my main hypotheses could be fixed in advance the same way.

D17. What are tokens, the context window and prompt caching?

A token is a piece of a word that the model reads, and the context window is the most tokens it can see at once. A long prompt can be cut, which is what happened to some BrandMemory rules. Prompt caching lets the provider reuse the repeated start of a prompt, so later calls are cheaper and faster. In Yuki 2.0, when I slimmed the prompt, the cached start of a typed request fell from about 32,500 to 14,800 tokens, and the median time to the first token fell from 1,572 to 1,372 milliseconds.

D18. What is object-oriented programming, and what are its benefits?

Object-oriented programming organizes code into objects that hold data together with the methods that work on it. Its main ideas are encapsulation, inheritance and polymorphism. The benefit is that you can hide details behind a clear interface and reuse code, which makes large programs easier to change. For example, in Yuki for Mac the activity observer has a base Source class with one run loop that catches errors. Each source, like the window source or the media source, is a subclass that fills in one method, iterate. The part that starts the sources treats them all the same, so I can add a new source without changing it.

Key point: A past NAIST applicant was asked exactly this. Keep it simple.

D19. What is technical debt, and what is self-admitted technical debt?

Technical debt is the future cost of a shortcut, like a quick fix that makes later changes harder. Self-admitted technical debt is when developers write it down, for example a TODO comment saying a hack needs fixing. It is a big line of work in your lab, for example the TOSEM 2026 paper on self-admitted technical debt in test code. Agent READMEs suggests that context files collect a similar "context debt" as they grow.
