Statistics primer: what I need to defend my plan

When and how long: December to early February: mixed models, p-values, confounders.

Written 21 Oct 2026 for the lab pre-application interview and the official exam.

How to use this file

  • Every topic has four parts: Plain definition, Tiny example, In my plan, and Say it (a 2 sentence answer in my own voice).
  • Read the "Say it" lines out loud. They are short on purpose.
  • Numbers from papers come from the PDFs in ../04_Papers/. Numbers marked [my arithmetic] are my own calculations, done to explain an idea. They are not results from any study.
  • I have no full statistics course on record. If asked, I say: "At VTU, probability and basic statistical inference were part of my third-semester mathematics course, Mathematics for Computer Science. It covered probability distributions, sampling, hypothesis tests such as the t-test and chi-square test, and basic ANOVA. I have not taken a full statistics course, which is why it is in my Year 1 plan. For this plan I studied logistic regression and mixed effects models on my own."
  • The lab's Recruitment page lists statistics as a helpful skill, and my own schedule (Table 1 of the proposal) puts a statistics course in Year 1, first half. Saying "I know the basics and I know where my gaps are" is a good answer.

My plan in statistical words (memorise this paragraph)

I run a controlled experiment. The unit is one run: one agent, one task, one version of the context file. The outcome for compliance is binary at each applicable place (the new code follows the rule or not), so a run gives a proportion. Tests are also binary (pass or fail). I model these with mixed effects logistic regression: file version and agent are fixed effects, task and rule are random effects. For code quality (complexity, warnings) the outcomes are counts or skewed numbers, so I also use rank based tests and effect sizes that the lab already uses. The real pull request study is observational, so I report it as associations and use designs such as interrupted time series and difference in differences with human PRs as a comparison.

Part A. Data and variability

1. Sampling and variability

Plain definition.

  • A population is everything I want to talk about. A sample is the part I actually observe.
  • A number computed from the sample (for example, the fraction of runs that follow a rule) is a statistic. If I took a new sample, the statistic would change a little. This change is sampling variability.
  • The standard error (SE) is the typical size of that change. For a proportion p measured on n independent trials, SE = sqrt(p x (1 - p) / n).

Tiny example. [my arithmetic]

  • Suppose on one task the agent "truly" follows a rule 70% of the time (the rate I would see after thousands of runs).
  • With 3 runs, the observed rate can only be 0%, 33%, 67% or 100%.
  • The chance that all 3 runs follow the rule is 0.7 x 0.7 x 0.7 = 34.3%. The chance that none does is 0.3 x 0.3 x 0.3 = 2.7%.
  • SE with n = 3 is sqrt(0.7 x 0.3 / 3) = 0.26, so about 26 percentage points. With n = 30 it is 0.084 (8 points). With n = 180 it is 0.034 (3 points).

In my plan. There are three layers of sampling:

  1. Runs: the agent is random, so each run is one draw.
  2. Tasks: I use a few tasks, but I want to talk about tasks in general.
  3. Rules and repositories: about 30 rules from about 10 Python repositories in AIDev. They are not a random sample of all GitHub. They are repositories that have a context file and tests that run in a container. So my results speak for that kind of repository.

Say it.

"Each number I report is an estimate from a sample, so it comes with noise, and the noise shrinks with the square root of the sample size. In my study the noise comes from three places, the agent's randomness, the choice of tasks, and the choice of rules, and my analysis has to account for all three."

2. Why repeated runs

Plain definition.

  • A coding agent can do different things on the same task with the same input. One run is one draw from its behaviour.
  • Repeating runs lets me estimate the run to run noise and separate it from the effect of the file version.

Tiny example.

  • The Guardrails paper [6] measured a "baseline retest reliability of 88.2%". The authors write that "each task has an ≈ 11.8% chance of flipping under run-to-run variance alone". So with one run per condition, some "effects" are just noise.
  • Gloaguen et al. [5] write "We sample completions for each agent once", and they set temperature to 0 for some models. That is a reasonable choice for task success on a big benchmark, but it cannot show run to run noise.
  • If one run with the rule complies and one run without the rule does not, that tells me almost nothing. If 6 of 6 runs comply with the rule and 0 of 6 without it, a Fisher exact test gives p = 0.002 [my arithmetic].

In my plan.

  • 3 runs per task, per version, per agent. This lets me see if the agent is stable on a task.
  • Important: runs of the same task are correlated. They share the same code, the same prompt and the same difficulty. So 3 runs are worth less than 3 new tasks. This is why tasks are a random effect in my model.

Say it.

"Agents are not deterministic, and the Guardrails paper measured that a task can flip about 12% of the time just by rerunning it, so one run per condition can produce fake effects. I run each condition 3 times to measure that noise, but I know repeated runs of the same task are correlated, so for generalisation more tasks matter more than more runs."

3. Binary outcomes and proportions

Plain definition.

  • A binary outcome has two values: yes or no, 1 or 0. Examples: "the new test file is in the tests folder", "the test suite passes".
  • A proportion is successes divided by trials, k / n.
  • Binary data needs special models. A normal linear model can predict values below 0 or above 1, and the spread of binary data depends on p itself (largest at p = 0.5).

Tiny example.

  • In one run the agent creates 4 new test files. 3 are in tests/. Compliance for that run = 3 / 4 = 0.75.
  • Two ways to pool two runs, one with 1/1 and one with 3/10:
    • Average of fractions: (1.00 + 0.30) / 2 = 0.65.
    • Total successes over total places: 4 / 11 = 0.36.
    • The second weights places, the first weights runs. I must choose one and say why. A logistic model on counts (successes out of places) weights by places.

In my plan.

  • Compliance = fraction of applicable places in the new code that follow the rule (proposal wording).
  • Runs with no applicable place (the agent never wrote code where the rule applies) have no compliance value. I report them separately, as the proposal says, because dropping them silently could hide an effect (for example, a rule that makes the agent avoid the situation completely).
  • Test result per run is pass or fail.

Say it.

"My main outcomes are yes or no: did the new code follow the rule at this place, and did the tests pass. So I treat compliance as a proportion of applicable places and use a logistic model, and I report runs with no applicable place separately so they do not disappear from the data."

Part B. Models

4. Logistic regression and odds ratios

Plain definition.

  • Odds = p / (1 - p). If p = 0.8, odds = 4 ("4 to 1").
  • Log odds (logit) = ln(p / (1 - p)). It goes from minus infinity to plus infinity, so a straight line is safe on this scale.
  • Logistic regression fits: logit(p) = b0 + b1 x X. Each coefficient is a change in log odds.
  • Odds ratio (OR) = exp(b1). OR = 1 means no effect. OR > 1 means higher odds.
  • To get back a probability: p = 1 / (1 + exp(-(b0 + b1 x X))).

Tiny worked example. [my arithmetic]

File version Runs that comply Runs that do not p Odds
Rule kept (original) 24 6 24/30 = 0.80 24/6 = 4.00
Rule removed 12 18 12/30 = 0.40 12/18 = 0.67
  • OR = 4.00 / 0.67 = 6.0.
  • Model with "removed" as the reference level: b0 = ln(0.67) = -0.41, b1 = ln(6) = 1.79.
  • Check: for "kept", logit = -0.41 + 1.79 = 1.39, and p = 1 / (1 + exp(-1.39)) = 1 / (1 + 0.25) = 0.80. Correct.
  • Fisher exact test for 24/30 vs 12/30: p = 0.003.

Trap: odds ratio is not "times more likely".

  • Risk ratio (RR) = 0.80 / 0.40 = 2.0. The agent is twice as likely to comply, not 6 times.
  • Difference in percentage points = 80 - 40 = 40 points.
  • OR and RR are close only when p is small. Compliance is often high, so I will report the percentage point difference next to the OR.

Lab and related use. McMillan [7] reports odds ratios from a mixed logistic model, for example "approximately 5.6% lower odds of compliance per generation step (OR = 0.944)".

Say it.

"Logistic regression models the log odds of a yes, so a coefficient becomes an odds ratio when I take the exponent; for example 80% versus 40% compliance is an odds ratio of 6. I always report the plain difference in percentage points too, because an odds ratio of 6 does not mean 6 times more likely, here it is only twice as likely."

5. Fixed effects, random effects and mixed effects models

Plain definition.

  • A fixed effect is a factor whose levels I chose on purpose and want to estimate one by one. In my plan: file version (5 levels) and agent (2 levels).
  • A random effect is a factor whose levels are a sample from a bigger population. I do not care about each level by itself. I want to (a) allow each level its own baseline and (b) generalise beyond the levels I happened to pick. In my plan: task and rule.
  • A mixed effects model has both. In R (lme4) it would look like: glmer(cbind(followed, not_followed) ~ version + agent + (1 | task) + (1 | rule), family = binomial)
  • (1 | rule) is a random intercept: each rule gets its own baseline compliance, drawn from a normal distribution around the overall average.

Intuitive example with tasks and rules. [made up numbers]

Rule Compliance when kept Compliance when removed
"Put new tests in the tests folder" 95% 85%
"Use the logger, not print" 70% 20%
"Add type hints to public functions" 50% 30%
  • The test folder rule is easy even without the file: the agent sees the existing folder and copies it. The logger rule is hard without the file.
  • If I ignore this and pool all runs as if independent, two bad things happen:
    1. Pseudo replication. 1,800 runs look like 1,800 independent facts, but they are clustered by task and by rule. Standard errors become too small and p values too optimistic.
    2. Confusion between "easy rule" and "effective rule". A random intercept for the rule absorbs "this rule is just easy", so the version effect is estimated within rules.
  • Tasks work the same way. McMillan [7] found that task identity mattered more than the file variables: compliance ranged from 45.1% to 84.4% across tasks. He treated task as a random effect "so that inferences generalise across tasks rather than conditioning on any one of them".
  • Bonus effect, partial pooling: a rule with few runs gets its estimate pulled a little toward the overall average. With only 6 runs per rule and version, this protects me from extreme estimates like 0% or 100%.

Choices I can defend.

  • If I want a claim about each of my 30 rules one by one, I could treat rule as fixed. I treat it as random because my question is about rules in general and their properties (RQ2).
  • If compliance is counted per place, places inside one run are also correlated. McMillan added a random intercept for the run as well, (1 | RunID). I can do the same.
  • The effect of removing a rule probably differs by rule. A random slope, (version | rule), models that. With 6 runs per rule and version it may be hard to estimate, so I will try it and report if it does not fit.
  • RQ2: rule properties (negative wording, specificity, linter coverage) enter as rule level predictors that interact with version. Wording is the strongest test, because I reword the same rule. Specificity and linter coverage differ between rules, so the real sample size there is about 30 rules.

Say it.

"File version and agent are fixed effects because I chose them and want their effects; task and rule are random effects because they are samples, some are just easier than others, and I want to generalise beyond them. Without the random effects I would treat 1,800 runs as independent, my p values would be too small, and I could confuse an easy rule with an effective one."

Part C. Inference

6. p values

Plain definition.

  • A p value answers: "If there were really no effect, how often would I see a difference at least this large just by chance?"
  • A small p value (below 0.05 by convention) means the data would be surprising if there were no effect.
  • What a p value is not:
    • not the probability that the null hypothesis is true;
    • not the size of the effect;
    • p > 0.05 does not mean "no effect". It can mean "not enough data".

Tiny examples.

  • My worked example above: 24/30 vs 12/30, Fisher p = 0.003 [my arithmetic].
  • Gloaguen et al. [5]: developer written context files "improve agent performance by 2.4% on average (p = 21%)". That is not significant. It does not prove the files are useless; the difference is small relative to the noise.
  • Large samples make tiny effects significant. In the Agentic Refactoring paper (lab), a Wilcoxon test was "statistically significant (FDR-adjusted p < 0.001)" but "the effect sizes are negligible (Cohen's d = -0.027 and -0.026)". In the lab's testing paper, p < 0.001 but "the calculated effect size is negligible (Cliff's δ = -0.12)".

In my plan. I report p values together with effect sizes and confidence intervals, never alone. Per rule results with only 6 runs per cell will rarely be significant, and I will say that clearly instead of saying "no effect".

Say it.

"A p value tells me how surprising my data would be if there were no effect, not how big or important the effect is. So I always report it with an effect size and a confidence interval, and I never read a large p value as proof of no effect."

7. Confidence intervals

Plain definition.

  • A 95% confidence interval (CI) is a range built by a method that captures the true value in 95% of repeated studies.
  • Simple reading: the range of values that are reasonably consistent with my data. Narrow = precise, wide = uncertain.
  • For proportions near 0 or 1, or small n, use the Wilson interval, not the simple "p plus or minus 1.96 SE" (Wald) interval. McMillan [7] uses Wilson intervals "where exact rates approach 0 or 1".

Tiny examples. [my arithmetic]

  • Difference 80% vs 40% (30 runs each): 40 points, 95% CI about 17 to 63 points. The effect is clearly positive, but its size is uncertain.
  • My rule checker hand check: 19 of 20 examples correct. Wilson 95% CI = 76% to 99%. The Wald interval would give 85% to 105%, which is impossible. With 20 of 20 correct, Wilson still gives 84% to 100%.

In my plan.

  • I will report every checker's accuracy as "x of 20 (Wilson 95% CI)". 20 examples tell me the checker is probably better than about 75%, not that it is 95%. For checkers with errors, I will check more examples.

Say it.

"A confidence interval shows how precise my estimate is; for example 19 correct out of 20 on a checker only tells me the accuracy is somewhere between about 76% and 99%. That is why I will report the interval for every checker and check more examples when a checker makes mistakes."

8. Effect sizes

Plain definition.

  • An effect size says how big a difference is, separate from sample size.
  • For proportions:
    • difference in percentage points (easiest to explain);
    • risk ratio;
    • odds ratio (comes out of logistic regression);
    • Cohen's h = 2 x asin(sqrt(p1)) - 2 x asin(sqrt(p2)). Cohen's usual labels are 0.2 small, 0.5 medium, 0.8 large. McMillan [7] reports Cohen's h for proportions.
  • For numbers like complexity (skewed): Cliff's delta (see Section 15), which the lab uses.

Tiny example. [my arithmetic] 80% vs 40%: difference 40 points, RR 2.0, OR 6.0, Cohen's h = 0.84 (large).

Lab use. The Agent READMEs paper uses Mann-Whitney U plus Cliff's delta with fixed thresholds (negligible if |d| ≤ 0.147, small to 0.33, medium to 0.474, large above). The Agentic Refactoring paper uses the same thresholds.

Say it.

"A p value says whether a difference is likely real, and an effect size says whether it is big enough to matter. For compliance I report the difference in percentage points and the odds ratio, and for complexity I report Cliff's delta like the lab's papers do."

9. Statistical power, and why 3 runs per version is limited

Plain definition.

  • Power = the chance that my study detects an effect that really exists. A common target is 80%.
  • Power goes up with: bigger true effect, more data, less noise, a less strict alpha.
  • Minimum detectable effect = the smallest true effect I have 80% power to detect.

Tiny example. [my arithmetic, two proportion test, assumes independent runs, alpha 0.05]

Comparison Runs per arm Power for 80% vs 50% Power for 80% vs 70%
One rule, one agent (2 tasks x 3 runs) 6 about 4% (exact test) to 18% (approximation) about 7%
30 rules pooled, one agent 180 about 100% about 59%
30 rules pooled, both agents 360 about 100% about 87%
  • Minimum detectable effect around 75% compliance: about 70 points for one rule (6 vs 6), about 13 points pooled (180 vs 180).
  • But runs are correlated. With 3 runs per task and a within task correlation of 0.5, the design effect is 1 + (3 - 1) x 0.5 = 2. Then 180 runs behave like about 90 independent runs. Power for 80% vs 70% drops to about 34%, and the minimum detectable effect grows to about 18 points.
  • Even a perfect split in 3 vs 3 runs (3/3 vs 0/3) gives Fisher p = 0.10. So 3 runs alone can never show a significant difference for one task.

What this means for my plan (be honest).

  • Pooled RQ1 (does removing a rule change compliance on average) has reasonable power for medium effects.
  • Per rule results are weak. I will report them as estimates with intervals, and use partial pooling from the mixed model, not as 30 separate significance tests.
  • RQ2 compares properties between rules, so the real sample size is about 30 rules. Example [my arithmetic]: if rule effects vary with a standard deviation of 20 points, a 15 vs 15 split can only detect about a 20 point difference in effectiveness. So RQ2 is exploratory, except wording, which I test within the same rule.
  • What I will do:
    1. Use the pilot on two repositories to measure the real run to run and task to task variance.
    2. Run a simulation based power analysis before the main runs. McMillan [7] did this with R's simr package and reports "at least 98% power at n = 50 to detect a 15-percentage-point ICR shift". He used 50 runs per condition; I have a smaller budget.
    3. If the budget is fixed, I would rather add tasks than add runs, because between task differences are large (45.1% to 84.4% in McMillan) and new tasks also improve generalisation.
  • Guardrails [6] shows the same limit: "At n = 58 ... our McNemar tests detect ∼15pp paired effects".

Say it.

"Three runs per version is enough to see whether an agent is stable on a task, but it is not enough to make claims about one rule on its own, so my main test pools all rules in a mixed model and per rule results are reported as estimates with intervals. Before the main runs I will use the pilot to measure the variance and do a simulation based power analysis, and if I need more power I will add tasks rather than runs."

10. Multiple comparisons

Plain definition.

  • If I run many tests at alpha 0.05, some will be "significant" by chance.
  • Chance of at least one false positive in m independent tests with no real effect = 1 - 0.95^m.
  • Fixes:
    • Bonferroni: use alpha / m. Simple, very strict.
    • Holm: sort p values, compare the smallest to alpha/m, the next to alpha/(m-1), and so on; stop at the first failure. Same protection, more power.
    • Benjamini-Hochberg (BH): controls the false discovery rate (the expected share of false positives among my "discoveries"). Compare the i-th smallest p to (i/m) x alpha.

Tiny example. [my arithmetic]

  • 30 rules tested separately: 1 - 0.95^30 = 78.5% chance of at least one false positive. Bonferroni threshold = 0.05 / 30 = 0.0017.
  • Four p values: 0.004, 0.014, 0.02, 0.2.
    • Bonferroni (0.0125): only 0.004 survives.
    • Holm: 0.004 ≤ 0.0125 yes, 0.014 ≤ 0.0167 yes, 0.02 ≤ 0.025 yes, 0.2 ≤ 0.05 no. Three survive.
    • BH: 0.004 ≤ 0.0125, 0.014 ≤ 0.025, 0.02 ≤ 0.0375 yes; 0.2 ≤ 0.05 no. Three survive.
  • Real case: in Guardrails [6], the most impactful single rule ("do not refactor unrelated code") had McNemar p = 0.016, but this "would not survive a strict multiple-comparison correction across 18 tests" (Bonferroni would need 0.05 / 18 = 0.0028). The authors therefore reported the pattern, not per rule significance.

Lab use. Agentic Refactoring uses Benjamini-Hochberg FDR. Voria et al. [9] (with Assoc. Prof. Kashiwa) plan Holm-Bonferroni for pairwise tests and say they "predefine hypotheses and analyses".

In my plan. A small number of main hypotheses written down in advance (RQ1 pooled version effect; RQ2 three properties; RQ3 three quality measures). Per rule and per pair results get BH correction and are labelled exploratory. A registered report format, like Voria et al., would be a good way to fix the analysis before seeing the data.

Say it.

"With 30 rules, testing each one at 0.05 gives about a 78% chance of at least one false positive, so per rule tests need a correction such as Holm or Benjamini-Hochberg. I keep a few main hypotheses fixed in advance and label everything else exploratory, which is also what the Guardrails authors did when their best single rule did not survive correction."

Part D. Tests and measures the lab uses

11. Cohen's kappa (two raters)

Plain definition.

  • Measures agreement between two raters on categories, corrected for chance agreement.
  • kappa = (po - pe) / (1 - pe). po = observed agreement. pe = agreement expected by chance from each rater's label rates.
  • Common reading (Landis and Koch): 0.41 to 0.60 moderate, 0.61 to 0.80 substantial, above 0.80 almost perfect.

Tiny example. [my arithmetic] Two people label 50 checker outputs as "follows" or "violates".

B says follows B says violates
A says follows 30 6
A says violates 4 10
  • po = (30 + 10) / 50 = 0.80.
  • A says follows 36/50 = 0.72; B says follows 34/50 = 0.68.
  • pe = 0.72 x 0.68 + 0.28 x 0.32 = 0.58.
  • kappa = (0.80 - 0.58) / (1 - 0.58) = 0.52, only moderate. 80% raw agreement can be just moderate kappa, because many agreements happen by chance when one label is common.

Lab use.

  • Agentic Refactoring: "Cohen's kappa coefficient of 0.77, which indicates a substantial level of agreement".
  • Readability paper: "Micro-averaged Cohen's Kappa: 0.80".
  • Voria et al. [9]: "We will consider κ ≥ 0.70 as the minimum acceptable agreement level".
  • The PR paper reported raw agreement (75.8%) instead of kappa "since our classification was a multi-label task". Agent READMEs reports an "agreement rate of 80.3%".

In my plan.

  • The second person who checks that a reworded rule keeps its meaning: I can report kappa between us on "same meaning / not same".
  • For the rule checkers, a script is compared with a human. There I report accuracy, precision and recall with intervals, and I can also report kappa between script and human.

Say it.

"Cohen's kappa is agreement between two raters after removing the agreement you would expect by chance, so 80% raw agreement can still be a kappa of only about 0.5. In my plan I would use it for the second person who checks that reworded rules keep the same meaning, and I would aim for at least 0.7 as Voria et al. planned."

12. Mann-Whitney U test (also called Wilcoxon rank-sum)

Plain definition.

  • Compares two independent groups without assuming a normal distribution. It uses ranks.
  • Idea: take every pair (one value from each group) and count which side is bigger. U = number of pairs where group A is bigger (ties count half).
  • Good for skewed data such as complexity or number of warnings.

Tiny example. [my arithmetic] Cyclomatic complexity of functions:

  • A (rule kept): 2, 3, 5. B (rule removed): 4, 6, 7.
  • 9 pairs. A is bigger in 1 pair (5 > 4). B is bigger in 8. So U = 1.
  • Exact two sided p = 0.2. Even perfect separation in 3 vs 3 gives at best p = 0.1. Small groups cannot reach significance.

Lab use. Agent READMEs ("Mann-Whitney U test ... at a significance level of α = 0.05"), the PR paper, What to Cut, and the testing paper all use it, usually with Cliff's delta.

Watch out. It assumes independent observations. Runs from the same task are not independent, so in my experiment I prefer paired tests on per task averages, or the mixed model.

Say it.

"Mann-Whitney compares two independent groups using ranks, so it works for skewed data like complexity, and the lab uses it with Cliff's delta in most of its papers. In my experiment runs are grouped by task, so I would use it only on independent units, for example in the real pull request study, and use paired or mixed models in the experiment."

13. Wilcoxon signed-rank test (paired)

Plain definition.

  • Compares paired values (same task under two versions, or the same file before and after a commit).
  • Take each pair's difference, drop zeros, rank the absolute differences, and compare the sum of positive ranks with the sum of negative ranks.

Tiny example. [my arithmetic] Change in complexity, rule removed minus rule kept, per task: +1, +2, -1, +3, 0, +2.

  • Drop the 0. Absolute values 1, 2, 1, 3, 2 get ranks 1.5, 3.5, 1.5, 5, 3.5.
  • Positive rank sum = 13.5, negative rank sum = 1.5. Mostly positive.
  • With only 5 non zero pairs, the smallest possible two sided p is 0.0625. Again, small samples limit what I can claim.

Lab use. The readability paper uses it on before and after metrics per commit and notes that "the Wilcoxon signed-rank test excludes pairs with zero differences". Agentic Refactoring uses it with BH correction.

In my plan. RQ3 compares file versions on the same task, so pairing by task is natural: average the 3 runs per task and version, then compare versions with a signed-rank test, as a simple check next to the mixed model.

Say it.

"The signed-rank test is the paired version: it looks at the differences within each pair, like the same task with and without the rule. It fits RQ3 well because I compare file versions on the same task, and I would use it as a simple check next to the mixed model."

14. Kruskal-Wallis test (three or more groups)

Plain definition.

  • The rank based test for 3 or more independent groups. Rank all values together, then check if the mean ranks differ.
  • It only says "some group differs". Then do pairwise tests (for example Mann-Whitney) with a correction such as Holm.

Tiny example. [my arithmetic] Complexity under three versions:

  • Original: 2, 3, 4 (ranks 1, 2, 3, mean rank 2.0)
  • Removed: 5, 6, 8 (ranks 4, 5, 7, mean rank 5.3)
  • No file: 7, 9, 10 (ranks 6, 8, 9, mean rank 7.7)
  • H = 12 / (9 x 10) x (6² / 3 + 16² / 3 + 23² / 3) - 3 x 10 = 6.49, p about 0.04 (rough with so few values).

Lab use. Voria et al. [9] plan "the non-parametric Kruskal-Wallis test, followed by post-hoc pairwise Wilcoxon rank-sum tests with Holm-Bonferroni correction. Effect sizes will be quantified via Cliff's Delta." Agentic Refactoring also uses Kruskal-Wallis with FDR adjustment.

In my plan. Useful in the real PR study, for example comparing complexity across rule types or repositories. In the experiment, my 5 file versions are better handled in the mixed model, because the same tasks appear in all versions.

Say it.

"Kruskal-Wallis is the rank based test for three or more groups, and it only tells me that some group differs, so I follow it with pairwise tests and a Holm correction. That is exactly the plan in Voria et al., so I would use the same approach where my groups are independent, for example across rule types in the real PR data."

15. Cliff's delta

Plain definition.

  • An effect size for two groups, based on pairs: delta = (number of pairs where A > B - number where A < B) / (nA x nB).
  • Ranges from -1 to +1. 0 means the groups overlap fully. It does not need normal data.
  • Thresholds used in the lab's papers: |d| ≤ 0.147 negligible, ≤ 0.33 small, ≤ 0.474 medium, above that large.

Tiny example. [my arithmetic] From Section 12: A = 2, 3, 5 and B = 4, 6, 7. delta = (1 - 8) / 9 = -0.78, large: functions written with the rule kept tend to be simpler.

Real lab examples.

  • Agent READMEs: Claude Code and Copilot files are longer than Codex files, "effect sizes are small (Cliff's delta d = 0.21 and d = 0.22)".
  • Testing paper: significant but "negligible (Cliff's δ = -0.12)".
  • Agentic Refactoring: "Cliff's delta (d = 0.838) indicates a large effect size".

Say it.

"Cliff's delta tells me how often a value from one group is bigger than a value from the other, from minus one to plus one, so it works for skewed data like complexity. The lab reports it with every Mann-Whitney test, using 0.147, 0.33 and 0.474 as the cut points, and I would report it the same way for my quality measures."

Part E. Causal thinking (mainly for the real PR study)

16. Association vs causation

Plain definition.

  • Association: two things move together.
  • Causation: changing one thing changes the other.
  • An association can come from: real causation, reverse causation, confounding, chance, or selection (which cases ended up in my data).
  • A controlled experiment gets causation by changing one thing on purpose and holding everything else fixed. The counterfactual ("what would the agent have done on the same task without this rule") is approximated by the "rule removed" version on the same task.

Tiny example.

  • In real repositories, rules are often added because agents broke them. Cai et al. [12] report that developers update rules to correct AI errors. So "repos with the rule have more violations" could be reverse causation.
  • Agent READMEs [2]: after an indentation rule was added, violations fell from 60.82% to 11.03% (rsyslog) and from 20.17% to 7.57% (lotgd). The authors themselves write "two cases cannot establish causality".

In my plan.

  • The experiment (RQ1 to RQ3) is causal by design: same task, same container, same everything, only the rule sentence changes. The neutral sentence version controls for file length, and the no file version is a baseline.
  • To stop time effects lining up with versions, I will mix the order of runs instead of running all "original" runs first.
  • The real PR study is observational, so I report associations, as the proposal says.
  • Assistant Prof. Zhenlan Ji works on causality and LLM agents. His CAM paper simulates errors in one intermediate output at a time and measures the effect on correctness. My plan has the same shape: change one rule at a time and measure the effect on compliance.

Say it.

"In real repositories a rule and good compliance can move together for many reasons, including reverse causation, because developers add rules after agents break them. That is why my main study is a controlled experiment that changes only one sentence on the same task, and the real pull request study is reported as associations."

17. Confounding

Plain definition.

  • A confounder is a third factor that affects both the "cause" and the "outcome", and creates a fake or distorted link.

Tiny example. [made up numbers] A team adds a rule in the same month they move from an older agent model to a newer one.

  • Before the rule: 80 PRs by the old model (40% comply) and 20 by the new model (80% comply). Overall 0.8 x 40 + 0.2 x 80 = 48%.
  • After the rule: 20 by the old model (40%) and 80 by the new model (80%). Overall 0.2 x 40 + 0.8 x 80 = 72%.
  • Compliance "jumps" from 48% to 72% while the rule had zero effect. The change in the mix of agents did it all.

Other confounders in the real PR study. A linter or CI check added at the same time; the project getting more mature; different kinds of tasks before and after (more tests written later).

Confounding inside my own experiment. If for RQ3 I compared runs that happened to follow the rule with runs that did not, a hidden factor such as "the agent understood the task well" could cause both compliance and simpler code. So I compare by assigned file version on the same task, not by observed compliance (the proposal says this).

Fixes. Randomisation (the experiment), stratifying or adjusting for agent and model version, excluding cases where linter settings changed at the same time (in the proposal), and using a comparison group (human PRs).

Say it.

"A confounder affects both the cause and the outcome; for example if a team adds a rule in the same month it upgrades the agent model, compliance can jump even if the rule did nothing. That is why I compare by assigned file version in the experiment, and in the real PR study I adjust for agent version, exclude linter changes, and use human PRs as a comparison."

18. Regression to the mean

Plain definition.

  • When something is measured at an unusually extreme moment, the next measurement tends to be closer to normal, even if nothing changed.

Tiny example. [made up numbers]

  • A repository's agent PRs usually violate a rule about 20% of the time; by chance it moves between 10% and 30% month to month.
  • One bad month hits 35%. The team gets annoyed and adds the rule.
  • Next month: 22%. It looks like a 13 point improvement from the rule, but most of it would have happened anyway.

In my plan. This is a real risk in the real PR study, because rules are added after violations (Cai et al. [12]). What I can do:

  • use a longer "before" window, not just the weeks right before the rule;
  • model the trend with an interrupted time series;
  • compare with human PRs and, if possible, with similar repos that had a spike but did not add a rule.
  • The controlled experiment does not have this problem, because I choose when the rule is present.

Say it.

"Rules are often added right after a bad period, and bad periods tend to be followed by normal ones anyway, so a simple before and after comparison can overstate the effect of a rule. I would use a longer before window and a time series model with a comparison group, and this is one more reason the controlled experiment is my main study."

19. Interrupted time series (ITS)

Plain definition.

  • Many measurements over time, with an "interruption" (the rule is added). Fit a line before, then test whether the level or the slope changes after.
  • Segmented regression: Y_t = b0 + b1 x time + b2 x after + b3 x (time since rule) + error.
    • b1 = trend before. b2 = immediate jump. b3 = change in trend.
  • Key assumption: without the rule, the old trend would have continued, and nothing else changed at the same time.

Tiny example. [made up numbers] Monthly violation rate of agent PRs.

  • Months 1 to 6 (before): 50, 48, 46, 44, 42, 40. Already falling 2 points per month.
  • Rule added at month 7. Months 7 to 12: 30, 28, 26, 24, 22, 20.
  • Naive before vs after: 45 vs 25, a 20 point drop.
  • ITS: the trend predicts 38 at month 7; the real value is 30. Level drop b2 = -8 points, slope unchanged (b3 = 0). The rule explains 8 points, not 20. The rest is the existing trend (for example, agents improving over time).

In my plan.

  • Many repos have few agent PRs, so I would pool repos and use a mixed model with a random effect for repository, aligning time on "months since the rule was added".
  • Problems to say out loud: consecutive months are correlated (autocorrelation), I need several time points on each side, and other changes at the same time (linter, model upgrade) break the assumption.
  • First step in the proposal: count how many repos have enough agent PRs before and after a checkable rule was added.

Say it.

"An interrupted time series fits the trend before a rule was added and checks whether the level or the slope changes afterwards, so it does not mistake an existing downward trend for an effect of the rule. In my toy example a naive before and after drop of 20 points becomes only 8 points once the trend is modelled."

20. Difference in differences (DiD)

Plain definition.

  • Compare the change in a treated group with the change in a comparison group over the same period. The comparison group's change shows what would have happened anyway.
  • DiD = (treated after - treated before) - (comparison after - comparison before).
  • Key assumption, parallel trends: without the rule, both groups would have changed by the same amount. I can check this partly by looking at the trends before the rule.

Tiny example. [made up numbers]

  • Agent PRs in the repo: compliance 40% before, 70% after (+30 points).
  • Human PRs in the same repo, same period: 50% before, 60% after (+10 points).
  • DiD = 30 - 10 = +20 points attributed to the rule (under parallel trends).

In my plan (proposal: "Human pull requests in the same repositories will serve as a comparison").

  • Things that can break it:
    • Humans can read CLAUDE.md or AGENTS.md too, so the human group may be partly "treated". That would make DiD underestimate the effect.
    • Some "human" PRs contain undisclosed AI code. The lab's PR paper notes that "the presence of undisclosed AI-generated code would likely dilute the differences between the two groups".
    • Agent PRs and human PRs may do different kinds of tasks.
  • Rules are added at different times in different repos (staggered timing). One simple regression with fixed effects for repo and time can give wrong answers in that case, and newer DiD methods are designed for it. I would need to learn the right estimator for staggered timing, so I would read that literature in Year 1 and ask Dr. Ji.

Say it.

"Difference in differences compares how much agent PRs changed after a rule was added with how much human PRs in the same repository changed over the same period, so general changes in the project cancel out. It depends on the two groups having parallel trends, and since humans can also read the context file, my estimate would more likely be too small than too large."

Say it.

"I think about four kinds of threats: internal, whether the rule really caused the change; construct, whether my scripts measure compliance and quality correctly; external, how far the results generalise; and conclusion, whether my statistics are sound. The biggest ones for me are construct validity of the checkers and the limited scope to Python and script checkable rules, and I handle them by checking every script by hand and stating the scope clearly."

Part G. Rapid fire: attacks and short answers

"3 runs is too few."

"For a single rule, yes, and I say so; my main test pools all rules in a mixed model, and per rule results are reported as estimates with intervals. The pilot will give me the real variance, and I will do a power simulation before fixing the number of runs."

"Why not just use a t-test or chi-squared test?"

"A simple test treats every run as independent, but my runs are grouped by task and by rule, so the p values would be too small. The mixed logistic model handles the grouping and the binary outcome together."

"Why logistic and not linear regression?"

"Compliance and test results are yes or no, so a linear model can predict impossible values like 110% and gets the variance wrong. Logistic regression works on the log odds scale, which keeps predictions between 0 and 1."

"What is a random effect, simply?"

"It lets each task and each rule have its own baseline, because some are simply easier, and it treats them as a sample from a bigger population. That way my conclusion is about tasks and rules in general, not only the ones I picked."

"Your RQ3 is circular: the rule improves the metric it checks."

"I leave out any check that encodes the rule itself, for example the print warning if the rule is about using the logger. And I compare file versions on the same task, not runs that happened to comply, so the comparison is not selected on the outcome."

"How do you know your checker is right?"

"I check each script by hand on at least 20 examples and report its accuracy with a confidence interval. If a checker makes mistakes, I check more examples or fix it, and I can have a second person label a sample to report kappa."

"Your real PR study cannot show causation."

"I agree, and I report it as associations. Its job is to check whether the experimental results look similar in real projects, using time series, human PRs as a comparison, and excluding linter changes."

"What if removing a rule changes nothing?"

"That is still a useful result, because it tells developers which rules they may not need, and the no file version tells me whether the agent was simply copying what it saw in the codebase. I would report it with an interval, so it is clear how large an effect I could have missed."

"Gloaguen already says instructions are followed."

"Their evidence on following comes from agent traces, for example uv is used about 1.6 times per task when the file mentions it and almost never when it does not, and they do not remove or reword single rules. I test single real rules against a version without the rule on the same task and measure compliance in the code with scripts."
