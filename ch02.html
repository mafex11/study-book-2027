Part 1: Before Monday (23 to 26 Oct)

Chapter 2 of 30

Full script: from "hello" to the last slide

When and how long: Sunday: read it out loud three times, with the slides open. Monday 08:30: once more. About 6 minutes for the slides.

Monday 26 October 2026, 10:30 IST (14:00 JST), Google Meet with Dr. Zhenlan Ji and Dr. Brittany Reid. Words in [brackets] are actions. Do not say them.

This is the plain version: short sentences, normal words, the way you would explain it to a friend at work. Read it out loud twice. Then present from the slides and just say it your way. If you lose your place, the Cue line under each slide is enough to get you going again.

Part A. Joining, before the slides

[Join at 10:25 IST. Camera on, mic on. Slides PDF already open in Preview.]

When they appear:

Good afternoon, Dr. Ji and Dr. Reid. Thank you for meeting me today.

If they ask "How are you?" or "Can you hear me?":

I'm good, thank you. I can hear you fine. I'm in Bangalore, so it's morning here.

If they introduce themselves or the lab first, listen, then say:

Thank you. I've read your lab's papers on these context files, so I'm really happy to talk to you.

When they ask you to introduce yourself and your research:

Sure. I made seven short slides, about six minutes. Can I share my screen?

[In Meet: Present now, then "A window", then choose Preview. In Preview press Cmd + Shift + F.]

Can you see my slides?

[Wait for "yes".]

Part B. The slides (about 6 to 6.5 minutes)

Slide 1. Title (about 25 seconds)

Cue: CLAUDE.md, rules, do agents follow them, is the code better

My name is Sudhanshu Pandit. Coding agents like Claude Code read a file like this one, a CLAUDE.md. It has rules the developer wrote, like "put new tests in the tests folder".

My question is simple. Does the agent actually follow these rules? And when it does, is the code any better?

First, a bit about me.

[Next slide]

Slide 2. About me (about 55 seconds)

Cue: degree, Layerpath, BrandMemory, Magic Editor, Yuki

I finished my B.E. in Computer Science at Visvesvaraya Technological University this May, and I worked as a software engineer during college.

Since last November I've been an AI engineer at Layerpath, a small startup. I was on the founding team, and I build the AI parts of our product.

On the right are three things I built. BrandMemory gives a model a company's writing rules, so the text sounds like that company. Magic Editor is an AI assistant that edits product demos, and the user approves every change. And Yuki, my side project, is an AI agent that can use Mac and Windows apps for you.

I use Claude Code and Codex every day, and I keep their rule files up to date. My question came out of BrandMemory.

[Next slide]

Slide 3. Where my question comes from (about 50 seconds)

Cue: some rules did nothing, cut off, overridden, 6 to 0, 15 to 1, one example only

When I tested BrandMemory, some rules did nothing. Some sat at the end of a long prompt and got cut off, so the model never saw them. Others did reach the model, but a default style in the prompt won over them.

I fixed both, then made the same product demo twice, without the rules and with them. Contractions went from 6 to zero, and "you" and "your" from 15 to one. Both match rules in the file.

It's one example, so it doesn't prove much. But it taught me to check whether a model follows a rule, not assume it. Coding agents get their rules the same way, so I want to check this properly for them.

[Next slide]

Slide 4. What is known, and the gap (about 55 seconds)

Cue: your lab's papers, whole file, task success only, benchmark tasks, nobody does all three

Your lab's papers looked at what developers actually write in these files. Agent READMEs also found fewer indentation mistakes after an indentation rule was added, in two repositories.

Gloaguen and colleagues tested whole files. A file didn't really help agents finish more tasks, and it cost over 20 percent more. Zhang and colleagues removed rules one at a time, but only checked whether the task passed. Harness-IF tests single rules, but on tasks made for the benchmark. And Voria and colleagues, with Dr. Kashiwa, plan to link changes in these files to code quality.

So as far as I can tell, nobody has done all three of these together: one real rule, real tasks from the same project, and checking both the rule and the code.

[Next slide]

Slide 5. Three research questions (about 60 seconds)

Cue: take a rule out, what kind of rules work, does the code get better

So I have three questions.

RQ1 is the main one. If I take one real rule out of the file, do agents follow it less on the same tasks? If they do, the rule was doing something.

RQ2: what kind of rules work? "Do this" versus "don't do this", rules that name a specific file or command, and rules the linter already checks. The do-versus-don't part I test directly, because I write the same rule both ways. The other two I can only compare across rules, so I'll call them patterns, not causes.

RQ3: does keeping a rule make the code better? Tests, complexity and warnings, with the rule versus without it, on the same task. I leave out any check that is basically the rule itself, or the answer would be yes by default.

[Next slide]

Slide 6. Design (about 80 seconds)

Cue: real pull request, five versions, two agents, script checks the rule, 1,800 runs, pilot, two limits

One test works like this. I take a merged pull request from a real project. Its tests fail before the change and pass after. The agent gets the code from just before it, with no git history. The task doesn't mention the rule.

I run that task with five versions of the file: the original, the rule taken out, the rule reworded, a neutral sentence of the same length, and no file. The neutral sentence tells me the effect comes from the rule, not just from a longer file.

Claude Code and Codex get the same text, three runs per version, in a fresh container each time. A script counts how often the rule was followed where it applies, and I'll check each script by hand on at least 20 examples.

30 rules with two tasks each is at most 1,800 runs, roughly 1,300 to 1,900 dollars. A small pilot on two repositories comes first to get the real numbers.

Two limits: I can only study rules a script can check, and one rule at a time won't show how rules affect each other.

[Next slide]

Slide 7. Plan and expected results (about 60 seconds)

Cue: year 1, year 2, dataset, evidence, small tool, why this lab

Year one is courses in software engineering and statistics, the checkers, the pilot, and the main experiment. I'll also start looking at real pull requests. Year two is the code quality part, a first paper, and a small tool that flags rules agents ignore, which developers will rate.

So I hope to end up with a public dataset of real, checkable rules, evidence on which kinds of rules work, and that tool.

Why your lab? You've studied these files, and what happens to agent code after it's merged. Your pull request paper even recommends keeping a file like CLAUDE.md. My study asks the next step: once you write those rules, does the agent follow them? And I want to learn how you mine repositories and measure code quality.

That's all from me. Thank you, and I'd be happy to hear your questions and advice.

[Stop sharing.]

Part C. After the slides

Right after the last slide:

I'll stop sharing so we can talk.

Useful lines during the questions:

  • Did not hear the question: "Sorry, could you say that again?"
  • Need a moment: "Good question. Let me think for a second."
  • Do not know: "I'm not sure yet. I'd check it by ..." (then say how).
  • Want to check you understood: "Do you mean ...?"

When they ask "Do you have any questions for us?":

Yes, one. I saw that the Information Science IPGP scholarship is open until 13 November, for October 2027 entry. If you think my application is a good fit, could I apply with the lab's support?

Second question, only if there is time:

Is there anything you'd suggest I read or build before I start, so I can be useful to the lab from the first month?

Closing:

Thank you so much for your time, Dr. Ji and Dr. Reid. I really enjoyed talking with you, and I look forward to hearing from you.

[Wait for them to end the call, or say "Goodbye" and leave after they do.]
