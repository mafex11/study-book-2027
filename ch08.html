1.5 What he seems to value as a researcher [INFERENCE, from his own writing]

3. Papers in depth (most relevant first)

3.1 Causality-Aided Evaluation and Explanation of LLM-based Code Generation (ISSTA 2025)

  • Citation: Zhenlan Ji, Pingchuan Ma, Zongjie Li, Zhaoyu Wang, Shuai Wang. Proc. ACM Softw. Eng. 2(ISSTA), 2025, pp. 1374 to 1397. DOI 10.1145/3728938 [10]. Preprint: arXiv 2310.06680 (2023, titled "Benchmarking and Explaining LLM-based Code Generation: A Causality-Centric Approach").
  • Note on versions: the 2023 preprint used 3 models and APPS only. The published version adds Qwen-2.5-Coder (14B), BigCodeBench, two validation pilot studies (PS1, PS2; the preprint had one small pilot) and a human evaluation of the graphs. The numbers below are from the published version [10].
  • Problem: the same intent, written in different words, gives different code. Benchmarks report pass rates but "fail to capture the interplay between the prompt and the generated code" [10].
  • Method:
    • Causal chain: rephrasing instruction (meta-prompt) → prompt (described by 255 linguistic features from LFTK) → 10 code metrics in 5 groups: correctness, diversity, overhead, readability (black PEP8 count), security (Semgrep count).
    • 12 rephrasing intentions chosen from over 20: instructions (Long, Short, Formal, Fluent, Technical, Logical), roles (Student, Programmer, Competitor) and scenarios (Clearer, Improve, Specify). GPT-3.5-Turbo does the rephrasing.
    • Data: 6K sampled APPS problems plus all of BigCodeBench (1K). Models: GPT-Neo, GPT-3.5-Turbo, GPT-4, Qwen-2.5-Coder. Three solutions per data point "to avoid the randomness of LLMs".
    • Causal discovery with DiBS, in two steps (meta-prompt → features, features → code). Effects estimated as the average treatment effect, ATE = E[Y | do(X = x1)] - E[Y | do(X = x2)], with double machine learning (EconML).
    • Algorithm 1: find the 3 code metrics most affected by each instruction, then find the linguistic features that carry the effect ("potential mediators").
  • Key results:
    • Rephrasing followed the instruction in 93.5% of checked cases on average (100 sampled questions) [10].
    • Rephrasing changed the code metric distributions: Pillai's Trace 0.9961 to 0.9986, p = 1.1e-16 [10].
    • Learned graphs: five experts found error rates below 10% for every model (highest 9.26%, GPT-3.5 on APPS); Kappa 0.80 to 0.94 [10].
    • On APPS, Long and Formal tended to hurt and Short and Fluent tended to help, but "this pattern is not as evident on BigCodeBench" [10].
    • Roles and scenarios helped stronger models more than GPT-Neo [10].
    • Prompt search with a genetic algorithm on APPS: for GPT-4, similarity to the reference rose by 15.47% versus 9.33% for the best single instruction (original 0.4867) [10].
  • Limits they state: few models and datasets; few rephrasing instructions; the application is "a proof-of-concept study in an idealized setting"; graphs differ so much by dataset that "it is impossible to learn a universal causal graph" [10]. They also assume the linguistic features are a sufficient proxy for the prompt and use DiBS's standard assumptions "such as causal sufficiency" [10].
  • Why it matters to you: this is the nearest paper to your RQ2 wording question. He rewrites the whole prompt and studies standalone programming problems (APPS, BigCodeBench). You rewrite one rule inside a real file and study repository-level agents. His finding that results change between datasets supports your random effects for task and rule.

3.2 CAM: A Causality-based Analysis Framework for Multi-Agent Code Generation Systems (ISSTA 2026)

  • Citation: Zongyi Lyu, Zhenlan Ji (NAIST, co-corresponding), Songqiang Chen, Liwen Wang, Yuheng Huang, Shuai Wang, Shing-Chi Cheung (co-corresponding). Proc. ACM Softw. Eng. 3(ISSTA), Article ISSTA147, Oct 2026. DOI 10.1145/3832238. arXiv 2602.02138 v3. Local: 04_Papers/A_Iida_Lab_papers/L12_...pdf [11]. Full guide: 04_Papers/GUIDE_2_more_lab_papers.md, section L12.
  • Problem: which intermediate outputs of a multi-agent code generator (MetaGPT) actually cause correct code? Asking an LLM works badly: GPT-4o names the failure-causing output in only 41% of 100 cases, because LLMs pick outputs "merely correlated with failures" [11]. "All-but-one" ablation removes whole agents and ignores that parts are "cross-dependent" and "non-additive" [11].
  • Method: actual causality (Halpern: AC1 actuality, AC2 counterfactual dependence, AC3 minimality). 12 features in 4 categories. An LLM rewrites one feature, or a group of up to 5, into a plausible but wrong version. They rejected random noise, rule-based edits and "direct text deletion" because deletion "causes information loss without reflecting plausible failures". 99 of 100 sampled interventions were judged coherent. Feature responsibility adds (1/size)^2 per important group [11].
  • Key results: Kendall's correlation with human rankings 0.76 to 0.91. For Program_Lang, only 21.2% of its important groups are the feature alone; 78.8% need other features. Groups of 2 or more carry 18.4% of all responsibility (size 1: 81.6%). Repair by fixing the top 3 features: 73.6%. Pruning low-ranked features cut intermediate tokens by up to 33.6%. Hybrid backends: up to 7.3% relative Pass@1 gain [11].
  • Limits they state: 3 models and 4 benchmarks; subjective manual rankings (two annotators); randomness handled by temperature 0 and three runs. Cost about 25M tokens and 8 to 12 hours per setting [11].
  • Why it matters to you: same logic as your experiment (change one part, hold the rest, measure the outcome). It is also the strongest argument against your one-rule-at-a-time design. Know the 18.4% and the 78.8%.

3.3 Function Calling as a Flexible LLM Defense Add-On (ISSTA 2026)

  • Citation: "Function Calling as a Flexible LLM Defense Add-On: Capability and Application Exploration". Zhenlan Ji (NAIST), Daoyuan Wu, Wenxuan Wang, Pingchuan Ma, Shuai Wang, Lei Ma, Juergen Rahmel. Proc. ACM Softw. Eng. 3(ISSTA), 2026, pp. 2704 to 2726. DOI 10.1145/3832209. Published 1 Oct 2026 [12]. I read the full text from the ACM Digital Library; a text copy is in 04_Papers/D_Interviewers_papers/.
  • Problem: jailbreak defenses are slow, hurt helpfulness, and are static, while each app has its own rules [12].
  • Method: define "defense functions" that describe forbidden actions (12 categories based on OpenAI's usage policies and a taxonomy by Shen et al., for example prepare_illegal_activity). If the model's intent matches, it calls the function, which raises an alert. Baseline: the same rules written in the system prompt as instructions to refuse. The authors call the two "goal-equivalent": "prompt-based defense instructs the model not to do something, while FC encourages the model to do the same thing" [12]. Models: GPT-3.5-Turbo, GPT-4o-mini, GPT-5.4-mini, Claude-3.5-haiku. Data: WildJailbreak; helpfulness on MMLU-Pro; a new dataset DSpec (1,000 samples, 7 application scenarios) [12].
  • Key results (defense rate, Table 2) [12]:
Model No defense Same rules in prompt Function calling (total)
GPT-3.5 0.1592 0.7338 0.7934
GPT-4o 0.4080 0.7144 0.7666
GPT-5.4 0.8300 0.8680 0.9850
Claude-3.5 0.1295 0.8560 0.9765
  • Model names in the table: GPT-4o = GPT-4o-mini, GPT-5.4 = GPT-5.4-mini (reasoning off), Claude-3.5 = Claude-3.5-haiku. Columns: no defense, prompt refused, FC total (refused plus triggered) [12].
  • On DSpec, average attack success fell from 0.845 to 0.080 with function calling [12].
  • Helpfulness for GPT-3.5 fell from 0.4902 to 0.2416 with function calling and to 0.0931 with the prompt rules. They give two reasons: GPT-3.5 is less able to cope with an added defense, and the functions are very general [12].

  • Refusals were detected by string matching; an LLM judge agreed over 95% [12].

  • Limits they state: black-box threat model; the function list could leak through prompt leakage; tested against one adaptive attack (GCG) under a leaked setup [12].

  • Why it matters to you: same rules, different delivery, different defense rate. That is close to your RQ2 linter property (is a rule a tool already enforces still worth writing?). It is not your Year 2 checker, which flags rules agents tend to ignore, rules that conflict and rules a linter already covers [26b]. Be careful: the defense functions are still text the model reads ("the function specification is converted to prompt-like text and fed into the LLM"), and the model itself decides whether to call one. The authors explain the gain as a "honeypot" that lures out the model's intent, not as enforcement outside the model. The outcome is defense rate against jailbreak inputs, not general compliance [12]. Note also that in this comparison polarity ("do not" versus "do") and delivery change together. In your design you change only polarity.

3.4 Digging Into the Internal: Causality-Based Analysis of LLM Function Calling (arXiv 2025, preprint)

  • Citation: Zhenlan Ji, Daoyuan Wu, Wenxuan Wang, Pingchuan Ma, Shuai Wang, Lei Ma. arXiv 2509.16268, Sep 2025 [13]. [INFERENCE: it is a companion to 3.3, with an overlapping author list. I cannot confirm it was published.]
  • Problem: function calling "can substantially enhance the compliance of LLMs with user instructions". Why? [13]
  • Method: layer-level and token-level causal interventions inside the forward pass (ablate or replace hidden representations) on Llama-3.1-8B, Llama-3.1-70B, Hermes-3-8B and Mistral-22B, with and without function calling [13].
  • Key results: function calling changes which layers matter, and makes models less distracted by jailbreak snippets. Function calling gave "an average performance improvement of around 135% over conventional prompting methods in detecting malicious inputs". Figure 1 example (Llama-3.1-70B): 81.3% detected with a prompt, 98.3% with a function [13].
  • Why it matters to you: he studies instruction compliance directly, from inside the model. You study it from outside, through the files developers write. Both ask why some instructions are followed more than others.

3.5 Understanding and Bridging the Planner-Coder Gap (arXiv 2025, preprint)

  • Citation: Zongyi Lyu, Songqiang Chen, Zhenlan Ji (corresponding), Liwen Wang, Shuai Wang (corresponding), Daoyuan Wu, Wenxuan Wang, Shing-Chi Cheung. arXiv 2510.10460 v2, Jan 2026 [14]. Google Scholar also lists it as "Testing and Enhancing Multi-Agent Systems for Robust Code Generation" [5].
  • Problem: are multi-agent code generators robust to inputs that mean the same thing? [14]
  • Method: four meaning-preserving mutation operators run by GPT-4o: Rephrase, Insert, Expand, Condense. Manual check of 500 mutants: 99.2% kept the meaning; Sentence-Transformers similarity 98.4% on average. Fuzzing guided by a fitness function on code and plan differences. Systems: Self-Collaboration, MetaGPT, PairCoder. Models: GPT-3.5-Turbo, GPT-4o, DeepSeek-Coder-V2. Data: HumanEval-ET, MBPP-ET, CodeContest, CoderEval [14].
  • Key results: systems failed 7.9% to 83.3% of problems they had solved before the mutation. The "planner-coder gap" explained 75.3% of failures (5 error patterns). Their repair (multi-prompt generation plus a monitor agent) fixed 40.0% to 88.9% of failures; detected failures fell by up to 85.7% [14].
  • Limits they state: representativeness; reliability of mutations (hence the 500-mutant check); subjectivity of failure labels (two developers, disagreements resolved) [14].
  • Why it matters to you: wording alone changes agent behavior a lot, which supports RQ2. And it gives you a method: validate rewordings by hand on a sample and report the rate.

3.6 Bridging the Gap between Causal Inference and Software Engineering (ASE 2025 tutorial)

  • Citation: Pingchuan Ma, Zhenlan Ji, Zongjie Li, Shuai Wang. ASE 2025 Tutorials, Seoul, 16 Nov 2025 [8].
  • Content (from the abstract only): "While correlation doesn't imply causation, being able to tell the difference is essential in software engineering, where systems often involve complex interactions between variables." It introduces causal inference, applies it to "debugging and testing", and stresses a "two-way synergy": SE practices "like testing and verification, can inform and improve causal inference techniques" [8].
  • Limits: I found no slides or recording.
  • Why it matters to you: expect him to test whether you can tell correlation from causation in your own plan. C24 is your best answer.

3.7 Testing and Understanding Erroneous Planning in LLM Agents (PDoctor, arXiv 2024, preprint)

  • Citation: Zhenlan Ji, Daoyuan Wu, Pingchuan Ma, Zongjie Li, Shuai Wang. arXiv 2404.17833 [15].
  • Problem: agents make wrong plans on long tasks, and there is no oracle to detect it [15].
  • Method: a DSL for user requests; the Z3 solver synthesizes natural language requests and derives constraints that act as the test oracle; mock tools record the agent's action sequence. Frameworks: ReAct, OpenAI Tools, OpenAI Assistant. Models: GPT-3.5 and GPT-4 [15].
  • Key results: GPT-4 agents had 48.53% lower error rates on average than GPT-3.5 agents. Error causes were similar across models but differed across frameworks: "agent frameworks play a more significant role in determining the error cause than the model itself". The OpenAI Assistant framework "cannot set the temperature", which led to more randomness errors [15].
  • Why it matters to you: (1) an automatic, checkable oracle, like your script checkers; (2) the harness matters, which is why you compare Claude Code and Codex as products, not models; (3) PDoctor found randomness errors even in frameworks set to temperature 0, so repeated runs are needed either way [15]. Neither the official Claude Code CLI reference nor the Codex config reference documents a temperature setting (checked 25 Oct 2026). Say: "As far as I know, neither CLI lets me set temperature, so I treat each file version as a distribution of runs and use repeated runs."

3.8 Evaluating LLMs on Sequential API Call Through Automated Test Generation (StateGen, arXiv 2025, preprint)

  • Citation: Yuheng Huang, Jiayang Song, Da Song, Zhenlan Ji, Wenhan Wang, Shuai Wang, Lei Ma. arXiv 2507.09481 v2 [16].
  • Problem: tool-use benchmarks use hand-made tests and string matching, and ignore dependencies between calls [16].
  • Method: state machines of APIs, constraint solving, sampling and control-flow injection generate executable programs; two LLM agents turn them into task text. Benchmark StateEval: 120 manually verified cases in Session Service, Tensor Operation and ElevenLabs MCP. Checks include server-side state, not only assertions [16].
  • Key results: pass@1: GPT-4.1 56%, Gemini-2.5-Flash 45%, GPT-4.1-nano 35%, Llama-4-Scout 34%, Qwen2.5-Coder 25%. GPT-4.1 reached 78% on Tensor Operation, more than double its Session Service score [16].
  • Why it matters to you: a tool-evaluation paper. It shows his group's habit of generating tests automatically and checking real effects, not text.

3.9 Reassembling Distributed Risk (ReDiR, arXiv 2026, preprint)

  • Citation: Yanbo Dai, Zhenlan Ji (NAIST), Zongjie Li, Shuai Wang. arXiv 2608.25711, Aug 2026 [21].
  • Problem: in multi-turn attacks, a harmful goal is split across harmless-looking requests (for example, one helper returns "rm -rf", another returns "/"). It shows only in the whole trajectory [21].
  • Method: before each action, compress the trajectory into a latent safety representation and inject it into the frozen model [21].
  • Key results: attack success below 8% on MT-AgentRisk and AgentDojo, across Qwen3.5-9B, Ministral-3-8B-Instruct and Gemma-4-E4B; the strongest competing defense stays around 20% to 34%; below 7% on eight held-out tool domains [21].
  • Why it matters to you: it is a direct challenge to the Yuki 2.0 checker, which judges one step against the user's words (see 6d).

3.10 Earlier causality work (ICSE 2023, ASE 2023 x2, ICSE 2024)

  • CC: Causality-Aware Coverage Criterion for DNNs. Ji, Ma, Yuan, Wang. ICSE 2023 [9]. Problem: neuron and layer coverage ignore "how one neuron would influence subsequent neurons". Method: score a test suite by how many new causal relations among neurons it exercises. Result: "CC outperforms previous DNN criteria under various settings with moderate cost" [9]. Code: DL_CC [6]. I did not read the full paper. Why it matters: coverage of interactions, not single units, the same instinct as CAM.
  • PerfCE. Ji, Ma, Wang. ASE 2023. arXiv 2207.08369 [18]. Problem: root causes of database slowdowns; correlation-based debugging misleads. Method: learn a causal graph from passive observations plus active chaos experiments (Chaos Mesh), then answer counterfactual queries. Evaluated on MySQL and TiDB, with up to 254 KPIs [18]. Why it matters: it mixes observational and interventional data, like your real pull request study plus your experiment.
  • Causality-Aided Trade-off Analysis for ML Fairness. Ji, Ma, Wang, Li. ASE 2023. arXiv 2305.13057 [19]. Data: Adult, COMPAS, German; 12 fairness-improving methods. Findings: the choice of metrics "can significantly affect the pattern of observed trade-offs"; AOD and Theil Index often drive trade-offs; a fairness and robustness trade-off is "inevitable" [19]. Why it matters: for RQ3, report each quality metric separately, because metrics can trade off.
  • CICheck: Runtime Verification of Causal Discovery. Ma, Ji, Yao, Wang, Ren. ICSE 2024. arXiv 2309.05264 [20]. Causal discovery depends on conditional independence tests that "can often be unreliable". CICheck checks them against Pearl's axioms with SMT, to detect wrong tests and prune extra ones [20]. Why it matters: he checks the checker. So check yours (C19).

4.2 Threats to validity he is most likely to raise

  • Interactions (CAM). Answer with C27. Do not say they are rare.
  • Meaning drift when rewording (planner-coder; ISSTA 2025 assumed meaning was kept). Answer with C11 plus a hand-check rate.
  • Confounding in RQ2 properties. Possible confounders: rule category, the base rate of the behavior in the existing code (the no-file version measures it), the repository, the length of the rule. Say: "I can adjust for some of these, for example category and the no-file rate, but I still call it association."

6. Questions he could ask you, with short model answers

6a. About your proposal

Q1. What is your treatment, your outcome, and what could confound it? (C24, C7)

The treatment is the file version, which I assign. The outcomes are compliance with the rule, hidden test results, complexity and warnings. The task, the starting commit, the agent version and the container stay the same, so the task cannot confound RQ1 and RQ3. Specificity and linter coverage are rule properties I do not assign, so those results are associations.

Q2. Define "effective" as a causal quantity. (C3)

It is the difference in compliance when the rule is kept versus removed, on the same tasks, so an average treatment effect. The mixed logistic model gives an odds ratio for a typical task and rule. To report the average difference in shares, I average the model's predicted compliance for each version over all tasks, and I also show the raw difference. A rule can be followed but not effective, if agents do it anyway.

Q3. What does the neutral sentence control for? (C9)

Adding a rule also adds text. The neutral sentence has the same length and position but gives no instruction. So original versus neutral is the effect of the content, and neutral versus removed is the effect of just having more text.

Q4. You remove one rule at a time. Your CAM paper says effects are non-additive. (C27)

Yes, that is a real limit. In CAM, groups of features carried 18.4% of the responsibility, and Zhang et al. found two of five rule pairs clearly non-additive. I measure what happens when a developer deletes one rule from the real file, with the rest in place. If the pilot shows related rules, I can test a few pairs and compare them with the sum of single effects.

Q5. How do you know the reworded rule means the same thing? (C11)

A fixed template flips only the polarity, and a second person checks every pair. Following your planner-coder paper, I would also report the share of pairs judged to keep the meaning. If a rule cannot be flipped without adding or losing information, I leave it out and report how many.

Q6. Specificity is not randomized. Can you get closer to a causal answer? (C24, C5)

One way is to write a specific and a vague version of the same rule, as I do for wording. But that changes the information in the rule, so it answers a slightly different question. Otherwise I can adjust for confounders I can measure, like rule category and the no-file compliance rate, and still call it association. I would like your advice on which is better.

Q7. Does quality change because the rule was followed? (C23)

That is a mediation question. Comparing file versions on the same task is causal. But compliance is not assigned, and task difficulty can affect both compliance and quality, so a mediation analysis needs extra assumptions. I would report it as exploratory.

Q8. Agents are random. Is 3 runs enough? (C25)

For one rule, no, and I will not make strong per-rule claims. The main test pools all rules, about 180 removed-rule runs per agent. I treat each version as a distribution of runs, as your ISSTA 2025 paper recommends, and the pilot will show the spread and set the final number. As far as I know, neither the Claude Code CLI nor the Codex CLI lets me set temperature, so repeated runs are the way to handle the randomness.

Q9. Why a mixed logistic regression and not causal discovery like your papers? (C22)

Because I can intervene directly. Causal discovery is for when you cannot assign the treatment. I assign the file version, so a regression on the experimental data estimates the effect. Task and rule are random effects because some are easier than others. I am still learning these models; statistics is in my Year 1 plan.

Q10. Why not let an LLM judge compliance? (E11)

A script gives the same answer every time, and I can measure its accuracy on hand-checked examples. In Harness-IF, swapping the judge model gave only 62.1% agreement. Your function calling paper did it carefully: string matching, checked against an LLM judge, over 95% agreement. I would do the same: scripts for the core study, and an LLM judge later only for rules a script cannot check, checked by a person and reported separately.

Q11. Public pull requests may be in training data. Is that a confounder? (C16)

It affects every version of the same task, so it should mostly shrink differences, not create them. But the original file might cue memory more than an edited one, so I cannot fully rule out a false gap. I prefer tasks after the training cutoff and report older and newer tasks separately.

Q12. Claude Code and Codex differ in model and harness. Is "agent" a clean factor? (C17)

No, and I do not claim it is. "Agent" means the product: harness plus model. Your PDoctor paper found the framework mattered more than the model for the cause of errors, so separating them is a different study.

Q13. The real pull request study: what confounds it, and how would you analyze it? (C33, C34)

Rules are often added right after agents break them, so violations may drop anyway. Models also improve over time, and linters change. Human pull requests in the same repositories share the time trend, so I compare the change for agent pull requests with the change for human ones, a difference-in-differences idea. I report it as associations only.

6b. About his own work

Q14. What did you take from my ISSTA 2025 paper?

Two things. First, the idea of rephrasing a prompt with a fixed set of instructions to create controlled variations, and measuring several code metrics, not only pass rate. Second, your finding that the pattern on APPS was not as clear on BigCodeBench, which warns me not to generalize from one repository.

Q15. How would you extend that paper to coding agents?

I would keep the task fixed and vary one rule in the context file, not the whole task text, because developers edit rules, not tasks. The outcomes would be compliance with that rule and code quality in a real repository. If a reworded rule works better, your mediator analysis could help explain which features of the wording carry the effect.

Q16. How does your design relate to CAM?

It is the same logic: change one part, hold the rest, and measure the outcome. CAM goes further by searching groups of up to five features, with a budget of 100 runs per problem. My budget is smaller, so I start with single rules and accept that I miss interactions.

Q17. CAM rejected deletion as an intervention. You delete rules. Why?

CAM asks which outputs matter when an agent makes a realistic mistake, so deletion would be unrealistic there. My question is about a choice developers really make: keep the rule or delete it. So deletion is the realistic intervention for my question. The neutral sentence covers the length change that deletion causes.

Q18. What does the function calling paper mean for context files?

It shows that the same rules, given in a different form, changed how often the model caught jailbreak attacks: for Claude-3.5-haiku, 0.8560 with the rules in the system prompt and 0.9765 with defense functions. The model still decides to call the function, so it is a different channel, not outside enforcement. A linter or hook goes further, because it does not depend on the model. That is why my linter question asks whether a rule a tool already enforces still needs to be written down. One thing I noticed: there, polarity and delivery change together, and in my rewording only polarity changes.

Q19. How does the planner-coder gap paper relate?

It shows that meaning-preserving rewording alone made systems fail 7.9% to 83.3% of problems they had solved. So wording matters, which is why I test it. I would borrow its method of checking rewordings by hand on a sample.

Q20. Give an example of correlation versus causation in your own plan. (D10)

In real pull requests, compliance may rise after a rule is added. But rules are often added right after violations, and models improve over time, so the rise could happen without the rule. That is a correlation. In the experiment I add or remove the rule on the same task, so the difference comes from the rule.

Q21. Did you read my other work?

Only the abstracts of PerfCE, the fairness trade-off paper and CC, not the full papers. PerfCE combines passive observation with chaos experiments; my plan has a similar shape, with the real pull request study as the passive part and the experiment as the active part.

Say this only after you have read those three abstracts. Of his papers, only CAM is on your reading list (question bank B22).

Q22. Would causal discovery help your study?

Maybe for the real pull request data or for explaining RQ2, where I cannot assign the treatment. But it needs strong assumptions, like no hidden confounders, and my sample of rules is small. For the core questions I prefer direct intervention.

6c. About your work and projects

Q23. Was your BrandMemory A/B test causal? (B10)

In a narrow sense: after both fixes, I generated the same product demo with and without the rules. But it was one demo and one comparison, with one output on each side and no statistics, so it is not evidence that rules work in general. It taught me to measure whether a model follows an instruction instead of assuming it.

If he quotes your pre-application text, "I ran A/B comparisons" (plural), use your B10 answer:

Yes, there were a few. Before the fix, on and off pairs were nearly identical. After the fix I ran an offline comparison on a test demo, and then the live pair on our beta system. The live pair is the one I report in the proposal.

Q24. What were the two failures in BrandMemory, in causal terms? (B9)

Some rules never reached the model, because they sat at the end of a long prompt that was cut off, so the treatment was never delivered. Others were overridden by a default house style elsewhere in the prompt, so two instructions interacted and one won. I found it because projects with brand memory on logged that the guidance was applied, but the output had no trace of the brand voice, and on and off pairs looked almost the same. So I traced what the model actually received. The brand voice section had the lowest priority in the prompt, so it was the first thing cut at a 3,200-character limit.

Q25. How did you evaluate the Yuki 2.0 checker? (B21)

I replayed past requests offline. It held 9 of 9 actions the user had not asked for and 0 of 36 that the user had asked for. That is 15 cases, 3 unasked and 12 asked, each replayed 3 times, and I tuned the checker on the same cases. So it is a check, not a held-out test.

Q26. What did Yuki teach you about rules? (B15)

Rules in the prompt kept growing after each incident: one night the voice prompt grew 30% and the planner prompt 69%. The agent followed the words but lost the goal. So I moved hard rules into code and put a size limit on the prompt. That is a bit like your function calling result, where the form of the instruction mattered. Moving a rule into code goes one step further, because the model no longer decides.

Q27. What did you build yourself in Yuki for Mac? (B15)

The agent core is built on a fork of MacOS-Use. I added things like tool retrieval for small models, the eval set, and a hard stop after three identical actions in a row; the repeat detection itself came with the fork. On my small eval, retrieval helped a local 7B model pick the right first tool in 9 of 10 cases. On top of the fork I built the Mac app itself, a SwiftUI menu bar app with a typed command bar that runs a Python backend, and I changed how the agent acts, so it presses the real accessibility element instead of clicking coordinates. I also added a leaner accessibility tree, LoRA fine-tuning experiments, a Stop button, an automatic pause when the user touches the mouse or keyboard, and a local memory of apps, window titles and music, and I shipped it from v0.1.0 to v0.5.1 through GitHub Releases and Homebrew.

Q28. How do you use coding agents at work? (B18)

I use Claude Code and Codex every day, review the changes they make, and maintain our CLAUDE.md and AGENTS.md files. Once an agent applied a database change directly instead of writing a migration file. The change worked, but it broke our migration history and blocked a deploy. So I added a rule to the instructions my coding agent reads: always write a migration file and let the deploy pipeline apply it, and never push changes straight to the shared database. I have not measured whether agents follow it every time. That is where my question comes from: I write rules and I do not know which ones matter.

6d. Curveballs and tough ones

Q29. Isn't this just an A/B test? Where is the research? (E9, C39)

The method is simple on purpose. What is new is the combination: one real rule from a developer's file, removed or reworded in place, on real tasks from the same repository, two production agents, and both compliance and code quality measured with scripts. As far as I know, that combination has not been done.

Q30. Your causal claim holds for two agents at fixed versions. Is it worth anything next year? (E10, C29)

The exact numbers will age. The method and the dataset will not: I release the scripts, file versions and tasks so anyone can rerun with new agents. Which kinds of rules are effective may change more slowly than model versions, but that is a hypothesis, not a promise.

Q31. My ReDiR paper shows risk can be split across turns. Your Yuki checker sees one step. Isn't it broken?

For that kind of attack, yes, a per-step checker can miss it. I saw a related gap, though not a multi-turn attack: the checker once saw only part of a PowerShell command that would keep acting later, and only my test harness caught it. Now the whole command is checked and "later" effects are refused, but it still does not reason over the whole trajectory.

Q32. You have no statistics course. What is an odds ratio? (D7, D10)

Odds are the probability of following the rule divided by the probability of not following it. An odds ratio compares the odds in two conditions, for example kept versus removed; 2 means the odds doubled. I know the basics, not the depth, and a statistics course is in my Year 1 plan. At VTU, probability and basic statistical inference were part of my third-semester mathematics course, Mathematics for Computer Science. It covered probability distributions, sampling, hypothesis tests such as the t-test and chi-square test, and basic ANOVA. For this plan I studied logistic regression and mixed effects models on my own.

Q33. What if removing rules shows no effect at all? (C37)

Then that is a result, if the study had enough power, and I would report intervals so it is clear what size of effect I could miss. It would suggest agents follow many rules because the code already shows the pattern, which the no-file version measures. Developers could then shorten their files and save cost.

Q34. Why not study the model's internals, like my function calling analysis?

Claude Code and Codex are closed products, so I can only change their inputs. I chose them because developers use them. Your internal analysis needs open models; an open-weight agent could be a small extra check later, not the core.

Q35. Which part of your plan are you least sure about? (C31, E16)

Two things. Building enough runnable tasks: Gloaguen et al. got 138 tasks from 5,694 pull requests, so the pilot counts usable tasks first. And the cost estimate, which uses per-task costs from Gloaguen et al. on their tasks and models.

Q36. If I asked you to change the topic toward my area, would you? (E3)

I would be open to it, especially if it keeps the link to coding agents and rules. Causal analysis of why an agent follows or ignores an instruction is close to my question. I would want to keep a part where I measure real developer files.
