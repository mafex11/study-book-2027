This guide covers references [4] to [12] of your proposal, except [9] (a lab paper, see GUIDE_1), and the 4 extra papers in C_Extra_background/. Every number below comes from the PDF in this folder (read on 21 Oct 2026). Where something comes from our dossier and not from the paper, it says so.

How to use it:

  1. Learn the novelty map (section 0) first. It is how you defend your idea.
  2. For each paper, know the one breath summary, 2 or 3 numbers, and the "how my study differs" lines.
  3. Practise the model answers out loud. They are in your voice.

Small notes:

  • "pp" means percentage points (for example 49% to 72% is +23 pp, not +23%).
  • File names: REF4 = your reference [4], and so on.

What is new, in one breath

"I take one real rule from a developer's own CLAUDE.md or AGENTS.md, remove it or reword it while the rest of the file stays the same, run Claude Code and Codex on real tasks from that same repository, and measure with scripts both whether the agent follows that rule and whether the code quality changes."

What is NOT new (say this before they do)

  • Removing one rule at a time: Guardrails [6] did it for 18 generic rules (pass rate only). Agent Skill Evolution [11] did it for SKILL.md rules.
  • A same-length neutral text control: [11] used "unrelated text of the same length". My neutral sentence is the same idea, applied to context files.
  • Scoring a rule against a run without it: Harness-IF [10] (to label rules) and McMillan [7] (no-file baseline).
  • Real PR tasks with Claude Code and Codex, with the file written as CLAUDE.md for Claude Code and AGENTS.md for Codex: Gloaguen [5].
  • Real merged-PR tasks with both Claude Code and Codex: also Khatri. But Khatri removed AGENTS.md from the workspace and gave its text through the system prompt (Claude Code) or the user prompt (Codex).
  • Mixed-effects logistic regression with the task as a random effect: McMillan [7] did this for compliance.
  • Before and after mining of a rule: the lab's own [2] (2 repos) and Cai [12]. Voria and Kashiwa [9] link file changes to later code quality.
  • Negative vs positive rules: Guardrails [6] compared different rules. Our dossier also lists a registered-report protocol by Lulla, Galster, Zhang, Baltes and Treude (arXiv 2606.03907) that plans to test prohibition vs preference wording for one behaviour. It is not in this folder and I have not read its full text.

What remains open (as far as I found)

No single paper does all of these together: (a) one real, developer-written rule in CLAUDE.md or AGENTS.md, changed while the rest of the file stays fixed; (b) real tasks from the same repository; (c) both production agents; (d) script-checked compliance and code quality that the rule itself does not check; (e) the same rule reworded, so wording is separated from content; (f) "already enforced by the linter" checked against the project's real linter settings.

Always say "as far as I found", never "nobody has done this". The field moves every week.

[4] AIDev: Studying AI Coding Agents on GitHub

  • Authors: Hao Li, Haoxiang Zhang, Ahmed E. Hassan (Queen's University, Canada)
  • Venue / status: MSR '26 (13 to 14 April 2026, Rio de Janeiro). DOI 10.1145/3793302.3797249 (from the arXiv page).
  • arXiv: 2602.09185 (v1, 9 Feb 2026)

One breath: A public dataset of 932,791 pull requests written by five coding agents on GitHub, with a richer subset from popular repositories.

What they did

  • Collected "Agentic-PRs" made by OpenAI Codex, Devin, GitHub Copilot, Cursor and Claude Code, and linked each PR to its repository and developer.
  • For repositories with more than 100 stars, added review comments, reviews, commits, file-level diffs, linked issues, full PR timelines, and a GPT-based label of the PR's purpose (Conventional Commits categories).
  • Released on Hugging Face and Zenodo, with example notebooks.
  • Listed open research questions. One is very close to yours: "Do Agentic-PRs conform to project conventions and CI checks (linters, formatters, license headers)?"

Key numbers

  • 932,791 PRs, 116,211 repositories, 72,189 developers, cutoff 1 August 2025.
  • Curated subset: 33,596 PRs from 2,807 repositories with more than 100 stars.
  • In the subset: 88,576 commits, 711,923 file-level diffs, 28,875 reviews, 19,450 inline review comments, 325,500 timeline events.

Limitations

  • It is a short dataset paper. It has no validation section and no limitations section.
  • It contains agent PRs only. For a human comparison you must collect human PRs yourself.
  • Rich data (diffs, reviews) only for the subset with more than 100 stars.
  • From our dossier (Hugging Face check, not the paper): there is no table of context files and no full repository history; newer releases exist (a v4 with 2,743,854 PRs and a work-in-progress v5); some sub-tables in v3 and v4 are cut at 30 items per PR.

How my study uses it and differs

  • AIDev is my sampling frame, not my data. I use it to find Python repositories that have agent activity, a CLAUDE.md or AGENTS.md, and tests that run in a container.
  • I then clone each repository and work from its own git history.
  • My supporting study uses AIDev agent PRs before and after a rule was added. Their open question about conventions is the question I want to test with a controlled experiment.
  • Several lab papers also use AIDev (see GUIDE_1).

Likely questions

  • Q: AIDev stops in August 2025, but you want PRs merged after the models' training cutoff. How? A: I use AIDev only to choose repositories. The tasks come from each repository's own history on GitHub, so I can take recent merged PRs. Newer AIDev releases also go further, but I would check their dates first.
  • Q: Does AIDev contain the context files? A: No, as far as I know it has PR data, not the files or the full history. I would follow the lab's Agent READMEs method: take repositories from AIDev, look for a root CLAUDE.md or AGENTS.md with the GitHub API, clone them, and read the file history with git log.

[5] Gloaguen et al.: Evaluating AGENTS.md

  • Title: Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?
  • Authors: Thibaud Gloaguen, Niels Mündler-Sasahara, Mark Niklas Müller, Veselin Raychev, Martin Vechev (ETH Zurich, LogicStar.ai)
  • Venue / status: preprint, no venue
  • arXiv: 2602.11988 (v3, 29 Sep 2026)

One breath: On real Python tasks, context files did not significantly raise task success, but agents followed their instructions, explored and tested more, and cost rose by over 20%.

What they did

  • Built CTXbench: 138 tasks from 12 niche Python repositories that have developer-written context files, taken from 5,694 PRs. An LLM agent wrote the task descriptions and the tests. Authors reviewed all of them and edited the tests in 25 of 138 tasks.
  • Also used SWE-bench Lite (300 tasks), with LLM-generated context files.
  • Three settings: no file, LLM-generated file (each agent's own recommended /init), developer file.
  • Agents: Claude Code with Sonnet-4.5; Codex with GPT-5.2 and GPT-5.1 mini; Qwen Code with Qwen3-30B-Coder. One run per setting, temperature 0 (0.7 for Qwen).
  • The file was written as CLAUDE.md for Claude Code and as AGENTS.md for Codex and Qwen Code. Docker container, git history removed.
  • Trace analysis: GPT-OSS-120B labelled each shell command.
  • Appendix: removed one category (Overview, Tooling, Testing) from LLM-generated files with GPT-5.4, then reran with GPT-5.2. Also file length and contamination checks.

Key results

  • LLM-generated files: success fell 0.5% (SWE-bench) and 2% (CTXbench) on average, not significant (p = 0.87 and 0.37). Cost rose 20% and 23%. Steps rose by 2.45 and 3.92.
  • Developer files: success +2.4% on average, not significant (p = 0.21). They beat LLM-made files (p = 0.038). Steps +3.34, cost up to 19% higher.
  • Developer files helped every agent except Claude Code. On CTXbench, Sonnet-4.5 scored 73.2% with no file and 70.3% with the developer file.
  • Evidence that instructions are followed: uv was used 1.6 times per task when the file mentioned it, under 0.01 times when it did not. Repository tools: 2.5 vs under 0.05.
  • Reasoning tokens rose (for example +22% for GPT-5.2 on SWE-bench with LLM files, +20% with developer files).
  • Overviews did not help agents find the right files faster.
  • Category ablation (LLM-made files only): CTXbench accuracy 68.12% full, 66.67% without testing (p = 0.80), 62.32% without overview (p = 0.15), 63.77% without tooling (p = 0.31). No category changed accuracy significantly. Removing the testing section lowered cost significantly.
  • Cost per task (Table 2): Claude Code with Sonnet-4.5 1.15 to 1.51 USD; Codex with GPT-5.2 0.32 to 0.57 USD. These are the numbers in your budget.
  • Contamination: no consistent difference between PRs before and after each model's knowledge cutoff.

Limitations

  • Python only. The outcome is task success. They name efficiency and security as future work.
  • One run per setting. Task text and tests are LLM-written (reviewed by hand).
  • Their evidence that rules are followed is observational: files that mention a tool are compared with other files that do not. No single rule was removed.
  • The category ablation used only LLM-made files, because developer files have "no clear categories shared between them".

How my study differs

  • They change the whole file (or a whole category of an LLM-made file). I change one real rule and keep the rest of the developer's file.
  • Their compliance evidence compares different files. Mine compares the same file with and without the rule.
  • They measure task success. I measure compliance with the rule and code quality (complexity, warnings) on top of tests.
  • I reuse their good choices: CLAUDE.md for Claude Code and AGENTS.md for Codex, a clean container with no git history, PR-based tasks, and their costs for my first budget.

Likely questions

  • Q: Gloaguen already shows agents follow instructions. Why do you need RQ1? A: Their evidence comes from traces. Files that mention uv lead to more uv use, but those are different repositories from the ones that do not mention it. They did not remove one rule and compare. Also, they looked at tool use, not at rules about the code itself. I want the effect of each rule, because some rules are followed anyway.
  • Q: Context files did not raise success. Why should single rules matter? A: Success is one outcome. A rule like "put new tests in the tests folder" may not change whether tests pass, but it changes whether the code matches what the maintainers want. That is what I measure.
  • Q: Your budget uses their costs. Are they valid for your tasks? A: Only as a rough guide. They are per-task costs on SWE-bench-style tasks, and prices and models change. That is why the pilot on two repositories sets the real budget.

[6] Guardrails Beat Guidance (Zhang et al.)

  • Title: Guardrails Beat Guidance: A Large-Scale Study of Rules, Skills, and Persistent Configuration for Coding Agents
  • Authors: Xing Zhang, Guanghui Wang, Yanwei Cui, Wei Qiu, Ziyuan Li, Bing Zhu, Peiyang He (AWS Generative AI Innovation Center; HSBC)
  • Venue / status: preprint (v2, 28 May 2026)
  • arXiv: 2604.11088

One breath: With Claude Code and Opus 4.6 on SWE-bench Verified, any rule file raised the pass rate about equally (random rules as much as curated ones), and in a leave-one-out of 18 rules, the helpful rules were all "do not" rules and the harmful ones were all "do" rules.

What they did

  • Scraped 679 rule files (486 CLAUDE.md, 193 .cursorrules) and kept 25,532 rules. An LLM classifier (87% agreement with humans on 200 rules) put them in six categories. Project-specific rules were 64.9%, and the experiments excluded them.
  • Ran all 500 SWE-bench Verified tasks 3 times (1,500 runs) and kept 58 "discriminative" tasks solved 1 or 2 times out of 3.
  • Swapped the CLAUDE.md before each run.
  • Experiment 1: 8 rule sources (none, curated, random, popular, matched, mismatched, native, shuffled). Experiment 2: 0 to 50 rules. Experiment 3: 5 rule types. Experiment 4: 18 curated rules on 35 tasks: (a) remove each rule once, (b) each rule alone on 17 solved tasks, (c) rule pairs.
  • McNemar and Cochran's Q tests. Over 5,000 runs, about 2,000 USD in API cost (about 5 USD per task and condition).

Key results

  • No rules: 50.0%. All 7 rule conditions were 6.9 to 13.8 pp higher. Random rules 63.8% = curated rules 63.8%. No single comparison was significant (closest: random, p = 0.077). Across the 7 directions, a sign test gave p = 0.008.
  • 0 to 50 rules: pass rate stayed between 59% and 67%. 50 rules 66.7% vs 0 rules 60.3%.
  • Rule types: tool/process rules 63.8%, architecture rules 53.4% (not significant).
  • Leave-one-out from 65.7% with all 18 rules (5 pp threshold): 3 "shaping" rules, all negative: no unrelated refactoring (+20.0 pp, p = 0.016), no new dependencies (+8.6), no unrelated files (+5.7). 4 "distorting" rules, all positive: follow code style (-14.3), read test files (-14.3), handle edge cases (-11.4), preserve compatibility (-8.6). 11 inert.
  • Fisher test of the polarity split: p = 0.029. It weakens at a 7 pp threshold (p = 0.067) and disappears at 10 pp (p = 0.25). A threshold-free test gives p of about 0.13.
  • Note: not every "do not" rule helped. "No type stubs" and "no build changes" were inert (-2.9 each).
  • Baseline retest reliability on solved tasks: 88.2%, so each task flips about 11.8% of the time by chance.

Limitations

  • One vendor, one model, one benchmark (Python bug fixes).
  • With 58 and 35 tasks they can only detect effects of about 15 pp. Only rule 6 was individually significant, and it would not survive correction for 18 tests.
  • Discriminative task selection, pass rate only.
  • My own note: polarity is mixed with content. All their negative rules were scope or safety rules, and the positive ones were style or process rules.

How my study differs

  • Their tested rules are generic best practices they wrote. They excluded project-specific rules. I use exactly the project-specific rules developers wrote.
  • They measure pass rate. I measure whether the agent follows the rule, plus code quality.
  • They compare negative and positive across different rules. I reword the same rule, which separates wording from content.
  • One agent vs two. Rule files from elsewhere vs the file and tasks of the same repository.

Likely questions

  • Q: If random rules work as well as curated ones, does rule content matter at all? A: For pass rate, maybe not much. But for compliance, content must matter. An agent cannot follow "put tests in the tests folder" through priming alone. My neutral sentence of the same length is there to separate the priming effect from the rule itself.
  • Q: They found negative rules help. Isn't your RQ2 already answered? A: Not yet. In their data all the negative rules were also scope rules, and all the positive ones were style or process rules, so wording and content are mixed. I reword the same rule, so only the wording changes. And they measured pass rate, not whether the rule was followed. I honestly do not know which way it will go.

[7] McMillan: Instruction Adherence, a Factorial Study

  • Title: Instruction Adherence in Coding Agent Configuration Files: A Factorial Study of Four File-Structure Variables
  • Author: Damon McMillan (HxAI Australia)
  • Venue / status: preprint, no venue (18 pages)
  • arXiv: 2605.10039 (v1)

One breath: Across 1,650 Claude Code sessions, file size, rule position, splitting into several files and a conflicting rule did not detectably change how often the agent followed one simple annotation rule; the task and how far into the session mattered more.

What they did

  • Target rule: start every new or changed function body with the comment // @tracked. An AST script checked every function.
  • Four factors: file size (25, 100, 250, 500 lines; padding written to look like real files), position (line 2, 63, 128, 187, 250), architecture (CLAUDE.md; plus AGENTS.md; plus nested CLAUDE.md files), and a conflicting rule in AGENTS.md.
  • Two TypeScript codebases (a Next.js boilerplate and Umami), five tasks written by the author, 50 runs per condition.
  • Claude Code CLI pinned at 2.1.92 in --print mode. Mainly Sonnet 4.6, plus Opus 4.6 and Opus 4.7 (Opus 4.7 needed CLI 2.1.123).
  • Analysis: binomial mixed model (GLMM) with random intercepts for run and task, plus a Bayesian version.

Key results

  • No file: 0 of 524 functions had the marker. With the file (reference): 67.7%.
  • Size: 60.0%, 65.2%, 67.7%, 64.0% (p = 0.16). Bayes factor 0.096, which supports "no effect".
  • Position: 67.7%, 63.2%, 64.0%, 64.0%, 61.8% (p = 0.83). No U-shape.
  • Architecture: 67.7%, 68.2%, 61.7% (p = 0.19).
  • Conflict: 63.7% vs 64.1% (p = 0.76). Bayes factor 0.053.
  • Task mattered most: 45.1% (refactor an existing sidebar) to 84.4% (a button component).
  • Within a session, each extra function had about 5.6% lower odds of compliance (OR 0.944). Median first miss at the 4th function. Found during analysis, not planned.
  • Opus 4.6: 54.9%, which is 12.8 pp below Sonnet 4.6 at the same setting. On Umami: 56.7%, 11.0 pp below.
  • Follow-on: compliance vs share of tests passing, Spearman 0.104; not detectable after controlling for task.

Limitations

  • One trivial, synthetic rule. In their own words: "we did not vary instruction phrasing".
  • TypeScript only, Claude Code only, single-turn --print mode. Synthetic padding and tasks.
  • The position and architecture nulls have no Bayes-factor support. Effects smaller than about 6 pp cannot be ruled out.

How my study differs

  • Many real rules of different kinds vs one marker rule.
  • I change the rule itself (removed, reworded, neutral sentence), not the file around a fixed rule.
  • Real PR tasks in Python vs five written tasks in TypeScript. Two agents. Code quality.
  • What I borrow: compliance measured by script at every applicable place, a mixed-effects logistic model with the task as a random effect, and pinned tool versions.

Likely questions

  • Q: McMillan used 50 runs per condition. You use 3. Is that enough? A: He studied one rule, so he needed many runs of it. I study about 30 rules, and the mixed model pools over rules and tasks. Each run also gives several places to check. But I am not sure yet. The pilot will show the variance. If it is too high, I will use fewer rules and more runs.
  • Q: He found file structure does not matter. Why expect rule properties to matter? A: He changed the file around one fixed rule. I change the rule. His marker never appears without the file, so his baseline is zero. Real rules, like where tests go, are often followed anyway because the agent copies the existing code. So the effect of a real rule can be much smaller, and it may depend on the rule. He also says he did not vary the wording.

[8] Santos et al.: Configuration Smells in AGENTS.md Files

  • Title: Configuration Smells in AGENTS.md Files: Common Mistakes in Configuring Coding Agents
  • Authors: Hélio Victor F. dos Santos, Vitor Costa, João Eduardo Montandon, Luciana Lourdes Silva, Marco Tulio Valente (UFMG and IFMG, Brazil)
  • Venue / status: SCAM 2026 (26th IEEE International Conference on Source Code Analysis and Manipulation), from the arXiv journal reference. The PDF itself does not print the venue.
  • arXiv: 2606.15828 (v5, 30 Jul 2026)

One breath: A first catalog of six "smells" in agent configuration files, with detectors; in 100 popular repositories, 91 files had at least one smell, and the most common was repeating rules a linter already checks.

What they did

  • Grey literature review: a Google search in May 2026, top 30 results, 14 documents kept (6 by companies such as Anthropic and GitHub).
  • Six smells: Context Bloat, Skill Leakage, Lint Leakage, Blind Reference, Init Fossilization, Conflicting Instructions.
  • Checked PRs that changed the files (760 commits, 383 PRs, 17 relevant, 2 about config problems). No new smells found.
  • Dataset: the 100 most-starred application repositories with a root AGENTS.md (39) or CLAUDE.md (61), January 2026.
  • Detectors: Context Bloat = 200 lines or more. Init Fossilization = the file has only one commit. The other four = an LLM prompt (gemini-3.1-flash-lite, temperature 0). The first author checked every detected case.
  • Co-occurrence with the Apriori algorithm.

Key results

  • Lint Leakage: 62 detected, 4 false positives (precision 93%). The abstract says "62% of the files", but after checking, 58 were real.
  • Context Bloat: 42. Skill Leakage: 35 detected, 29 confirmed (the table says 82%). Init Fossilization: 24. Conflicting Instructions: 28 detected, only 16 confirmed (57%). Blind Reference: 16 detected, 14 confirmed (87%).
  • 91 of 100 files had at least one smell.
  • Conflicting Instructions plus Skill Leakage predict Context Bloat with confidence 0.83 (lift 1.81).

Limitations

  • Only precision was checked, by one author. Recall is unknown.
  • LLM-based detection; sources are grey literature.
  • No agent runs. The paper does not show that smells actually hurt agents.
  • Lint Leakage is judged from the file text, not checked against the repository's real linter settings.

How my study relates

  • [8] says linter-type rules waste context. My RQ2 asks the next question: are rules that the project's linter already enforces followed differently? I check the real linter configuration, not just the wording.
  • My Year 2 checker would reuse their detectors (their replication package is on Zenodo) and add warnings based on RQ2.

Likely questions

  • Q: Your checker reuses their detectors. How good are they? A: Precision was 93% for Lint Leakage but only 57% for Conflicting Instructions, checked by one author, and recall was not measured. So I would reuse them as a starting point and test them again on my own rules.
  • Q: If linter-type rules are a smell, why study them? A: Because developers clearly write them, in about 6 of 10 files. [8] gives advice but no measurement of agent behaviour. If agents follow linter-covered rules no better than other rules, that supports their advice with data.

[10] Harness-IF

  • Title: Harness-IF: Evaluating Instruction Following Across Instruction Surfaces in Coding Agents
  • Authors: Zining Huang, Haoran Que, Hong Zeng, Ge Zhang, Zuo Wang, Jin Chen, Haodong Wang, Zhongfei Hou, Changxin Pu, Shen Yan, Wenhao Huang (ByteDance Seed; Tsinghua University; Peking University)
  • Venue / status: preprint (paper dated 15 July 2026)
  • arXiv: 2608.11727 (v1, 12 Aug 2026)

One breath: A benchmark that gives one verdict per rule in multi-turn coding tasks, for rules placed in different parts of the agent's prompt, and shows every model is worse on rules that go against what it would do by default.

What they did

  • A 642-rule library, first seeded from public CLAUDE.md, AGENTS.md, CONTRIBUTING.md, skill and tool files, then atomized and rewritten by the authors, with LLM help to fill gaps.
  • 60 multi-turn coding items (kept from 80). Each item injects 25 to 35 rules, each placed on one of five "surfaces": system prompt, tool description, skill description, project file (like CLAUDE.md), user instruction.
  • 12 models x 60 items x 3 rounds = 2,160 runs, 40,104 verdict rows.
  • Scoring by regex, AST, cross-file and command checks, a hybrid, or an LLM judge (GPT-5.2, 3 votes).
  • "Against-prior" label: a probe run with the rule withheld on 9 model builds; if 5 of 9 agree, the rule is labelled as against or with the default (287 rules). Other labels are curated.
  • A separate conflict pilot (E0): 916 runs on 9 older builds.

Key results

  • Accuracy 72.1% to 85.9%. Against-prior accuracy (AP-Acc) 66.1% to 78.6%. Every model is worse on against-prior rules, by 3.6 to 7.4 points (mean 5.81).
  • On the fully script-checked subset, the gap is 13.09 points.
  • Project-file rules: 79.1% pooled accuracy (descriptive, placements were not balanced).
  • Failures: rules that require an action make 77.1% of failures, but the fail rates are similar (23.8% for require-type vs 20.8% for forbid-type rules).
  • Output-control rules are hardest (70.9%).
  • When two surfaces conflict: system prompt, project file and user instruction tie for first, then tool description, then skill description.
  • Reliability: 86.8% of verdicts involve the LLM judge. Swapping the judge gave only 62.1% agreement (kappa 0.163). An older human check gave kappa 0.515. Test-retest ICC 0.725; the mean spread of one item across 3 rounds was 15.6 points.

Limitations

  • Rules and items are written by the authors, not taken from real repositories.
  • The LLM judge dominates the measurement and is unstable when swapped.
  • Item selection used difficulty, so there is some selection optimism. The harness is not named. No code quality.
  • Some against-prior labels come from models that are also scored.

How my study differs

  • It is the closest benchmark. But they own the tasks and the rules. I use the developer's real file and a real task from the same repository.
  • They inject 25 to 35 rules at once. I keep the original file and change one rule.
  • Their "rule withheld" runs only label rules. In my design, "rule removed" is the main comparison.
  • Script checks only, real Claude Code and Codex, and code quality.
  • Lesson for me: their 15.6-point spread across 3 rounds shows run-to-run noise is large. And their against-prior idea matches my definition: a rule only counts as effective if behaviour changes when it is removed.

Likely questions

  • Q: Harness-IF already measures single-rule compliance with a withheld baseline. What is new? A: Yes, the idea is close, and I would cite it as the main benchmark. But their tasks and rules are written by the authors, and 86.8% of verdicts need an LLM judge. I keep the developer's own file and task, change one rule at a time, check with scripts, and also look at code quality.
  • Q: Why not use an LLM judge to cover more kinds of rules? A: In their own test, two judges agreed only 62.1% of the time. For a first study I prefer fewer rules with reliable scripts. Rules about design are a later step, and the proposal says this limit openly.

[11] Agent Skill Evolution (Wang et al.)

  • Title: Agent Skill Evolution: How Revisions Affect Coding Agents
  • Authors: Jiajie Wang, Yutong Zhao, Tianlin Li, Huashan Chen, Jinfu Chen, Kebin Peng, Sen He (University of Arizona and others)
  • Venue / status: preprint, no venue stated
  • arXiv: 2610.04832 (v1, 4 Oct 2026)

One breath: When maintainers add a checkable rule to a SKILL.md file, models follow it much more often and agents take the required action more often, mostly when the rule names a command or path the old file did not mention.

What they did

  • Rebuilt the history of 3,159 Skills in 856 repositories (from the SkillMD-138K snapshot) and compared first and last versions (2,608 pairs).
  • RQ1: how Skills change, and whether harness files like CLAUDE.md change in the same commits.
  • RQ2: took "directives" (imperative lines that name a command, path or identifier in backticks) that were added or deleted. An LLM (Qwen 3.5-27B) wrote a realistic request that needs the rule without mentioning it. A string check looks for the required token.
  • Conditions: no body, old version, new version. Controls: old plus only the new rule, new without the rule, old plus unrelated text of the same length, old plus a sentence that only names the token.
  • 396 added-rule probes (300 in the main set), 245 deleted-rule probes, 1,349 "dilution" probes.
  • 21 models: 16 open-weight (3.8B to 32B) and 5 closed (Claude Sonnet 3.5, 3.7, 4.5, Haiku 4.5, GPT-5.5). Five samples per condition (three for closed models), no thinking mode.
  • Sandbox: 80 tasks in 57 repositories, mini-SWE-agent scaffold (12 steps), with Qwen 3.5-9B, Qwen 3.5-27B, Devstral-Small and Claude Sonnet 4.5. Blind human judges for final correctness.

Key results

  • One answer: an added rule raises compliance by +0.41 (95% CI 0.35 to 0.46) across the 16 open-weight models. Closed models: +0.43.
  • Removing the rule from the new version: -0.21. Unrelated text of the same length: no detectable effect. Stating the rule beats only naming its token by +0.15.
  • Rules with a token new to the Skill: +0.51 to +0.66. Tokens already in the old version: only +0.08.
  • Deleting a rule lowers compliance by 0.27 to 0.33, about three quarters of what adding one gains.
  • Sandbox: required action +0.23 on average (+0.16 to +0.36). Sonnet 4.5: 0.62 to 0.81.
  • Final correctness (blind humans): +0.10 pooled over three agents. For Sonnet 4.5 alone, +0.06 (not significant, too few pairs).
  • Loading the Skill only on demand keeps about 51% of the action gain (open models about 38%).
  • Cost: a revision adds 18 to 19% input tokens to one answer, no detectable cost per agent episode. In 20% of rule and model pairs, tokens rose with no gain.
  • Only about 25% of later in-scope commits actually need the added rule.
  • Commits that revise a Skill also change CLAUDE.md (+2.1 points) and AGENTS.md (+2.0 points) more often than similar commits.

Limitations

  • SKILL.md files, not context files. Skills can load on demand.
  • The string check credits answers that merely repeat the token. It also misses compliance phrased differently (precision 0.97 to 0.98, recall 0.73 and 0.82 against two annotators).
  • The filter keeps 17% of candidate rules and under-represents prohibitions and conditional rules.
  • Requests are written by an LLM. Mostly small open models without reasoning. One research scaffold, not production agents (their own words).

How my study differs

  • Context files are always loaded and hold many rules at once. Skills load on demand.
  • Real merged PR tasks vs LLM-written requests. Claude Code and Codex vs mostly small models and mini-SWE-agent.
  • Code quality (complexity, warnings) vs correctness only. They exclude rewording; I test it.
  • Overlap I must admit: they already used "rule removed" and "same-length unrelated text" controls. My neutral sentence is the same idea.
  • Their "new token" result supports my specificity idea in RQ2: rules that name a concrete file or command may be followed more.

Likely questions

  • Q: They already showed that removing a rule lowers compliance. Isn't RQ1 answered? A: For Skills, mostly with small models answering once, yes. I expect the same direction. But a context file is always in the prompt with many other rules, and production agents read the code around them. Their own paper says production harnesses may behave differently. So the size of the effect for real context-file rules is still open, and RQ1 is the base for RQ2 and RQ3.
  • Q: Isn't your neutral-sentence control copied from them? A: It is the same idea, and I should cite them for it. It is a simple way to check that a longer file alone does not explain the effect. I apply it to context files with real tasks.

[12] Cai et al.: Rule Taxonomy and Evolution in AI IDEs

  • Title: Rule Taxonomy and Evolution in AI IDEs: A Mining and Survey Study
  • Authors: Guangzong Cai, Ruiyin Li, Peng Liang, Zengyang Li, Mojtaba Shahin (Wuhan University; Central China Normal University; RMIT University)
  • Venue / status: arXiv comment says "Manuscript submitted to a Journal (2026)". The PDF uses the ACM TOSEM template, but acceptance is not confirmed.
  • arXiv: 2606.12231 (v1, 10 Jun 2026)

One breath: They mined rule files from 83 projects built with AI IDEs, built a taxonomy, studied how rules change, surveyed 99 developers, and found that code followed a rule more often after the rule changed.

What they did

  • 25,587 search hits filtered to 83 projects whose README says they were built with an AI IDE (Cursor, Windsurf, Trae, Qoder, Kiro). 325 rule files, 7,310 rules.
  • Taxonomy: 5 primary categories (Architecture and Design; Code Implementation; Development Workflow and Project Management; Quality Assurance; AI Collaboration Specifications) and 25 secondary ones.
  • Evolution: 1,540 rule changes. Reasons coded on 504 changes that three LLMs agreed were clear.
  • Compliance: removed deleted rules and rules that a simple script could not check, ending with 160 rules. For each, Gemini 3 Flash Preview judged up to 5 commits before and 5 commits after the change.
  • Survey: 99 valid responses.

Key results

  • Mined reasons: Expansion 29.17% and Context Enrichment 26.59%. Correction only 6.35% (32 of 504).
  • Survey: 77.78% of developers said they change rules to correct AI errors.
  • Mining: corrections were mostly additions (68.75%, 22 of 32 cases, Table 7). The authors suggest these are often negative constraints ("do not" rules); that share was not measured.
  • Compliance rose from 49.14% before to 72.13% after (+22.99 percentage points), Wilcoxon p < 0.001, r = 0.71. It peaked at 76.03% at the change commit and stayed above 65% in the next five commits (post-change average 72.13%). The discussion notes it drifts down to about 65% at commits +4 and +5, still above the 39.13% to 50.45% before the change.
  • Big rises for Dependency Management (+64.82) and Testing Strategy (+52.73), small for Project Documentation (+6.25) and System Architecture (+3.33).
  • Survey: 79.80% saw quality improvement; 18.18% said rules were ineffective or harmful.

Limitations (they say most of these)

  • Not causal: the rise "could also stem from manual code adjustments made by developers within or around the same commit".
  • They cannot separate human code from AI code ("not feasible"). They rely on the README saying the project was built with AI.
  • Only statically checkable rules. Mostly TypeScript and web projects by small teams. LLM judge. No control group.

How my study differs

  • AI-IDE rule files vs CLAUDE.md and AGENTS.md.
  • Observed before and after, no control vs a controlled experiment where only the rule changes.
  • LLM judge vs scripts.
  • In my supporting study I separate agent PRs and use human PRs in the same repositories as a comparison.

Likely questions

  • Q: Cai found compliance went up 23% after a rule update. Isn't that your answer? A: It is 23 percentage points, judged by Gemini, with no control group and no way to tell agent code from human code. The biggest jump is at the very commit that changed the rule, where a developer may also have fixed the code by hand. The authors say it is not causal. My experiment changes only the rule and keeps everything else fixed.
  • Q: What does Cai mean for your real-PR study? A: Developers say they add rules to correct AI errors. So rules are often added right after bad behaviour, and compliance may rise anyway, like regression to the mean. That is why I compare with human PRs in the same repositories and report only associations.

Extra 1. Khatri: Do Context Files Help Coding Agents?

  • Title: Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories
  • Author: Prakhar Khatri (independent researcher)
  • Venue / status: preprint
  • arXiv: 2607.27250 (v1, 28 Jul 2026)

One breath: On 15 to 17 real merged-PR tasks from 3 Python repositories, giving Claude Code or Codex the AGENTS.md in different ways did not measurably change whether the hidden tests passed.

What they did

  • Repositories: pdm (AGENTS.md of 477 words), firebase-admin-python (1,236 words), opshin (248 words).
  • Tasks from merged PRs; the PR's own test files are hidden gold tests. 17 tasks for Codex, 15 for Claude Code.
  • Three strategies: NONE; ALWAYS ON (whole AGENTS.md in the system prompt every turn); SELECTIVE (wiki files the agent reads when needed). The real AGENTS.md was removed from the workspace in all three.
  • Claude Code (claude-sonnet-4-6) run with claude --print --bare and the file added through --append-system-prompt. Codex CLI (gpt-5.5) with the file added to the user prompt.
  • 3 repeats. 291 runs, 288 evaluated. Permutation tests, equivalence tests (TOST), Monte Carlo power analysis.

Key results

  • Pass rates (NONE / ALWAYS ON / SELECTIVE): Claude 53.3% / 55.6% / 55.6%; Codex 58.8% / 56.9% / 52.9%. Overall p = 1.000 and 0.66.
  • Differences bounded under 10 pp (Claude) and 15 pp (Codex), "not a powered equivalence claim".
  • Power: with 17 tasks and 3 repeats, a 30 pp effect is found only 57% of the time. Finding 10 pp with 80% power needs about 120 to 200 tasks. Going from 3 to 10 repeats raises power for a 15 pp effect only from 13% to 58%. "Task-level variance dominates: scaling requires more tasks, not more repeats."
  • On opshin, whose file warns the full test suite is slow, Claude ran the full suite less often with the file (3.67, 2.44, 1.67 runs per cell). Exploratory.
  • Task difficulty is agent-specific (Spearman 0.75). About 40% of shared tasks were borderline for only one agent.

Limitations

  • Small sample, 3 repositories, one model per agent.
  • The file reaches the two agents through different channels. ALWAYS ON is stronger than the normal workflow (the author says so). The SELECTIVE wiki is not matched in content.

How my study differs and what I learn

  • Same family of design: real merged PRs, the PR's tests, Claude Code and Codex, 3 repeats.
  • But they change how the whole file is delivered and measure only test success. I change one rule and measure compliance with it, plus quality.
  • They used --bare and the system prompt. I leave the real file in the workspace, as agents normally read it.
  • Big lesson: for test results (my RQ3), 3 runs on few tasks will be weak. More tasks help more than more repeats.

Likely question

  • Q: Khatri shows that even a 30-point effect is hard to detect with 17 tasks and 3 repeats. What about your design? A: For test results, I agree, and RQ3 may be underpowered. My main outcome is compliance, where effects are much bigger: McMillan saw 0% without the file and 67.7% with it, and Wang et al. saw +0.41. Each run also gives many places to check. For RQ3 I will report effect sizes with intervals, and if needed I will add tasks rather than repeats, as Khatri suggests. The pilot decides.

Extra 2. Lulla et al.: AGENTS.md and Agent Efficiency

  • Title: On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents
  • Authors: Jai Lal Lulla, Seyedmoein Mohsenimofidi, Matthias Galster, Jie M. Zhang, Sebastian Baltes, Christoph Treude (SMU, Heidelberg, Bamberg, King's College London)
  • Venue / status: ICSE JAWs 2026 (Journal Ahead Workshop), 5 pages
  • arXiv: 2601.20404 (v2, 30 Mar 2026)

One breath: With Codex on 124 real PRs, having the root AGENTS.md was associated with about 29% lower median run time and about 17% fewer median output tokens.

What they did

  • From 89 repositories with only a root AGENTS.md, an LLM filter kept 26 whose file has conventions, architecture or a project description. 10 were sampled.
  • Up to 15 merged PRs per repository, each at most 100 changed lines and 5 files, merged after the AGENTS.md appeared, code changes only. 124 PRs.
  • The task text was written by gpt-oss-120b from the PR diff and file tree.
  • With vs without AGENTS.md, Codex with gpt-5.2-codex, fresh Docker container.

Key results

  • Wall time: median 98.57 s to 70.34 s (-28.64%); mean 162.94 s to 129.91 s (-20.27%).
  • Output tokens: median 2,925 to 2,440 (-16.58%); mean 5,744.81 to 4,591.46 (-20.08%).
  • Both significant (Wilcoxon, p < 0.05). Input tokens did not change significantly.

Limitations

  • Codex and one model only. Small PRs.
  • Correctness was not evaluated, only a manual sanity check of 50 outputs. (The abstract's "comparable task completion behavior" rests on that check.)
  • Task text generated from the diff. Association, not cause.
  • They plan to study "how properties of these files, such as specificity, organization, and the inclusion of workflow guidance, relate to agent outcomes". That overlaps with my RQ2.

How my study differs

  • Whole file vs one rule. Efficiency vs compliance and quality. One agent vs two. I will still log tokens and time for every run.

Likely question

  • Q: Lulla's group plans to study specificity, like your RQ2. Aren't you competing with them? A: Maybe. It shows the question is open and people care about it. My angle is narrower: single real rules, checked by scripts, with code quality. If they publish first, I will build on their results and adjust.

Extra 3. Polandra et al.: Instruction Categories for Code Generation

  • Title: The Role of Agentic Instruction Categories for Code Generation: A Study of Five Python Libraries
  • Authors: Warren Gerald Polandra, Yoshiki Higo, Raula Gaikovina Kula (The University of Osaka, Japan)
  • Venue / status: arXiv comment says "Accepted to APSEC 2026 Technical Track" (not checked elsewhere)
  • arXiv: 2610.21421 (v1, 15 Oct 2026)

One breath: Agents wrote AGENTS.md files with every combination of five instruction categories and then rebuilt five tiny Python libraries from those files; more categories did not give better code.

What they did

  • Five categories: Repository Overview, Function Description, Implementation Detail, Testing, Reconstruction Steps. All 31 non-empty combinations.
  • 31 combinations x 5 libraries x 2 models (Gemma 4-26B-A4B run locally, GPT-5.4 by API) = 310 agent files, all generated by the LLM.
  • Agent harness: OpenCode (Plan and Build agents). Each library was rebuilt from scratch with only the agent file in the folder.
  • Measured tokens, compilation, the original human tests, and similarity to the original in lines, file count, total cyclomatic complexity (Radon) and function count. One run per condition, April 2026.

Key results

  • Compiled: Gemma 4 88.39%, GPT-5.4 98.06%.
  • Passed all tests: Gemma 4 0%, GPT-5.4 12.99%. Passed some tests: Gemma 4 17.42%, GPT-5.4 51.32%.

  • More instructions did not lower cost or raise correctness.

  • LLM-generated files, not developer-written. An unusual task (the authors admit rebuilding from scratch is not typical). Five trivial libraries, one run each, one harness.
  • They write that their structural metrics "should not be interpreted as direct evidence of maintainability".

How my study differs

  • Developer-written rules, normal PR tasks, single rules instead of whole categories, repeated runs, and quality measured on the code each task changes.
  • Side note: it is a Japanese group working on the same topic, so the topic is active in Japan too.

Likely question

  • Q: Polandra already measured cyclomatic complexity of code from different agent files. Isn't your RQ3 done? A: They compared whole LLM-written files on rebuilding tiny libraries, one run each, and they say their metrics are not evidence of maintainability. I keep the developer's file, change one rule, and measure the code for a normal task several times.

Extra 4. Xia and Miller: The Post-Merge Fate of Agentic Code

  • Title: Do These Violent Delights Have Violent Ends? Measuring the Post-Merge Fate of Agentic Code
  • Authors: Chunqiu Steven Xia (University of Illinois Urbana-Champaign), Courtney Miller (George Washington University)
  • Venue / status: preprint
  • arXiv: 2607.09902 (v1, 10 Jul 2026)

One breath: Following every line added by agents and humans in 182 repositories for a year, agent code was not changed more overall, but it got more bug fixes and brought more security warnings.

What they did

  • 182 projects from the "Agents in the Wild" dataset (not AIDev). Commits from 1 May 2025 to 31 May 2026.
  • Agent commits found by author name, email and signatures such as "Co-authored-by: Claude". 15 agents targeted.
  • Commit intent by rules, then an LLM (MiniMax-M2.7) for unclear cases (kappa 0.94 against one author on 100 commits).
  • Line-level survival (diff tracking plus git blame), Cox and Fine-Gray models, Semgrep and OSV-Scanner on every commit, SonarQube weekly, a panel model and a meta-regression.

Key results

  • Overall, agent lines were not changed more: HR 1.11 (0.85 to 1.45), p = 0.45. Raw survival: 75.8% agent vs 65.6% human.
  • Corrective maintenance: sHR 1.46 [1.02, 2.08] (Cox HR 1.49). Bug fixes: sHR 1.45 (Cox HR 1.51). By 180 days, 4.0% of agent lines vs 2.7% of human lines were changed by a bug-fix commit.
  • Nearly half of the changes to agent lines came from agent commits.
  • Semgrep findings 1.14 times the human rate (high severity 1.51 times). Dependency findings 1.10 times (high severity 1.15 times).
  • 10 pp more agent code last month: about 8.0% higher odds of corrective commits this month.
  • 10 pp more PRs merged without review: about 6% higher agent maintenance burden.

Limitations

  • Authorship by heuristics. Humans may use AI without it showing, which pushes differences toward zero.
  • Intent labels by rules and an LLM. Not every changed line is a defect. One year. Associations only.

How it relates to my study

  • It is not about rules. It is a methods model for the "later fix commits" measure in my supporting study (line tracking, intent labels, survival analysis, static tools).
  • It is also motivation: agent code needs more corrective work, so rules that make agent code better are worth studying.

Likely questions

  • Q: How will you measure later fix commits? A: Like Sawada et al. [3] and Xia and Miller: track the lines an agent PR added, find later commits that change them, and label those commits as fixes or not from the message, checking a sample by hand. I would report it as one sign of maintenance, not as proof of bad quality.
  • Q: Their human baseline may hide AI use. Same problem for you? A: Yes. Human PRs can contain AI help I cannot see. That makes differences look smaller, so I would state it clearly as a threat.

Questions that cut across papers

  • Q: Which paper is closest to yours, and what is different? A: Three are close. Harness-IF scores single rules, but with rules and tasks the authors wrote and mostly an LLM judge. Guardrails removes one rule at a time, but generic rules and pass rate only. Agent Skill Evolution removes real rules, but in SKILL.md with mostly small models. I combine real context-file rules, real tasks from the same repository, two production agents, script checks and code quality.
  • Q: What if you find nothing new, for example the same pattern as Guardrails? A: Then it is still useful: a check of earlier results on real context files with production agents, plus a public dataset of real checkable rules. A clear null result with a good design also helps developers decide which rules to keep.
  • Q: Many of these papers are 2026 preprints. How do you keep up? A: I search arXiv regularly for new work on context files and rules. My last full search was on 25 October 2026. Two of the papers here appeared in October 2026 alone. Say this date only after you have done the arXiv search on 25 Oct. Otherwise say the real date.

Numbers people often get wrong (do not misquote)

  • AIDev: 932,791 PRs is the version in the MSR 2026 paper. Name the version when you quote a size.
  • Gloaguen: developer files gave +2.4%, not significant (p = 0.21). Do not say "context files hurt" or "help". Cost rose by over 20% for LLM-made files.
  • Guardrails: the polarity split is p = 0.029 only with a 5 pp threshold; a threshold-free test gives about 0.13. Only one rule was individually significant.
  • McMillan: one synthetic rule. Position and architecture nulls lack Bayes-factor support. Phrasing was not varied.
  • Santos: "62% Lint Leakage" was detected; 58 were confirmed.
  • Harness-IF: rules and tasks are written by the authors, not taken from real repositories.
  • Agent Skill Evolution: +0.41 is over 16 open-weight models (21 models in total). SKILL.md, not CLAUDE.md or AGENTS.md.
  • Cai: +22.99 percentage points (49.14% to 72.13%), not a 23% relative rise. No control, LLM judge, not causal.
  • Lulla: correctness was not evaluated. Codex only.
  • Polandra: LLM-generated files, and the authors say their metrics are not maintainability.
  • Xia and Miller: overall HR 1.11 is not significant; 1.46 is for corrective maintenance. The data is "Agents in the Wild", not AIDev, and the paper never mentions context files.
