3. Papers in depth (most relevant first)

I = Iida author, K = Kashiwa author. PDFs read with pdftotext. I found no causal inference paper by either; their quality studies are observational and say so.

3.1 How Do Developers Maintain and Evolve Their Agents' Instructions? An Empirical Study. Voria, Cannavale, De Lucia, Kashiwa, Catolino, Palomba. ICSME 2026 Registered Report (Stage 1). arXiv 2606.25257 [P1]. K.

  • Problem: how context files change, and whether types of change relate to later agent code quality.
  • Planned method: AIDev (116,211 repositories, 932,791 pull requests) plus the 2,303-file Agent READMEs dataset. RQ1: a taxonomy mapped to "(corrective, preventive, adaptive, perfective, and additive)", coded by two people to "κ ≥ 0.70", then LLM-assisted labelling. RQ2: for each window of agent commits between two file changes, the change in cyclomatic complexity, lines of code and coupling, plus Corrective Commit Probability (CCP); Kruskal-Wallis, Holm-Bonferroni, Cliff's delta. RQ3: timing.
  • Results: none yet; Stage 2 goes to EMSE [19].
  • Stated limits: "ACFs contain heterogeneous instructions and modifications may affect only parts of the file, limiting causal interpretation", so "associations rather than causation".
  • For you: the closest work. You change one rule with the file fixed, which speaks to that threat. Their categories could be a rule property.

3.2 Agent READMEs: An Empirical Study of Context Files for Agentic Coding. Chatlatanagulchai, Li, Kashiwa, Reid, Thonglek, Leelaprute, Rungsawang, Manaskasemsak, Adams, Hassan, Iida. ACM TOSEM, DOI 10.1145/3840295; arXiv 2511.12884 v2 [P2]. I, K.

  • Method: 2,303 files from 1,925 AIDev repositories; 16 categories coded on 332 files; GPT-5 classifier (micro F1 0.79).
  • Results: Testing 75.9%, Implementation Details 70.8%, Architecture 68.1%; security and performance rare. 67.0% of Claude Code files change more than once, mostly by small additions. Indentation case: rsyslog violations fell from 60.82% to 11.03%.
  • Stated limits: "two cases cannot establish causality". They call for "agent context file smells (e.g., ambiguous directives, conflicting role definitions)" and "context debt".
  • For you: background for RQ2; your real pull request study extends the indentation check.

3.3 On the Use of Agentic Coding Manifests: An Empirical Study of Claude Code. Chatlatanagulchai, Thonglek, Reid, Kashiwa, Leelaprute, Rungsawang, Manaskasemsak, Iida. PROFES 2025 short paper, DOI 10.1007/978-3-032-12089-2_40; arXiv 2509.14744 [P3, 5]. I, K.

  • 253 CLAUDE.md files from 242 repositories; Build and Run 77.1%, Implementation Details 71.9%. No limitations section.
  • Future work proposes "controlled experiments where agents are tasked with identical coding challenges, but with varying qualities or completeness of agentic coding manifests", measuring "code quality (e.g., bug count, adherence to style guides)".
  • For you: your plan is a narrow, single-rule version. Do not raise it yourself (C48).

3.4 To What Extent Does Agent-generated Code Require Maintenance? An Empirical Study. Sawada, Shirai, Kashiwa, Yamaguchi, Iwata, Iida. EASE 2026 short paper; arXiv 2605.06464 [P4]. I, K.

  • Method: 508 agent-created and 508 human-created files in 100 repositories; 1,543 and 1,695 later commits. Agents found by bot committer names; Codex excluded "because it does not appear as a commit owner". Conventional Commits classifier (77.95% precision).
  • Results: "approximately half the commit count" of human files in month one. Agent files: feat 21.78%, refactor 14.19%, fix 11.73% (human files: fix 16.76%). "83.21% of commits (1,284) were made by human developers".
  • Stated limits: early-adopter period, undeclared AI code, only 508 files.
  • For you: your motivation, and the method for your later-fix-commit measure.

3.5 On the Use of Agentic Coding: An Empirical Study of Pull Requests on GitHub. M. Watanabe, Li, Kashiwa, Reid, Iida, Hassan. ACM TOSEM, DOI 10.1145/3798166; arXiv 2509.14745 [P5]. I, K.

  • 567 Claude Code pull requests matched with 567 human ones (157 repositories). Merged 83.8% vs 91.0%; 54.9% merged without revision. Revisions: bug fixes 47.7%, docs 29.0%, refactoring 27.1%, style 23.4%. They recommend a guideline file such as CLAUDE.md.
  • Stated limits: the "Generated with Claude Code" marker misses hybrid work; hidden AI in human pull requests "would likely dilute the differences".
  • For you: once conventions are written down, are they followed? That is RQ1.

3.6 Agentic Software Engineering: Foundational Pillars and a Research Roadmap. Hassan, Li, Lin, Adams, Chen, Kashiwa, Qiu. arXiv 2509.06216 v3, vision paper, venue [UNVERIFIED] [P6]; also an ICSE 2026 technical briefing [16]. K.

  • Proposes MentorScript, "machine-readable rulebooks that codify project norms", which "would be subject to their own quality gates, including linting, unit testing, and conflict detection". CLAUDE.md is "an early grassroots example".
  • Open problems: "Researchers should study how to verify that new rules improve agent behavior without causing unintended changes elsewhere." And "the community has no consensus on what such files should contain".
  • For you: RQ1 is the first half of that sentence, RQ3 the second, and your Year 2 checker is a small quality gate for rules. The clearest link to FOREST [INFERENCE].

3.7 AgentLogs: A Dataset for Opening the Black Box of GitHub's Cloud Agent. Richards, K. Horikawa, Fan, Kashiwa, Wessel. arXiv 2608.29204, venue [UNVERIFIED] [P7]. K.

  • 307,416 tasks, 549,239 sessions and 64,255,174 log entries of the Copilot cloud agent in 35,810 of 1,812,362 scanned repositories, collected through undocumented Copilot API endpoints (Hugging Face risenlab/agentlogs).
  • Open question 1b: "How do agents make use of repository provided context (e.g., custom instructions and skills), and is such context associated with different behavior and outcomes?"
  • For you: the traces could help study how agents use repository context (their question 1b) [INFERENCE]. Copilot only, not your agents.

3.8 Agentic Refactoring: An Empirical Study of AI Coding Agents. K. Horikawa, Li, Kashiwa, Adams, Iida, Hassan. arXiv 2511.04824; TOSEM 2026 per Kashiwa's researchmap, no DOI found [P8, 12]. I, K.

  • 15,451 refactorings in 14,998 Java commits from AIDev. Refactoring in 26.1% of agentic commits; low-level 35.8% vs 24.4% for humans; Class LOC median change -15.25, but smells "do not show FDR-significant reductions". Codex makes 89.3% of commits.
  • Stated limits: tool errors; LLM purpose labels (kappa 0.77); unclear human edits, so "human-AI collaborative refactoring".
  • For you: in the Java subset of AIDev studied here, Codex made 89.3% of commits; copy their careful authorship wording.

3.9 Do AI Agents Really Improve Code Readability? Kyogo Horikawa, Kosei Horikawa, Kashiwa, Uwano, Iida. MSR 2026 Mining Challenge, DOI 10.1145/3793302.3793590 [P9]. I, K.

  • 4,115 readability-related commits (about 0.3% of all agent commits); radon metrics on 403 of 577 Python commits. "The Maintainability Index decreased in 56.1% of commits, while Cyclomatic Complexity increased in 42.7%" (radon). Limits: tangled commits, Python only.
  • For you: use radon; report each metric on its own.

3.10 What to Cut? Predicting Unnecessary Methods in Agentic Code Generation. K. Watanabe, Shirai, Kashiwa, Iida. MSR 2026 Mining Challenge, Distinguished Paper, DOI 10.1145/3793302.3793591 [P10]. I, K.

  • Of 12,343 added methods, 2.6% (323) deleted; 9.9% in revised pull requests. Random forest AUC 87.1% but precision 0.049; GPT-4o AUC 0.621.
  • For you: your checker must report precision (E7).

3.11 Testing with AI Agents. Yoshimoto, Fujita, K. Horikawa, Feitosa, Kashiwa, Iida. MSR 2026 Mining Challenge, DOI 10.1145/3793302.3793620 [P11]. I, K.

  • AI wrote 16.4% of test-adding commits in the 10 projects with most AI tests; median assertions 2.00 vs 1.00; coverage measured in only 3 projects.
  • For you: running many repositories' tests is hard.

3.12 On the Use of ChatGPT for Code Review: Do Developers Like Reviews By ChatGPT? M. Watanabe, Kashiwa, Lin, Hirao, Yamaguchi, Iida. EASE 2024, DOI 10.1145/3661167.3661183 [P12]. I, K.

  • 229 review comments in 205 pull requests (179 projects), coded by hand; "only 30.7% of responses" to ChatGPT's answers were negative.
  • For you: an early lab LLM study built on careful manual coding.

3.13 Revisiting Code Ownership and its Relationship with Software Quality in the Scope of Modern Code Review. Thongtanunam, McIntosh, Hassan, Iida. ICSE 2016, DOI 10.1145/2884781.2884852 [P13]. I.

  • Six releases of Qt and OpenStack: "67%-86% of developers did not author any code changes for a module, but still actively contributed by reviewing 21%-39%"; the share of reviewers without expertise "shares a strong, increasing relationship with the likelihood of having post-release defects". Logistic regression with confounders controlled.
  • For you: Iida's template for "does a practice relate to quality?". Observational; your experiment adds control.

6. Questions they could ask you, with short model answers

6a. About your proposal

1. [Kashiwa] How is your study different from our registered report? (C46)

As I understand it, it is a Stage 1 plan that classifies changes to whole files and relates them to later quality, as associations. It says mixed instructions limit causal reading. I change one rule at a time on the same tasks and measure compliance with that rule. I see them as complementary.

2. [Kashiwa] AIDev has no context files. How do you get them? (C36)

Like Agent READMEs, I use AIDev as the list of repositories and get the files and their history from GitHub. I do not know yet if there is enough data for the real pull request part, so counting comes first.

3. [Kashiwa] How do you tell agent commits from human ones? (C35)

AIDev labels agent pull requests. For later fixes I would follow your EASE 2026 method, and I know its limit: Codex does not appear as a commit owner. So "human" means "not marked as agent", and hidden AI help would make differences smaller.

4. [Kashiwa] Why tests, complexity and warnings, and not defects or CCP? (C20)

They can be measured right after each run, on the same task for every version. Defects need time, so in the real pull request study I count later fix commits, as in your EASE paper; CCP could be a second measure there. All are proxies, and I will say so.

5. [Kashiwa] How many replayed pull requests will actually build? (C31)

I do not know; that is the main question for the pilot. Gloaguen et al. got 138 tasks from 5,694 pull requests, so I expect a big drop. If there are too few, I change the plan early.

6. [Kashiwa] Can a rule cause unintended changes elsewhere? (C21)

That is RQ3. I leave out checks that encode the rule itself. I would also mark rules that softly overlap a metric, like "keep functions small", and could report RQ3 with and without them.

7. [Iida] What will developers do differently after your study? (E14)

They will know which rules are worth keeping, which to reword, and which to move into a linter or a test. If many rules have no effect, they can shorten their files and save cost.

8. [Iida] Can you finish this in two years? (C32)

The core is RQ1 and RQ2 in Year 1. If time is short, I shrink the real pull request study first. The pilot tells me early if the plan is too big.

9. [Kashiwa] Would you pre-register it? (D16)

I think the main hypotheses could be fixed in advance, like your ICSME registered report. I would like your advice on whether that fits a master's timeline.

10. [Kashiwa] Rules are added right after violations. Isn't the real pull request study confounded? (C34)

Yes: regression to the mean, better models over time, linter changes. Human pull requests in the same months share the time trend, and I drop cases with linter changes. The causal claim comes from the experiment.

11. [Iida] Is this software engineering or prompt engineering? (E9)

Context files are project artifacts, maintained like configuration code, as Agent READMEs shows. I ask whether they change the code that ends up in the project, using repository data and quality measures.

6b. About their own work

12. [Kashiwa] What did you take from Agent READMEs? (C49)

The files grow mostly by small additions, and the indentation case showed fewer violations after the rule in two repositories. The paper says two cases cannot establish causality, so I want to test that kind of rule under control.

13. [Kashiwa] How will you use our EASE 2026 paper? (C50)

The 83.21% human share of later commits is my motivation, and my later-fix-commit measure follows your method. I also keep your warning that low maintenance frequency alone does not mean high quality.

14. [Kashiwa] How does your plan relate to the roadmap? (C53)

It asks researchers to verify that new rules improve agent behaviour without unintended changes elsewhere. RQ1 is the first part, RQ3 the second, and my checker is a small version of rule linting.

15. [Kashiwa] Could you use AgentLogs?

It covers the Copilot cloud agent, not Claude Code or Codex, so not for the main experiment. But its question 1b, how agents use custom instructions, is close to mine. I would also save full traces of my own runs.

16. [Iida or Kashiwa] Isn't this the future work of our Manifests paper? (C48)

I read that section, and I was glad to see it. I came to the question from my own work, where some rules had no effect. My plan is narrower: single real rules, one at a time, with compliance and quality measured by scripts.

17. [Kashiwa] What did you learn from What to Cut and the readability paper? (E7, C52)

From What to Cut, that a good AUC can come with low precision, so my checker must report precision. From the readability paper, that metrics can move against the goal, so I report each one on its own.

18. [Iida] Do you know our older process work?

Only a little. I read the KAKEN summary of the part of your 2010 to 2012 project on process observance and quality, and the main results of your ICSE 2016 paper relating review practice to defects. My RQ3 asks a related question for single rules given to agents.

Say this only after you have read the KAKEN summary and the ICSE 2016 paper.

19. [Kashiwa] Codex made 89.3% of commits in Agentic Refactoring. What does that mean for you?

In your Java subset, Codex made 89.3% of commits. If AIDev is similar, the compliance part of my real pull request study may hold mainly for Codex, while for later fix commits Codex may drop out because it does not appear as a commit owner. I would say so. The experiment runs both agents equally, so it does not depend on that mix.

20. [Iida] Our code review studies used mined data and regression. Why do you need an experiment?

In mined data, a rule is often added right after problems, so things may improve anyway. In my experiment only the file version changes on the same task. I keep a mining part, as your group does, to check real projects.

6c. About your work and projects

21. [Iida] Why leave a startup job for research? (A2)

At work I could check only one case, like my BrandMemory A/B test. I want to learn to answer the question properly, with a design others can trust. After about a year of building LLM systems at Layerpath, I keep meeting questions that engineering alone cannot answer, and these tools are new, so the questions are open now.

22. [Kashiwa] Is BrandMemory quality assurance for AI output? (B10)

In a small way. Some rules had no effect: some were cut off, others were overridden by a default style. After fixing both, one comparison showed contractions 6 to 0. It is one comparison, not a study.

23. [Kashiwa] How do you check Magic Editor's edits? (B11)

Every edit comes back as an action that must pass a schema check, and nothing is applied until the user approves it.

24. [Kashiwa] How did you evaluate Yuki? (B15, B21)

For Yuki for Mac, built on a fork of MacOS-Use, I wrote a small eval of first tool calls. My first run scored every model zero; the bug was in my own runner, and I recorded it. In Yuki 2.0 I replay past requests offline. Samples are small, often one run per task.

25. [Kashiwa] What did Yuki 2.0 teach you about rules?

The prompt grew rule by rule after incidents; one night the planner prompt grew 69%. The agent followed the rules but lost the goal behind the words. So I moved hard rules into code and limited the prompt size. That is close to asking which rules belong in a context file.
