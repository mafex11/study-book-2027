1.2 Research themes, in the lab's own words

The lab's Research page lists three areas [S7]:

  1. AI accelerating software development. It names GitHub Copilot and LLMs, and aims to automate developer work "beyond just programming".
  2. Software development automation achieving NoOps. Going past DevOps and CI to automate bug detection and fixing, and operational monitoring.
  3. Software analytics pursuing the ideal state of source code and projects. Mining Git, pull requests and bug trackers, and extracting data on feature work, refactoring and testing.

Two more things to know:

  • The lab is not only SE. The Recruitment page says its targets are "programs, networks, and development processes" [S5]. There is a network, cloud and HPC side (SDN, SRv6, GPU sharing, federated learning) linked to Kohei Ichikawa and Keichi Takahashi [S3, S4, S7]. Several current students work there, for example Pakorn Laohakanniyom on SRv6 and MPTCP [S3].
  • Kashiwa's project map on his profile groups the SE work into five lines [S10]:
    • Agentic Software Engineering: context files, pull requests, code quality, test generation.
    • AI-assisted development: JIT defect prediction, code completion, code review, bug triage.
    • DevOps and testing: build acceleration, continuous fuzzing, test maintenance, cloud and containers, dependencies and configuration.
    • Technical debt and refactoring: refactoring, SATD.
    • Bug analysis: visual issues, high impact bugs, issue linking.

The official NAIST page still lists older areas too: process modelling, project visualization, OSS social network analysis, code clones and design patterns, assurance, SDN and HPC [S8].

How your plan connects to his work

  • Voria et al. (his registered report). Their threats section says: "A key threat is linking code quality outcomes to ACF changes, as ACFs contain heterogeneous instructions and modifications may affect only parts of the file, limiting causal interpretation." They frame results "as associations rather than causation" (local PDF L9). Your design changes one real rule at a time while the rest of the file stays the same. That speaks to exactly this threat. Say "complements", never "fixes".
  • The roadmap he co-authored says about CLAUDE.md and AGENTS.md files: "the community has no consensus on what such files should contain or the appropriate level of detail, underscoring that future work involves ... discovering best practices for their effective use" (local PDF L11, section 8.1).     • the EASE 2026 paper found that on AI-generated files "83.21% of commits (1,284) were made by human developers". It excluded Codex PRs "because it does not appear as a commit owner" (local PDF L3).
    • Your later-fix-commit measure follows that EASE paper. Its agent identification limits apply to you too.
  • His industry and DevOps background (Hitachi; build acceleration; fuzzing build failures) [S10]. He will know how hard it is to rebuild old commits in containers. Be honest that this is your biggest practical risk, and that the pilot is there to measure it.

Likely questions from him

  1. "How is this different from the Voria et al. study?"
    • Hint: "Their study mines how files change over time and relates change types to later code quality, as associations. They say mixed instructions limit causal reading. I remove or reword one real rule at a time, with the rest of the file fixed, on real tasks. So I can say what one rule does. The two studies fit together."
  2. "AIDev has no context files. How do you get them?"
    • Hint: "Like Agent READMEs, I use AIDev as the list of repositories, then get the files and their history from GitHub."
  3. "How do you know a commit or PR is from an agent, and how do you find human PRs?"
    • Hint: "AIDev PRs are agent PRs. For humans and for later fixes I would start from the methods in your EASE 2026 paper, and I know its limit: Codex does not appear as a commit owner, and trailers can be turned off."
  4. "Why these quality measures and not defects?"
    • Hint: "Tests, complexity and static warnings can be measured right after each run. Defects need time. In the real PR study I use later fix commits, as in your EASE paper."
  5. "How many replayed PRs will actually build and run?"
    • Hint: "I do not know yet. That is the main question for the pilot on two repositories."
  6. "Would this fit the FOREST project?"
    • Hint: "I think it does, because it asks whether a rule changes agent code quality. But I would follow your view on how to fit it in."

Smart questions you can ask him

  1. "When Stage 2 of the Voria et al. study runs, would a per-rule experiment like mine be useful next to it, for example to check whether a change type really affects quality?"
  2. "AgentLogs has session logs with custom instructions. Do you think logs like these could tell me whether an agent actually read a rule before it broke it?"
  3. "For the FOREST project, are you planning shared infrastructure that students use together, for example containers for running agents on real repository tasks?"

How your plan connects to his work

  • Your file versions are a randomized treatment. Every task runs with every file version, and run order can be randomized. So for RQ1 (removed vs kept) and RQ3 (quality by file version) you compare like with like on the same task. This is the cleanest causal part of your design.
  • RQ2 has two kinds of evidence. Wording is manipulated (same rule, reworded by template), so it is close to causal. Specificity and linter coverage differ between rules, so they are only associations. Your proposal already says this. Ji will likely test whether you understand why.
  • His ISSTA 2025 paper is very close in spirit. It links prompt concepts to generated code across prompt adjustment strategies. Your rewording of one rule is a kind of prompt adjustment, inside a real agent and a real repository.
  • His CAM paper warns about one-at-a-time removal. Effects can be non-additive. Your design removes one rule at a time, so it cannot see interactions between rules. Be ready to say this is a limit, and how you might check a few pairs.
  • RQ3 design choice. You compare file versions, not "runs that happened to comply". That avoids comparing self-selected runs. He will likely like this. Be ready for a follow-up on mediation: "does quality change because the rule was followed?"

Likely questions from him

  1. "What is your treatment, your outcome, and what could confound it?"

  2. "Compliance is a fraction. Why logistic regression?"
    • Hint: "I would model the count of places that follow the rule out of the applicable places. That is still a logistic model, just for counts instead of one yes or no.     • Hint: "3 runs per version is a starting point. Task and rule are random effects, so the comparison pools many tasks. The pilot will show the run-to-run variance, and I will set the final numbers from it."
  4. "What about interactions between rules?"
    • Hint: "One-at-a-time removal cannot see them. I saw your CAM paper's point about non-additive effects. In the pilot I could test a few rule pairs to see if it matters."
  5. "Could you use the agent's trace to see whether it noticed the rule?"
