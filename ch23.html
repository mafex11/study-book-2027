Part 3: December to early February

Chapter 23 of 30

Optional: a tiny pilot you could run before the interview

When and how long: December to early February, optional: a small real experiment. Only if you can do it properly.

What this file is: a realistic, step by step plan for a very small version of your experiment: 1 repository, 2 rules, 3 tasks, Claude Code in headless mode. It includes the scripts, the time, the cost, how to show the result honestly on one slide, the risks, and when not to do it.

Read this first: it is optional. Your answers about the proposal, the weak points file and basic maths matter more. The lab interview is on Mon 26 Oct 2026, so do not run this before it. Run it before 10 Mar 2027 if at all. A pilot is a bonus, never a replacement.

1. Should you do it? Decide in one minute

Do it only if all of these are true:

  • The interview is at least about 7 to 10 days away, or the date is not set yet.
  • You can already explain the proposal, Fig. 1 and the top weak points without notes.
  • You have about 15 to 20 free hours outside work (one weekend plus two evenings).
  • You can pay about 50 to 100 USD yourself for this one-repository pilot (hard maximum 192 USD with the 3 USD cap per run). That fits inside the 265 to 375 USD you said you can pay for the two-repository pilot (answer sheet A6, CONFIRM C3).
  • You will use your own API key, your own time and a public open source repository. Never Layerpath's keys, code or work hours.

Do not do it if:

  • The interview is in the next few days. Say instead: "My next step is a pilot on two repositories, as in the proposal."
  • Setting up the repository's tests takes more than about 4 hours. Try one other repository. If that also fails, stop. The lesson ("setting up real tests is the hard part") is still worth one sentence in the interview.
  • You notice you are tempted to present it as evidence that rules work. It cannot show that.
  • Ever in the official entrance exam in March: no materials are allowed there.

You can also run it later, before the official exam on 10 March 2027, when it may be more useful.

2. What the pilot can and cannot show

It can show (about the method):

  • what one run really costs and how long it takes,
  • whether your rule checker counts correctly,
  • how much the 3 runs of the same setting differ,
  • how often a rule has no applicable place,
  • whether your isolation works (no hidden instructions leak in),
  • whether the agent follows a rule even with no file (the default).

It cannot show:

  • whether rules work in general (1 repo, 2 rules, 3 tasks, 1 agent is far too small),
  • anything about Codex, other languages or other rules,
  • anything statistically significant. Do not compute p-values.

3. The shape of the pilot

Item Pilot choice Why
Repository 1 public Python repo with an AGENTS.md or CLAUDE.md and unit tests that run without external services The proposal's own criteria, minimum size
Rules 2 script-checkable rules from that file One you expect agents to follow anyway, one you are less sure about

4. Step by step

Step 0. Prepare (about 1 hour)

  1. Docker. Docker was not found on this Mac when checked on 21 Oct 2026. Install Docker Desktop (or Colima). Give it enough memory, but on a 16 GB Mac run only one agent run at a time.
  2. API key. Create a personal Anthropic API key and set a monthly spend limit in the console. Keep the key only in an environment variable. Never write it into a file or a script.
  3. A working folder outside the interview folder, for example ~/code/personal/naist-pilot/, with this layout:
naist-pilot/
  Dockerfile
  config/model_id                  full model name, one line
  mirror/repo/                     a normal git clone of the chosen repository
  tasks/t1/base_commit             the commit just before the PR
  tasks/t1/prompt.md               the task text the agent sees
  tasks/t1/hidden_tests/...        the PR's own test files, at the same paths
  tasks/t1/hidden_test_paths       the paths of those test files, one line
  versions/t1/original.md          the context file at that commit
  versions/t1/A_removed.md
  versions/t1/B_removed.md
  scripts/check_rules.py
  scripts/run_one.sh
  scripts/run_all.sh
  scripts/summarize.py
  results/
  1. Write down your expectations before any run (one line per rule and version, for example "rule A: followed in almost all versions, even no file"). This is good research practice and makes your slide more honest.

Step 1. Pick the repository (1 to 3 hours)

Criteria:

  • Python, has a root AGENTS.md or CLAUDE.md that a developer edited (not only a generated one).
  • Unit tests run with one command and need no database, cloud account or secret.
  • Has merged pull requests from after the context file was added, and ideally after your model's training cutoff.
  • Not too huge (setup in minutes, not hours).
  • Check for nested context files too: git ls-files | grep -iE '(^|/)(AGENTS|CLAUDE)\.md$'.

One candidate checked on 21 Oct 2026: qodo-ai/pr-agent. Verify everything again yourself; files change.

  • It has a root AGENTS.md (first added Jan 2026, edited many times since, latest edits on 18 Oct 2026). It has no CLAUDE.md.
  • Its pyproject.toml requires Python 3.12 or later, configures Ruff with line-length = 120 and rule sets E, F, B, I, UP, and sets pytest testpaths = ["tests/unittest"].
  • Its AGENTS.md says unit tests run with PYTHONPATH=. uv run pytest tests/unittest, and that end-to-end tests need credentials (so use only unit tests).
  • It is one of the 12 repositories in Gloaguen et al.'s CTXbench [5] (Fig. 2 of their paper lists "pr-agent (10)"), so there is a precedent for building tasks from it.
  • Caution: it is a popular project, so older pull requests may be in training data. Prefer recent ones.

Other possible sources: the 12 repositories in Gloaguen et al. [5] (Fig. 2 of their paper: for example pdm, graphiti, fastmcp, smolagents, ragas), or the AIDev repository list. On 21 Oct 2026, graphiti's AGENTS.md said many of its tests need a Neo4j database, so it is a worse pilot choice.

Step 2. Pick two rules (1 hour)

Criteria: a script can check it; it applies in normal tasks; you can delete it cleanly.

Two candidates in pr-agent's AGENTS.md (as of 21 Oct 2026):

Rule A: test location Rule B: line length
Text in the file "keep new tests under the closest matching directory (tests/unittest/ for unit logic, ...)" "Keep Python lines within the 120-character limit declared in pyproject.toml."
Wording positive positive
Specific? yes, names a folder yes, names a number and a file
Linter enforces it? no (pytest only collects tests from tests/unittest) yes, Ruff rule E501 with line-length 120
Applicable place each new test function each added line of Python

Two lessons this already teaches (good to mention in the interview):

  • The same rule appears more than once in the file. tests/unittest is also in the test commands, and "120-character lines" also appears in the Dos and Don'ts. "Removing a rule" must mean removing every line that states it. Write down exactly which lines you removed. This is weak point 17 (rules interact) in real life.
  • The file also tells the agent to run ruff check --fix before committing. So even with rule B removed, the agent may fix long lines through the linter. That is exactly the "linter already enforces it" property of RQ2.

Step 3. Write the rule checker and check it by hand (2 to 3 hours)

This script was tested on 21 Oct 2026 on a small toy repository (it counted test functions and long lines correctly in new files, edited files and deleted files, and it counted tests in all three of rule A's folders as followed and a test outside them as not followed). It was not tested with a real agent run.

"""Score one finished agent run against two script-checkable rules.

Usage: python3 -I check_rules.py <repo_dir> <start_commit>
Prints one JSON line. For each rule: how many places the rule applied to
("applicable") and how many of those places followed it ("followed").
"""
import json
import re
import subprocess
import sys

# Rule A: new tests go under the matching test folder named in AGENTS.md
TEST_DIRS = ("tests/unittest/", "tests/e2e_tests/", "tests/health_test/")
MAX_LEN = 120                  # Rule B: Python lines stay within 120 characters
TEST_DEF = re.compile(r"^\s*(async\s+)?def\s+test_\w*\s*\(")


def git(repo, *args):
    return subprocess.run(["git", "-C", repo, *args], check=True,
                          capture_output=True, text=True).stdout


def main(repo, start):
    git(repo, "add", "-A")  # include files the agent created but did not commit
    diff = git(repo, "diff", "--cached", "-U0", start, "--", "*.py")

    a_app = a_ok = 0   # Rule A: each new test function is one place
    b_app = b_ok = 0   # Rule B: each added line of Python is one place
    path = None
    for line in diff.splitlines():
        if line.startswith("+++ "):
            path = line[6:] if line.startswith("+++ b/") else None
            continue
        if not line.startswith("+") or path is None:
            continue
        code = line[1:]
        b_app += 1
        b_ok += len(code) <= MAX_LEN
        if TEST_DEF.match(code):
            a_app += 1
            a_ok += path.startswith(TEST_DIRS)

    print(json.dumps({
        "rule_A_test_location": {"applicable": a_app, "followed": a_ok},
        "rule_B_line_length": {"applicable": b_app, "followed": b_ok},
    }))


if __name__ == "__main__":
    main(sys.argv[1], sys.argv[2])

Check it by hand on 20 examples before any agent run (this is the "at least 20 examples" step of the proposal):

  1. Take 20 recent merged pull requests of the repository.
  2. For each, run the checker on a copy of the repository: start = the commit before the PR, then check out the merged code.
  3. Open each diff and count by hand: new test functions, how many are under one of the three test folders the rule names (tests/unittest/, tests/e2e_tests/, tests/health_test/), added lines longer than 120 characters. Try to include at least one pull request that adds an end-to-end or health test, so you check that part of the checker too.
  4. Write down: "the checker matched my count on k of 20". If not 20 of 20, fix and recheck.

Known limits: rule A only sees functions named test_... (pytest's default). The real rule says "keep new tests under the closest matching directory" and names three folders (tests/unittest/ for unit logic, tests/e2e_tests/ for integration flows, tests/health_test/ for smoke coverage; AGENTS.md line 93, checked 21 Oct 2026). The checker accepts all three as followed, but it cannot tell whether a test sits in the closest matching one, for example a unit test placed in tests/e2e_tests/. A long line inside a multi-line string still counts as a long line. That is fine for a pilot, but write it down and note it on the slide.

Step 4. Pick three tasks (2 to 4 hours; often the slowest step)

  1. List recent merged pull requests that change both library code and unit tests. For example (not run here on 21 Oct because of a GitHub API rate limit, so test it yourself):
gh pr list -R qodo-ai/pr-agent --state merged --search "merged:>=2026-09-01" \
  --limit 100 --json number,title,mergedAt,files,mergeCommit

  Keep pull requests that change files under `pr_agent/` and add `def test_...` under `tests/unittest/`. Small ones are better (cheaper, faster).
  1. For each candidate, find the commit just before it: git rev-parse <merge_commit>^1. Save it in tasks/tN/base_commit.
  2. Copy the PR's test files from the merged code into tasks/tN/hidden_tests/ at the same paths (git show <merge_commit>:<path>), and list the paths in hidden_test_paths.
  3. Fail before, pass after: run those tests on the base code (they should fail) and on the merged code (they should pass). Keep only pull requests where this is true.
  4. Write prompt.md from the PR title and description. Remove anything that mentions where tests go or line length. Do not paste the solution. It is fine to say "Add unit tests for this change." Save the original PR text next to it so you can show what you changed.
  5. Take the context file as it was at the base commit: git show <base_commit>:AGENTS.md > versions/tN/original.md.

If you cannot find 3 fail-before, pass-after pull requests in about 3 hours, use pull requests that add tests even if the "fail before" check is messy, and say so on the slide. That is also a real finding: Gloaguen et al. [5] got only 138 tasks from 5,694 pull requests in 12 repositories.

Step 5. Make the file versions (30 minutes)

For each task folder:

  • original.md: unchanged.
  • A_removed.md: delete every line that states rule A. Keep everything else byte for byte.
  • B_removed.md: the same for rule B.
  • no_file: no file at all (handled by the script).
  • Optional A_reworded.md: flip rule A with your template, keeping all three folders, for example "do not put new tests outside the closest matching directory (tests/unittest/ for unit logic, ...)".
  • Optional A_neutral.md: replace rule A with a sentence of the same number of words that gives no instruction.

Use diff original.md A_removed.md to confirm only the intended lines changed. The script writes the text as CLAUDE.md and deletes any AGENTS.md, so Claude Code sees exactly one file.

Step 6. Build the container and prove the isolation (1 to 2 hours)

Dockerfile sketch (fill in the install line from the official Claude Code docs, and pin the version):

FROM python:3.12-slim
RUN apt-get update && apt-get install -y --no-install-recommends git curl ca-certificates \
    && rm -rf /var/lib/apt/lists/*
RUN pip install --no-cache-dir uv
RUN useradd -m runner
USER runner
ENV PATH="/home/runner/.local/bin:${PATH}"

# "Install a specific version"; it installs to ~/.local/bin/claude). 2.1.304 is the version whose
# flags were checked on 21 Oct 2026; change it if you pin another, and record `claude --version`.
ARG CLAUDE_VERSION=2.1.304
ENV DISABLE_AUTOUPDATER=1
RUN curl -fsSL https://claude.ai/install.sh | bash -s "${CLAUDE_VERSION}"

Two canary tests before the real runs:

  1. Is CLAUDE.md read in headless mode? Put this line in a test CLAUDE.md: "When you finish, end your final message with the word PINEAPPLE." Run a trivial task with exactly the flags of Step 7. PINEAPPLE must appear in the result. (Do not use --bare: the CLI help says it skips CLAUDE.md auto-discovery.)
  2. Is nothing else leaking in? Put the same PINEAPPLE line in /home/runner/.claude/CLAUDE.md inside the container, run with an empty CLAUDE_CONFIG_DIR (as the script does) and no project CLAUDE.md. PINEAPPLE must not appear. If it appears, the isolation does not work; fix it before going on.

Note: CLAUDE_CONFIG_DIR comes from the Claude Code environment-variable docs (as summarised in the verified fact sheet); the canary is how you confirm it on your version.

Step 7. The runner scripts

These were checked for syntax and run end to end on 21 Oct 2026 with a fake agent on a toy repository. The flags below were checked against claude --help for Claude Code 2.1.304 on 21 Oct 2026. Recheck them on the version you pin.

scripts/run_one.sh (one run, inside the container):

#!/usr/bin/env bash
# One agent run: ./run_one.sh TASK VERSION RUN   (example: ./run_one.sh t1 A_removed 2)
# Run this INSIDE the container. It never prints your API key.
set -euo pipefail
TASK="$1"; VERSION="$2"; RUN="$3"
ROOT=/pilot
MIRROR="$ROOT/mirror/repo"                      # one normal clone of the repo, made once
BASE="$(cat "$ROOT/tasks/$TASK/base_commit")"    # the commit just before the PR
MODEL_ID="$(cat "$ROOT/config/model_id")"        # full model name, not an alias like "sonnet"
OUT="$ROOT/results/$TASK/$VERSION/run$RUN"
mkdir -p "$OUT"

# 1. Fresh copy of the code at BASE: no git history, no remote, no old context file.
WORK="$(mktemp -d)"; CFG="$(mktemp -d)"
git -C "$MIRROR" archive "$BASE" | tar -x -C "$WORK"
rm -f "$WORK/AGENTS.md" "$WORK/CLAUDE.md"
if [ "$VERSION" != "no_file" ]; then
  cp "$ROOT/versions/$TASK/$VERSION.md" "$WORK/CLAUDE.md"
fi
cd "$WORK"
git init -q
printf '.venv/\n__pycache__/\n.pytest_cache/\n' >> .git/info/exclude   # never count these
(uv sync -q || true) > /dev/null 2>&1            # install deps so the agent can run tests
git add -A && git -c user.name=pilot -c user.email=pilot@example.com commit -qm base
START="$(git rev-parse HEAD)"

# 2. The agent run. Empty config folder = no user CLAUDE.md, no memory, no settings.
set +e
CLAUDE_CONFIG_DIR="$CFG" claude -p "$(cat "$ROOT/tasks/$TASK/prompt.md")" \
  --model "$MODEL_ID" --effort medium \
  --output-format json --no-session-persistence \
  --max-budget-usd 3 \
  --permission-mode bypassPermissions \
  --disallowedTools "WebFetch WebSearch" \
  > "$OUT/claude.json" 2> "$OUT/claude.stderr"
echo $? > "$OUT/exit_code"
set -e

# 3. Score the two rules, and keep the diff for hand checks.
python3 -I "$ROOT/scripts/check_rules.py" "$WORK" "$START" > "$OUT/rules.json"
git -C "$WORK" diff --cached "$START" > "$OUT/agent.diff"

# 4. Add the PR's own tests (the agent never saw them) and run them.
cp -R "$ROOT/tasks/$TASK/hidden_tests/." "$WORK/"
if (cd "$WORK" && PYTHONPATH=. timeout 900 uv run pytest -q $(cat "$ROOT/tasks/$TASK/hidden_test_paths")) \
     > "$OUT/tests.txt" 2>&1; then echo pass > "$OUT/tests_result"; else echo fail > "$OUT/tests_result"; fi

rm -rf "$WORK" "$CFG"

scripts/run_all.sh (all runs, random order, one at a time, skips finished runs so you can restart):

#!/usr/bin/env bash
# Every (task, version, run) once, in a random order, one at a time.
set -euo pipefail
mkdir -p /pilot/results
TASKS="t1 t2 t3"
VERSIONS="original A_removed B_removed no_file"   # add A_reworded A_neutral if you have budget
for t in $TASKS; do for v in $VERSIONS; do for r in 1 2 3; do echo "$t $v $r"; done; done; done \
  | shuf > /pilot/results/run_order.txt
while read -r t v r; do
  [ -f "/pilot/results/$t/$v/run$r/tests_result" ] && continue   # skip runs already done
  bash /pilot/scripts/run_one.sh "$t" "$v" "$r" < /dev/null || echo "FAILED $t $v $r" >> /pilot/results/failed.txt
done < /pilot/results/run_order.txt

Start it (the -e ANTHROPIC_API_KEY passes the key from your shell without writing it anywhere):

docker build -t naist-pilot ~/code/personal/naist-pilot
docker run --rm -e ANTHROPIC_API_KEY -v ~/code/personal/naist-pilot:/pilot \
  naist-pilot bash /pilot/scripts/run_all.sh

Important details and why:

  • --permission-mode bypassPermissions lets the agent edit and run commands without asking. Use it only inside the container, never on your Mac directly, and never mount your home folder.
  • --disallowedTools "WebFetch WebSearch": so the agent cannot look up the real pull request.
  • --max-budget-usd 3: a hard cost cap per run.
  • --model with the full model name and a fixed --effort: pinned versions, as in the proposal.
  • Random order (shuf): if the API changes during the day, all versions are affected equally.
  • First do 3 runs only (one per version on one task). Check cost, time and that the files look right. Then start the rest.

Step 8. Collect the numbers (1 to 2 hours)

scripts/summarize.py (tested on the toy data) prints a table with plain counts:

"""Collect all finished runs into one small table (plain counts, no statistics).

Usage: python3 -I summarize.py /pilot/results
"""
import json
import sys
from collections import defaultdict
from pathlib import Path

root = Path(sys.argv[1])
rows = defaultdict(lambda: defaultdict(float))
for run in sorted(root.glob("*/*/run*")):
    version = run.parent.name
    r = rows[version]
    r["runs"] += 1
    rules = json.loads((run / "rules.json").read_text())
    for key, short in (("rule_A_test_location", "A"), ("rule_B_line_length", "B")):
        app, ok = rules[key]["applicable"], rules[key]["followed"]
        r[short + "_app"] += app
        r[short + "_ok"] += ok
        r[short + "_none"] += app == 0          # runs with no applicable place
    r["tests_pass"] += (run / "tests_result").read_text().strip() == "pass"
    try:
        r["cost"] += json.loads((run / "claude.json").read_text()).get("total_cost_usd", 0)
    except (ValueError, FileNotFoundError):
        r["errors"] += 1

print("| version | runs | rule A followed | A: runs with no place | rule B followed "
      "| hidden tests passed | total cost USD |")
print("|---|---|---|---|---|---|---|")
for v, r in sorted(rows.items()):
    print(f"| {v} | {int(r['runs'])} | {int(r['A_ok'])}/{int(r['A_app'])} | {int(r['A_none'])} "
          f"| {int(r['B_ok'])}/{int(r['B_app'])} | {int(r['tests_pass'])}/{int(r['runs'])} "
          f"| {r['cost']:.2f} |")

The JSON from --output-format json includes the run's cost (total_cost_usd; confirm the field name in your version). Also:

  • Hand-check 5 agent diffs against the checker's counts.
  • Note the spread between the 3 runs of the same task and version (for example "rule A: 2/2, 0/1, 3/3").
  • Note how many runs had no applicable place for rule A.
  • Note the wall-clock minutes per run.

Optional add-on: Codex (only if everything above worked)

Codex reads AGENTS.md, so write the same text as AGENTS.md instead of CLAUDE.md. The rough command (flags checked against codex exec --help, codex-cli 0.161.0, 21 Oct 2026):

CODEX_HOME="$(mktemp -d)" codex exec --json --ephemeral --sandbox workspace-write \
  -m "$MODEL_ID" -C "$WORK" "$(cat prompt.md)" > codex.jsonl

A fresh CODEX_HOME avoids your global AGENTS.md, but you must log in or provide the key for that folder. As far as I know, codex exec reuses saved CLI authentication by default, and you can set CODEX_API_KEY inline for a single run (verify in the Codex docs before you run the pilot). If that is right, pass your key that way, only on the Codex command. Codex's JSON events give token counts; compute cost from the price list. Gloaguen [5] reported 0.32 to 0.57 USD per task with GPT-5.2, so 36 Codex runs would be roughly 12 to 21 USD on their numbers.

Rules for the slide:

  • Show counts as "k of n", never only percentages (2 of 3 is not "67%").
  • No p-values, no stars, no bold claims.
  • Put "Does NOT show" on the slide itself.
  • Put the main lesson about the method first, not about the rules.

Do not say this on 26 Oct. The pilot has not been run. Fill [total], [min] and the lesson only after real runs (answer sheet 6.9).

The 30 second spoken version:

"To check feasibility, I ran a very small pilot: one repository, two rules, three real pull requests, 36 runs with Claude Code in a container. The main thing I learned was [your main lesson from the runs, for example: the same rule appears twice in the file, so removing a rule needs care]. Do not say:

  • "The pilot shows rules work" or "do not work".
  • "Compliance dropped by X%" as if it were a finding.
  • That the pilot used two repositories (the proposal's pilot) if it used one.
