Part 1: Before Monday (23 to 26 Oct)

Chapter 5 of 30

Your proposal, explained simply

When and how long: Friday evening, about 45 minutes.

What this file is: every paragraph and sentence of the proposal you sent to Prof. Iida, in plain words. For each part you get: what it means, why it is there (why you made that design choice), and what to say if someone asks "why?".

How to use it:

  1. Read it once from top to bottom.
  2. The day before the interview, reread only: Section 0 (30 second version), Section 4 (Fig. 1), Section 5 (worked example) and Section 6 (the "why" table).
  3. The model answers are in your voice. Change the words until they sound like you. Do not memorise them word for word.

Sources: the proposal text (.context/proposal_text.md), and the papers in ../04_Papers/. Every claim about a paper below was checked in the paper itself on 21 Oct 2026. The personal answers come from your answer sheet (/Users/mafex/code/personal/masters-research/naist/answer_sheet.md).

0. The whole proposal in 30 seconds

Say this out loud until it feels natural:

"Developers write rules for coding agents in files like CLAUDE.md and AGENTS.md. I want to know which of these rules agents actually follow, what makes a rule work, and whether a rule changes the quality of the code. I take one real rule at a time from a real file. I remove it, or reword it, and run Claude Code and Codex on real tasks from the same repository. Small scripts check whether the rule was followed and how the code changed. A second, smaller study looks at real pull requests to see if the results hold in real projects."

If they want only one sentence:

"I test single real rules from CLAUDE.md and AGENTS.md files, by removing or rewording them one at a time, and I measure with scripts whether agents follow them and whether the code changes."

Paragraph 2: BrandMemory, Burnt, and why you care about this question

"The work at Layerpath closest to research is BrandMemory, a pipeline that extracts a company's writing rules from its website and gives them to a model as context."

  • Plain words: BrandMemory reads a company's website, finds its writing rules (for example "no contractions"), and puts those rules into the model's prompt.
  • Why it is there: this is the same situation as a context file. Rules written in plain language, given to a model, and you hope the model follows them.

"When I measured the output, some rules had no effect. Some never reached the model, because they sat at the end of a long prompt that was cut off. Others were overridden by a default house style elsewhere in the prompt."

  • Plain words: two failures. (1) The prompt was too long and the end was dropped, so the model never saw some rules. (2) Another instruction in the prompt (a general "house style") said something different, and the model followed that one instead.
  • Why it is there: it shows you found, in practice, that rules can silently fail.
  • Link to research (nice point to make): your two failures match two variables researchers study. Failure 1 is about position and length of instructions. Failure 2 is about conflicting instructions. McMillan [7] tested size, position and conflicts for one simple rule. Configuration Smells [8] lists "Conflicting Instructions" as a smell.
  • If asked "How did you measure that?": "Projects with brand memory on logged that the guidance was applied, but the output had no trace of the brand voice, and on and off pairs looked almost the same. So I traced what the model actually received. The brand voice section had the lowest priority in the prompt, so it was the first thing cut at a 3,200-character limit. After the fix, the live test was one A/B pair, one output on each side."

"I fixed both problems and then ran a small A/B test on one product demo, with and without the rules. Contractions fell from 6 to 0, and 'you' and 'your' fell from 15 to 1. That matches two of the rules: avoid contractions, and write in the third person."

  • Plain words: after the fix, you generated text for one demo twice: once with the rules, once without. With the rules, there were no contractions (like "don't") and almost no "you/your".
  • If asked "What did you fix exactly?": "I removed the per-feature 3,200-character limits and raised the overall limit from 6,000 to 30,000 characters. I turned off the default house style when a brand voice is active. I used the brand's verified examples as clean examples, and I moved the brand rules before the output requirements in the video prompt."
  • If asked "Is that significant?": "No. It is one comparison on one demo. I did not run statistics. It only showed me that the rules can work once they reach the model."

"One comparison is not a study, but it taught me to measure whether a model follows an instruction instead of assuming it."

  • Why it is there: honesty. You say the limit yourself before they do.

"I also built Burnt, a Mac app that reads the local logs of coding agents to track their cost."

  • Plain words: Burnt reads the log files that coding agents write on your laptop, and shows what each session cost and how much the prompt cache was used. It reads the logs of Claude Code and Codex, and uses the open source ccusage tool for the costs.
  • Why it is there: it shows you already understand agent logs and agent cost. Both matter for running about 1,800 agent runs and keeping the budget.
  • In the interview, lead with Yuki instead (see question bank B15).

"I use Claude Code and Codex every day and maintain the context files that guide them, so I want to ask the same question about coding agents."

  • Why it is there: your practical reason for this topic.
  • If asked "How much of your code do agents write?": answer honestly in your own words. A safe line: "I use Claude Code and Codex every day, and I review the changes they make." (Say "every change" only if it is literally true.) Your pre-application text says "I build most of my software with coding agents". If they quote it, say: "I would rather not give a number I have not measured. What matters is that I review and own the changes." Never say "most".

2. Part 2 of the proposal: "The research project I want to work on at NAIST"

The title question

"Which rules in a context file do coding agents follow, and does a rule change the quality of their code?"

  • Plain words: two questions. Do agents obey the rules? And when a rule is there, is the code better or worse?
  • Why phrased like this: it names both outcomes you measure: compliance (following the rule) and code quality.

Background paragraph

"Coding agents such as Claude Code and Codex now open many pull requests on GitHub."

  • Plain words: agents do not only suggest code. They now open real pull requests in real projects.

"The version of the AIDev dataset described in [4] already holds 932,791 pull requests created by five agents."

  • Plain words: AIDev is a public dataset of pull requests made by agents. The paper version (MSR 2026) has 932,791 pull requests by five agents: OpenAI Codex, Devin, GitHub Copilot, Cursor and Claude Code, in 116,211 repositories, collected up to 1 Aug 2025 (checked in [4]).
  • Why "the version described in [4]": AIDev has newer, larger releases. You cite the number from the paper so it is exact.
  • If asked "Isn't AIDev bigger now?": "Yes, there are newer releases. I quoted the number in the MSR paper so it matches the reference."

"To steer these agents, developers add a context file such as CLAUDE.md or AGENTS.md with project rules."

  • Plain words: a context file is a text file in the repository that the agent reads at the start. Claude Code reads CLAUDE.md. Codex reads AGENTS.md.

"Studies of real files show that most include build and test commands, implementation details and architecture notes [1, 2]."

  • Plain words: the lab's two papers looked at what is inside these files.
  • Numbers (checked): In [1] (253 CLAUDE.md files): Build and Run 77.1%, Implementation Details 71.9%, Architecture 64.8%. In [2] (2,303 files): Testing 75.9%, Implementation Details 70.8%, Architecture 68.1%, Build and Run 63.0%.
  • Careful: in [2], Testing is the top category, not Build and Run. The 77.1% is from [1].

"Like configuration code, the files grow through frequent small additions, and rules about security or performance are rare [2]."

  • Plain words: people keep adding small bits to these files, like they do with config files. Few files mention security (14.8%) or performance (14.5%) (from [2]).

"Human developers do most of the later maintenance of code written by agents [3], so whether agents follow these rules matters to the people who maintain that code."

  • Plain words: in [3], humans made 83.21% of later commits to files that agents created. So if an agent ignores the project's rules, a human pays for it later.
  • Why it is there: it gives the "who cares" reason, and links to the lab's own EASE 2026 paper.

Challenges paragraph (what others found, and why it is not enough)

"Results so far are mixed. Context files do not generally raise task success, and they add over 20% to inference cost on average [5]."

  • Plain words: Gloaguen et al. [5] ran agents with and without context files. Files did not reliably help agents finish tasks, but made them about 20% more expensive. Developer-written files gave +2.4% on average, not significant (p = 0.21).

"The same study reports from agent traces that agents follow the instructions, but it does not test single rules."

  • Plain words: [5] looked at what agents did (traces). For example, the tool uv was used 1.6 times per task when the file mentioned it, and almost never when it did not. But they never removed one rule to see the effect of that rule. Their category ablation (removing whole sections) was done only on files generated by an LLM, not developer files.
  • Why it is there: it is the strongest "but we already know this" attack, so you name it first. See 03_weak_points_and_honest_answers.md.

"In another study, random rules raised the pass rate as much as rules chosen by experts [6]."

  • Plain words: in "Guardrails Beat Guidance" [6], random community rules and expert rules both gave 63.8% pass rate, versus 50.0% with no rules. So maybe just having some rules helps, whatever they say.
  • Why it matters for your design: this is why you have the neutral sentence version. It separates "the content of this rule" from "just having some text there".

"Its ablation of 18 rules found that the rules whose removal lowered the pass rate were negative constraints such as 'do not refactor unrelated code', though it measured only task success [6]."

  • Plain words: they removed each of 18 rules one by one. 3 rules mattered (removing them hurt). All 3 were "do not" rules. But they measured only whether tests passed, not whether the agent obeyed the rule.
  • Why it matters: it motivates RQ2 (wording: negative vs positive). Also, the authors themselves say their only significant single rule would not survive a correction for many tests. So it is a hint, not proof.

"File size, instruction position and file structure had no detectable effect on how often agents followed one simple annotation rule [7]."

  • Plain words: McMillan [7] used one made-up rule (add the comment // @tracked) and changed file size, where the rule sits, how many files, and conflicts. None of these changed compliance in a detectable way. He did not change the wording of the rule.
  • Why it matters: structure seems not to matter much, so you study the rule itself (its content and wording) instead of headers or layout.

"Many files contain style rules of the kind that linters already check [8]."

  • Plain words: the Configuration Smells paper [8] calls this "Lint Leakage" and found it in 62% of 100 files.
  • Why it matters: this gives the third property in RQ2: is the rule already enforced by the project's linter?

"One benchmark checks single rules against runs where the rule is withheld, but its coding tasks were written for the benchmark [10]."

  • Plain words: Harness-IF [10] does check single rules, and compares with runs where the rule was left out. But its tasks were written by the authors, not taken from real repositories. Also 86.8% of its verdicts use an LLM judge.
  • Why it matters: your difference is real files, real tasks from the same repo, and script checks.

"Adding a checkable rule to an agent Skill file made agents take the required action more often, mainly for rules that name a command or path [11]."

  • Plain words: Agent Skill Evolution [11] studied SKILL.md files (not CLAUDE.md or AGENTS.md). Adding a rule raised the required action by +0.23 on average across four agents. The gain came mainly from rules naming a concrete command or path. It used one research scaffold (mini-SWE-agent), not production agents.
  • Why it matters: this motivates the specificity property in RQ2.

"In AI IDE projects, code followed a rule more often after the rule was updated, as judged by a language model, but that study did not separate code written by agents from code written by people [12]."

  • Plain words: Cai et al. [12] looked at Cursor-style rule files. After a rule update, compliance went from 49.14% to 72.13% (judged by Gemini 3 Flash Preview). But they could not tell if the code was written by an agent or a person, and they say they do not claim causality.
  • Why it matters: your real pull request study separates agent pull requests from human ones.

"A registered report by a team including Assoc. Prof. Kashiwa plans to relate changes in context files to code quality [9]."

  • Plain words: Voria et al. [9] (with Kashiwa) is a plan accepted at ICSME 2026 (Stage 1, no results yet). They will classify changes to context files (corrective, adaptive, and so on) and relate them to later code quality (complexity, size, coupling, corrective commits). They say results are associations, not causation.
  • Why it is there: it is the lab's closest work. You must show you know it, and that your study is different (single rules, controlled experiment) and complementary.

"As far as I know, no study has yet removed or reworded one real rule at a time in CLAUDE.md and AGENTS.md files written by developers, run agents on real tasks from the same repositories, and measured with scripts both whether agents follow that rule and how the code changes."

  • Plain words: your gap has four parts, and it is the combination that is new:
    1. one real rule at a time (removed or reworded),
    2. in files written by developers,
    3. real tasks from the same repositories,
    4. scripts measure both compliance and code change.
  • Why "As far as I know": the field moves fast. You hedge on purpose.
  • If asked "So what is new?": "Each part exists somewhere. Guardrails removed single rules but measured only pass rate. Harness-IF scored single rules but on tasks written for the benchmark. No study I found puts all four together."

"I call a rule effective if agents follow it more often when it is in the file than when it is removed."

  • Plain words: your definition. Effective = the rule makes a difference. If agents do the thing anyway (rule or no rule), the rule is followed but not effective.
  • Why this definition: Harness-IF [10] starts with exactly this problem: "When a coding agent obeys a rule, it may simply have been going to do that anyway."
  • If asked "Why not just measure compliance?": "High compliance can mean the agent does it by default. I want to know what the rule adds, so I compare with the rule removed."

The research questions

"RQ1. Does removing one real rule change how often agents follow it in their code?"

  • Plain words: take the rule out. Do agents follow it less?
  • Why removal, not adding: the rules already exist in real files. Removing one is a clean "leave one out" test while everything else stays the same.

"RQ2. Which properties of a rule predict how effective it is: its wording (negative or positive), its specificity (whether it names a concrete file, folder, function, command or tool), and whether the project's linter already enforces it?"

  • Plain words: which kinds of rules work best?
  • Why these three properties: each comes from earlier work.
    • Wording: Guardrails [6] found "do not" rules helped pass rate.
    • Specificity: Agent Skill Evolution [11] found rules naming a command or path worked best.
    • Linter: Configuration Smells [8] found style rules a linter already checks in 62% of files.
  • Important: you can test wording directly (you reword the same rule). Specificity and linter coverage differ between rules, so those are associations.

"RQ3. Does keeping a rule in the file, instead of removing it, change the quality of the code, measured by test results, complexity and static analysis warnings that the rule itself does not check?"

  • Plain words: with the rule, is the code better or worse in other ways?
  • Why "that the rule itself does not check": if the rule is "lines under 100 characters", you must not count the line length warning as "quality", or you would be measuring the rule twice. This avoids a circular result.

Approach: rules and tasks

"I will start with about 10 Python repositories from AIDev that have a context file and tests that run in a container."

  • Plain words: pick around 10 real Python projects where agents work, that have a CLAUDE.md or AGENTS.md, and whose tests can run in Docker.
  • Why AIDev: these are projects where agents really open pull requests. The lab's Agent READMEs paper [2] also took its repositories from AIDev.
  • Why Python: good tools (pytest, radon, ruff), and Gloaguen's benchmark [5] is also Python, so I can compare costs.
  • Why tests in a container: you need to run tests automatically and the same way every time.
  • Why about 10: enough variety, small enough for a master's student to set up.

"From their files I will collect about 30 rules that a small script can check in the code, such as 'put new tests in the tests folder'."

  • Plain words: pick rules you can check with code, not by reading.
  • Why scripts and not an LLM judge: scripts give the same answer every time. Harness-IF [10] used an LLM judge for 86.8% of verdicts, and its authors say verdicts were "far less stable" when they swapped the judge (62.1% agreement).
  • Why about 30: enough rules to compare properties in RQ2, within budget.

"I will check each script by hand on at least 20 examples to measure its accuracy."

  • Plain words: before trusting a checker, you test it. You look at 20 or more real cases yourself and see if the script was right.
  • If asked "Why 20?": "It is a minimum, not a magic number. If I find errors, I fix the script and check more examples."

"Only rules a script can check are included, so the results speak for this kind of rule, not for rules about design or process."

  • Plain words: you say the limit yourself: no results for rules like "keep the design simple".
  • Why: honesty about generalization.

"For tasks, I will replay merged pull requests whose own tests fail before the change and pass after it, with the context file as it was at that commit."

  • Plain words: take a real pull request that was merged. Its tests fail on the old code and pass on the new code. Give the agent the old code and the task, then run those tests on what the agent wrote. Use the context file exactly as it was at that time.
  • Why: real tasks (not written for a benchmark), and an automatic correctness check. This is how SWE-bench works.

"The agent starts from the code just before the pull request. It gets no git history, and the task description does not mention the rule."

  • Why no git history: so the agent cannot look up the real solution. Gloaguen [5] also removed the git history and remotes.
  • Why the task does not mention the rule: otherwise you measure whether it follows the task prompt, not the context file.

"I will prefer pull requests merged after the models' training cutoff."

  • Why: if the model saw the merged code during training, it might copy it from memory. That is contamination.

"Each rule is paired with tasks where it actually applies."

  • Plain words: for "put new tests in the tests folder", the task must involve writing tests. Otherwise there is nothing to check.

3. Versions, runs, measures and analysis

Versions and runs

"Each task runs with five versions of the context file (Fig. 1): the original file, the file with one rule removed, the file with that rule reworded by a fixed template, the file with the rule replaced by a sentence of the same length that gives no instruction, and no file at all as a baseline."

The five versions and what each one is for:

Version What it is What comparing it tells you
V1 original the real file normal behaviour
V2 removed the same file minus this one rule V1 vs V2 = the effect of the rule (RQ1)
V3 reworded the rule flipped by a fixed template (positive to negative, or the reverse) V1 vs V3 = does wording matter (RQ2)
V4 neutral the rule replaced by a sentence of the same length with no instruction V1 vs V4 = effect of the rule's content with length held fixed; V4 vs V2 = effect of just having extra text
V5 no file nothing at all what the agent does by default

"For example, 'put new tests in the tests folder' becomes 'do not put new tests outside the tests folder', and a second person checks that the meaning stays the same."

  • Why a fixed template: you do not want to "improve" the rule while rewording it. Only the polarity changes.
  • Why a second person: you might be biased. Another person checks the meaning is the same.

"Claude Code reads the text as CLAUDE.md, and Codex reads the same text as AGENTS.md."

  • Plain words: same words, different file name, because each agent looks for its own file name.

"I run both from a script with fixed versions, in a clean container, 3 times for each file version."

  • Fixed versions: the agent software version and the model version are pinned. McMillan [7] pinned Claude Code at 2.1.92.
  • Clean container: a fresh Docker container each run, so no memory or user settings leak in.
  • 3 times: agents are random. Claude Code does not expose a sampling seed (McMillan [7] says this), so the same input can give different code.

"About 30 rules with 2 tasks each, 5 file versions, 2 agents and 3 runs give at most 1,800 runs. The number is lower when one task tests several rules."

  • The arithmetic: 30 x 2 x 5 x 2 x 3 = 1,800.
  • Why lower when tasks are shared: V1 (original) and V5 (no file) do not depend on which rule you study. If one task is used for 3 rules, you run V1 and V5 once, and only V2, V3, V4 per rule.

"Using the costs per task reported in [5], 1.15 to 1.51 US dollars with Claude Code and 0.32 to 0.57 with Codex, the runs would cost about 1,300 to 1,900 US dollars."

  • The arithmetic: 900 Claude runs x 1.15 = 1,035 and x 1.51 = 1,359. 900 Codex runs x 0.32 = 288 and x 0.57 = 513. Total about 1,323 to 1,872.
  • Where the numbers come from: Table 2 of Gloaguen [5]: Claude Code with Sonnet-4.5 cost 1.15 to 1.51 USD per task, Codex with GPT-5.2 cost 0.32 to 0.57.
  • Honest caveat: those were their tasks and their models in early 2026. Real cost depends on my tasks and today's models. That is why the pilot comes first.

"A pilot on two repositories will set the final numbers and the budget."

  • Plain words: first a small test run to measure real cost, time and variance, then decide the final size.

Measures and analysis

"Compliance is the fraction of applicable places in the new code that follow the rule."

  • Plain words: count every place where the rule could apply, then count how many follow it. Example: rule "use the logger, not print". The agent writes 4 output statements, 3 use the logger. Compliance = 3/4.

"For compliance and test results I will use mixed effects logistic regression. The file version and the agent are fixed effects, and the task and the rule are random effects, because some tasks and rules are easier than others."

  • Plain words:
    • Logistic regression: each applicable place is followed or not, so you model followed places out of applicable places in each run with a binomial, logistic, mixed model. Hidden tests pass or fail per run, which is the same kind of model.
    • Fixed effects: the things you change on purpose and want to measure: file version, agent.
    • Random effects: things you sampled, which have their own baseline level: each task and each rule. Some rules are followed 90% of the time anyway, some 20%. The model allows for that.
  • In one line of code (R, lme4 style): followed ~ version + agent + (1 | task) + (1 | rule).
  • Precedent: McMillan [7] used the same kind of model (binomial mixed model with random intercepts for run and task).
  • If asked "Why not a simple t-test?": "The runs are not independent. Runs on the same task or rule are alike. A mixed model handles that."

"For RQ3 I compare file versions on the same task, rather than runs that happened to follow the rule, and I leave out any check that encodes the rule itself so the result is not circular."

  • Why compare versions, not "runs that complied": runs that complied may be different in other ways (for example easier). Comparing the versions I assigned keeps it a fair experiment.
  • Why leave out the rule's own check: see RQ3 above.

"I test wording directly, because I reword the same rule. Specificity and linter coverage can only be compared between different rules, so I will report those results as associations."

  • Plain words: wording is a real experiment (same rule, two wordings). Specificity and linter coverage are not: a specific rule and a vague rule differ in many ways. So you only say "associated with", not "causes".
  • How RQ2 enters the model: "effective" means the original vs removed difference, so a property must interact with the file version (for example version * linter_covered). The interaction asks: does removing a linter-covered rule change compliance less than removing other rules? See Step 7 in section 5.

"I will also report runs with no applicable place separately."

  • Plain words: if the agent writes no tests, the test location rule cannot be checked. You do not count that run as "followed" or "not followed". You report how often it happens.

Real pull requests

"In [2], the authors report a before and after check of one indentation rule in two repositories."

  • Plain words: in Agent READMEs [2], one Claude Code repository went from 60.82% to 11.03% violating lines after a 4-space indentation rule was added, and one Copilot repository from 20.17% to 7.57%. The authors say "two cases cannot establish causality".

"To see whether my results hold in real projects, I will first count how many repositories have enough agent pull requests before and after a checkable rule was added."

  • Why count first: you do not know yet if there is enough data. Counting first is honest.

"For rule types that recur across repositories, such as test location or logging, my rule checkers will compare how often agent pull requests follow the rule before and after it was added."

  • Plain words: reuse your checkers on real history.

"Human pull requests in the same repositories will serve as a comparison, and I will leave out cases where linter settings changed at the same time."

  • Why humans: if human pull requests also improve after the rule date, something else changed in the project (not the rule). If only agent pull requests improve, the rule is a more likely reason.
  • Why leave out linter changes: a new linter setting could fix the code by itself.

"For merged agent code I will also count later fix commits, as in [3], and treat them as one sign of later maintenance."

  • Plain words: after merge, how often do people come back to fix the agent's code? Sawada et al. [3] classified later commits with the Conventional Commits Classification System (fix, feat, refactor, and so on).

"Developers often change rules to correct AI errors [12], and agents improve over time, so I will report these results as associations."

  • Plain words: in Cai's survey, 77.78% of developers said they change rules mainly to correct AI errors. So rules are added right after things go wrong, and things often get better anyway afterwards. Also models get better over time. So this part can only show association.

Expected results

"The first is a public dataset of real, checkable rules and how often two widely used agents follow them." "The second is evidence on which kinds of rules are effective, for example whether negative rules, which helped task success in [6], are also followed more often." "The third is a small checker, built in Year 2, that flags rules agents tend to ignore, rules that conflict and rules a linter already covers. It will reuse the smell detectors of [8] where possible and add warnings based on the rule properties found in RQ2. I will evaluate it with a few developers by asking whether each warning is correct and useful." "I aim to publish at MSR, ICSME or EASE and release all scripts and data."

  • Plain words: a dataset, findings about rule types, and a small tool.
  • Why a tool: it turns the findings into something developers can use. The lab says it cares about solving real problems in actual development.
  • Why "a few developers": a small, honest first evaluation. Not a big user study.
  • Why these venues: the lab publishes there. [3] is EASE 2026, [9] is ICSME 2026, and the lab had MSR 2026 Mining Challenge papers.

5. One concrete example, end to end

Everything in this section is an imaginary example to show how the method works. The repository, the pull request and all numbers are made up. They are not results.

Step 1: the repository and its rule

An imaginary Python repository tinyshop has this CLAUDE.md:

# CLAUDE.md
## Commands
- Run tests with `pytest -q`.
## Code style
- Use type hints on public functions.
- Put new tests in the tests folder.          <- the rule we study (call it R)
- Use the logger from tinyshop/log.py, never print().
## Architecture
- Payment code lives in tinyshop/payments/.

Rule R is script-checkable: a script can see the path of every new test. Its properties for RQ2: wording = positive ("put"), specificity = names a folder (specific), linter = no linter checks test location.

Step 2: the task

A real merged pull request, imaginary number #231: "Add discount codes. apply_discount(cart, code) returns the new total. Unknown codes raise ValueError. With tests."

  • The pull request added tinyshop/discounts.py and tests/test_discounts.py.
  • On the code just before #231, tests/test_discounts.py fails (the function does not exist). On the merged code, it passes. So this pull request qualifies.
  • The agent gets: the code just before #231 (no git history), and a task description written from the pull request text, which does not mention where tests go.
  • The agent does not get: tests/test_discounts.py. Those are the hidden tests, used only to check the result.

Step 3: the five file versions

Version The line where rule R was
V1 original - Put new tests in the tests folder.
V2 removed (line deleted)
V3 reworded - Do not put new tests outside the tests folder.
V4 neutral - This project began as a weekend project. (7 words, same as R, no instruction)
V5 no file no CLAUDE.md at all

Everything else in the file stays exactly the same in V1 to V4.

Step 4: the runs

5 versions x 2 agents (Claude Code reads it as CLAUDE.md, Codex as AGENTS.md) x 3 runs = 30 runs for this one rule and this one task. Each run: a fresh container, pinned agent and model versions, the same task text, run from a script.

Step 5: what gets measured in one run

Imaginary run: Codex, V2 (rule removed), run 2. The agent wrote tinyshop/discounts.py and put its test in tinyshop/test_discounts.py, next to the code.

Measure How Imaginary value
Applicable places for R new test functions the agent wrote 2 test functions
Followed R test functions inside tests/ 0 of 2
Compliance followed / applicable 0/2 = 0.0
Hidden tests copy in tests/test_discounts.py, run pytest pass
Complexity radon cyclomatic complexity of added functions apply_discount has one if and one for, so 3
Static analysis warnings ruff warnings in changed files, minus any check that encodes R (none here) 1 (an unused import)
Cost and tokens from the agent's JSON output logged, not an RQ

If the agent had written no tests at all, R would have no applicable place in that run. That run is reported separately, not counted as followed or not followed.

Step 6: how to read the 30 runs for this rule and task

Four possible patterns (no real data, just how you would interpret them):

Pattern What you see What it means
A V1 and V3 high, V2, V4 and V5 low The rule works, wording does not matter much
B All five versions high Agents do this anyway (the existing tests already show the convention). The rule is followed but not effective. A candidate for "probably redundant" in the Year 2 checker.
C V1 high, V3 clearly lower Wording matters for this rule (RQ2)
D V1 and V4 both high, V2 low The extra text, not the instruction, explains the effect. This is why V4 exists.

Step 7: from one rule to the whole study

  • Do the same for about 30 rules, each with 2 tasks.
  • Put all runs into one table: one row per run, with task, rule, version, agent, applicable places, followed places, hidden tests pass/fail, complexity, warnings.
  • Fit the mixed model: followed ~ version + agent + (1 | task) + (1 | rule). The V1 vs V2 difference answers RQ1. Rule properties (specificity, linter) are rule-level variables, reported as associations. For RQ2 the property must interact with the file version, for example followed ~ version * linter_covered + agent + (1 | task) + (1 | rule). The interaction tells me whether removing linter-covered rules changes compliance less. A property on its own (a main effect) only tells me whether such rules are followed more overall, across all versions. Wording is a separate contrast, V1 vs V3, on the same rule.
  • For RQ3, compare V1 and V2 (and V5) on the same tasks for test pass rate, complexity and warnings, leaving out any check that encodes the rule.

6. The "why" table: every design choice in one place

Design choice Why What to say if asked "why?"
Single real rules, not whole files Whole-file comparisons exist [5]; they do not tell you which rule matters "Whole files have been tested. I want to know which rule does the work."
Developer-written files Real rules; Gloaguen's category ablation used only LLM-generated files "I want rules people really write."
Remove one rule (leave one out) Rest of the file stays fixed, so the difference is that rule "It is the cleanest way to see what one rule adds."
Reword by fixed template Tests wording without changing meaning "Only the polarity changes, so I test wording directly."
Neutral sentence of same length Random rules helped as much as expert ones [6]; separates content from length "It tells me if it is the rule's content or just extra text."
No-file baseline Shows the agent's default; links to [5] "It shows what the agent does by itself."
Two agents (Claude Code, Codex) Two widely used agents from different companies, both have a headless mode, both used in [5] "One agent could be a special case."
Same text as CLAUDE.md and AGENTS.md Each agent reads its own file name "Same words, different file name."
Pinned versions, clean container Reproducibility; no leftover memory or user settings "So every run starts the same and others can repeat it."
3 runs per version Agents are random; budget limit; pilot will decide "Three is a starting point within the budget. The pilot will tell me how many runs I need."
Script checks, not LLM judge Same answer every time; LLM judge unstable in [10] "A script gives the same answer every time, and I can measure its accuracy."
Hand check of 20+ examples per checker Measure checker accuracy "I need to know my measuring tool works."
Replayed merged PRs, fail-before / pass-after Real tasks plus automatic correctness "Real work from the same project, and I can check correctness automatically."
Context file as at that commit Realism "The rules the developer had at that time."
No git history Agent cannot find the real solution "So it cannot copy the answer."
Task text does not mention the rule Otherwise you test the prompt, not the file "I test the file, not the prompt."
PRs after training cutoff Contamination "So the model has not seen the answer in training."
Mixed effects logistic regression Each place followed or not, tests pass or fail per run; runs grouped by task and rule "Runs on the same task and rule are not independent."
Compare versions for RQ3, not complying runs Avoid selection bias "I compare what I assigned, not what happened."
Leave out the rule's own check in RQ3 Avoid circularity "Otherwise I would count the rule twice."
Associations for specificity, linter, real PRs Not randomly assigned "I assign the file version, including the wording. The rule properties are not assigned, so those are associations."
Pilot first Real cost, time and variance unknown "I want the numbers before I spend the budget."
Python, about 10 repos, about 30 rules Tools, precedent [5], feasible for a master's "Big enough to compare rule types, small enough to finish."
