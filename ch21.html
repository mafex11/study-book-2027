1. Mining software repositories (MSR)

What it is.

  • Studying software development by collecting and analysing data that projects already produce: git history, pull requests, code review comments, issues, CI logs, and so on.
  • MSR is also the name of the main conference (my target venue list: MSR, ICSME, EASE).
  • It is observational: the researcher does not change anything, so results are associations unless the design adds a comparison or a natural experiment.

A typical MSR pipeline.

  1. Select repositories: from a dataset (AIDev) or a search, with filters (stars, language, activity).
  2. Collect: GitHub REST or GraphQL API, git clone, tools such as PyDriller (used in Agent READMEs to extract commit data).
  3. Clean and filter: remove forks, toy projects, bots you do not want, duplicates.
  4. Label: manual coding of a sample with two raters and an agreement measure (kappa), sometimes an LLM classifier checked against humans.
  5. Measure: metrics such as cyclomatic complexity, lines of code, smells, merge rate, time to merge.
  6. Analyse: non-parametric tests, effect sizes, regression.
  7. Threats to validity and a replication package (code and data).

Common traps.

  • Most GitHub repositories are personal or inactive (the classic warning is "The Promises and Perils of Mining GitHub", Kalliamvakou et al., MSR 2014).
  • Tangled commits: one commit mixes several unrelated changes. The lab's readability paper lists this as a construct validity threat.
  • Squash merges rewrite commits, so commit SHAs in the PR may not exist on the main branch. Match on PRs instead.
  • Who is the author? Agent identification depends on signals that can be missing or changed:
    • the lab's PR paper only kept PRs marked "Generated with Claude Code" and calls such markers "brittle text markers";
    • Sawada et al. [3] match committer names with known agent bot accounts, and excluded Codex because "it does not appear as a commit owner";
    • Agent READMEs identifies Codex commits "based on pull request metadata and branch naming conventions";
    • Claude Code's commit attribution can be changed or turned off in its settings (attribution in the settings reference).
  • Fix commits as a quality signal: a later commit whose type is "fix" is one sign of maintenance. Sawada et al. [3] classify commit types with the Conventional Commits Classification System. The SZZ algorithm (Śliwerski, Zimmermann and Zeller, MSR 2005) goes one step further and traces a fix back to the commit that introduced the bug.

Link to the lab. The lab's research area "Software analytics" mines Git, pull requests and bug trackers. Assoc. Prof. Kashiwa's interests include mining software repositories, CI and DevOps data, and just in time defect prediction. The lab had three MSR 2026 Mining Challenge papers using AIDev (What to Cut won a Distinguished Mining Challenge Paper Award).

In my plan. The supporting study (real PRs before and after a rule is added) is an MSR study. The controlled experiment also uses MSR steps to pick repositories and tasks.

"Mining software repositories means studying how software is built by analysing the data projects already leave behind, like commits, pull requests and reviews. I want to learn the lab's methods for this, because my supporting study is exactly that kind of study, and the hard parts I already see are agent identification and confounding."

2. The GitHub pull request workflow

What it is.

  1. A developer (or an agent) creates a branch and makes commits.
  2. They open a PR from the head branch into the base branch, with a title and description.
  3. CI runs automatically (for example GitHub Actions): tests, linters, builds.
  4. Code review: reviewers leave comments and choose Comment, Approve or Request changes.
  5. The author pushes more commits to address the review.
  6. The PR is merged (merge commit, squash and merge, or rebase and merge) or closed without merging.
  • Extras: linked issues, labels, CODEOWNERS (who must review which files), branch protection (required checks before merge).

How agents fit in.

  • The AIDev paper's Figure 1 shows GitHub Copilot being assigned an issue, opening a PR, getting a review comment and replying with a follow up commit.
  • Claude Code PRs often contain "Generated with Claude Code" in the description and Co-Authored-By: Claude in commits (both used in the lab's PR paper).

Key facts from the lab's PR paper (Watanabe et al., TOSEM, arXiv 2509.14745):

  • 567 Claude Code PRs matched with 567 human PRs across 157 repositories.
  • 83.8% of agent PRs merged vs 91.0% of human PRs (chi-squared, p < 0.05).
  • 54.9% of merged agent PRs went in without changes. Revisions were for fixes (47.7%), docs (29.0%), refactoring (27.1%) and style (23.4%).
  • Section 5.3: "The high rates of style (23.4%) and refactoring (27.1%) revisions indicate that generic models do not fully capture local conventions." This is the gap that context file rules try to fill.

In my plan.

  • Tasks come from merged PRs whose own tests fail before the change and pass after it. The agent starts from the base commit, gets a task description that does not mention the rule, and gets no git history.
  • Practical details: run the tests several times to catch flaky tests; with squash merges, use the PR's base commit and the PR's test files.

Say it.

"A pull request is a proposed change that goes through CI checks and human review before it is merged, and coding agents now open many of them. In my plan I replay merged PRs: the agent starts from the code just before the PR, and the PR's own tests, which fail before and pass after, tell me if the task was solved."

3. AIDev

What it is. A public dataset of PRs opened by AI coding agents on GitHub, built at Queen's University (Hao Li, Haoxiang Zhang, Ahmed E. Hassan). MSR 2026 paper, "AIDev: Studying AI Coding Agents on GitHub", arXiv 2602.09185. Hao Li and Hassan also co-author the lab's Agent READMEs and PR papers.

Key facts (MSR 2026 paper version).

  • 932,791 agent PRs by five agents: OpenAI Codex, Devin, GitHub Copilot, Cursor and Claude Code.
  • 116,211 repositories, 72,189 developers. Cutoff: 1 August 2025.
  • Curated subset: 33,596 PRs from 2,807 repositories with more than 100 stars, with review comments, commit level diffs, timelines and linked issues.
  • Tables in the subset include pr_comments, pr_reviews, pr_review_comments, pr_commits (88,576 rows), pr_commit_details (711,923 file level diffs), pr_timeline, and pr_task_type (PR purpose, GPT based, using Conventional Commits categories).
  • Available on Hugging Face (hao-li/AIDev) and Zenodo.

4. SWE-bench and pass@k

What SWE-bench is.

  • Jimenez et al., "SWE-bench: Can Language Models Resolve Real-World GitHub Issues?", ICLR 2024 (arXiv 2310.06770).
  • 2,294 tasks from real GitHub issues and their PRs in 12 popular Python repositories. In the original paper the best model (Claude 2) resolved only 1.96%.
  • One task = an issue text + the repository at the commit before the fix. The model writes a patch. The harness runs tests in a container: the tests the real PR made pass (FAIL_TO_PASS) must now pass, and tests that passed before (PASS_TO_PASS) must still pass.
  • SWE-bench Lite: 300 tasks from 11 repositories (as described in Gloaguen et al. [5]).
  • SWE-bench Verified: a human validated subset of 500 tasks released by OpenAI with the SWE-bench authors. The agentic SE roadmap paper (Hassan, Kashiwa and others, arXiv 2509.06216) says GPT-4o solved 33% at launch in August 2024, leading agents passed 70% by mid 2025, and OpenAI later warned about data contamination and recommended SWE-Bench Pro.

How hard is it to build such tasks? Gloaguen et al. built CTXbench from repositories that have developer written context files: 138 instances from 5,694 PRs in 12 repositories. Most PRs had no usable tests, so they generated tests with an LLM and checked that they fail before and pass after the original change. They removed git history and remotes from the container. [my arithmetic: 138 / 5,694 is about 2.4% yield.] My plan uses PRs that have their own tests, so my yield may be even lower. The pilot will show this.

pass@k.

  • From Chen et al., "Evaluating Large Language Models Trained on Code" (arXiv 2107.03374, the HumanEval paper). Their abstract shows why it matters: one sample solves 28.8% of problems, but 100 samples per problem solve 70.2%.
  • pass@k = the chance that at least one of k attempts passes. Unbiased estimate from n attempts with c correct: pass@k = 1 - C(n - c, k) / C(n, k), averaged over tasks.
  • pass^k (from τ-bench, Yao et al., arXiv 2406.12045) = the chance that all k attempts pass: C(c, k) / C(n, k). It measures reliability.

Tiny example. [my arithmetic] 3 runs, 1 correct (n = 3, c = 1):

  • pass@1 = 1 - C(2,1)/C(3,1) = 1 - 2/3 = 0.33 (same as the success rate)
  • pass@2 = 1 - C(2,2)/C(3,2) = 1 - 1/3 = 0.67
  • pass@3 = 1 (C(2,3) = 0)
  • pass^3 = C(1,3)/C(3,3) = 0. The agent is not reliable on this task.

In my plan.

  • My tasks are SWE-bench style, but the rule is the focus, not just "solved or not".
  • With 3 runs per condition I can report the success rate (pass@1) and also "all 3 runs follow the rule" (a pass^3 style reliability number). For a project rule, reliability is what a developer cares about.
  • Contamination: I prefer PRs merged after the models' training cutoff. Gloaguen et al. split instances by cutoff and found "no significant or consistent difference".

Say it.

"SWE-bench turns real GitHub issues into tasks: the agent gets the code before the fix, and the real PR's tests decide if the task is solved, and my tasks are built the same way. pass@k is the chance that at least one of k attempts succeeds, but for following a project rule I care more about reliability, so I would also report whether all three runs follow the rule."

5. How coding agents work

5.1 The loop

  • A coding agent = a language model + a harness. Santos et al. [8] describe it like this: "a coding agent can be viewed as a combination of a language model and a harness", and the harness "implements an agentic loop that repeatedly interacts with the model, executes actions, and feeds the results back to the model".
  • One turn of the loop:
    1. The model reads everything in its context and decides on an action.
    2. It emits a tool call: a structured request such as "read file X", "edit lines in Y", "run pytest".
    3. The harness runs the tool (with permission rules) and puts the result back into the context.
    4. Repeat until the model decides the task is done.
  • My own experience: in Yuki, my desktop AI agent, a local 7B model picked the right tool much more often when I gave it only the relevant tools. Magic Editor returns every edit as a schema validated action that is applied only after the user approves it.

5.2 The context window

  • The context window is everything the model can see at once, measured in tokens: the system prompt, the context file, the conversation, and every tool result.
  • It is limited. Long sessions get compacted or summarised. Long files cost tokens on every call.
  • Facts:
    • Gloaguen et al. [5]: context files add "over 20%" to inference cost on average.
    • McMillan [7]: compliance with one rule falls as a session goes on, "approximately 5.6% lower odds of compliance per generation step (OR = 0.944)", but file size and rule position had no detectable effect.
  • My BrandMemory lesson: some rules never reached the model because they were at the end of a long prompt that was cut off. Context is a budget, and position can matter when text is truncated.
  • In Yuki 2.0, slimming the prompt cut the cached start of a typed request from about 32,500 to 14,800 tokens, and the median time to the first token from 1,572 to 1,372 ms. The repeated start of the prompt is sent with every call, so its size matters.

5.3 Context files

  • CLAUDE.md (Claude Code) and AGENTS.md (Codex and others) hold project rules: build and test commands, architecture, style, process.
  • Claude Code docs (from the verified dossier): CLAUDE.md "content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance." Claude Code reads AGENTS.md "only when you have no CLAUDE.md" (needs v2.1.277 or later).
  • Anthropic's docs recommend keeping each CLAUDE.md under 200 lines (quoted by Santos et al. [8], who use 200 lines as their Context Bloat threshold).
  • Codex (from the verified dossier): a global AGENTS.md in CODEX_HOME, plus one file per directory from the repository root down. project_doc_max_bytes is 32 KiB by default.
  • What files contain (lab papers):
    • Manifests (PROFES 2025): Build and Run 77.1%, Implementation Details 71.9%, Architecture 64.8%, Testing 60.5%, Security only 8.7%.
    • Agent READMEs (TOSEM, v2 numbers): Testing 75.9%, Implementation Details 70.8%, Architecture 68.1%, Build and Run 63.0%, Security 14.8%, Performance 14.5%. 67.0% of Claude Code files change in more than one commit; files grow by small additions and "evolve like configuration code".

5.4 Headless mode (running agents from a script)

Claude Code (docs at code.claude.com/docs/en/headless, checked 21 Oct 2026):

  • claude -p "task" runs non-interactively ("-p (or --print)").
  • --output-format json gives the result plus metadata, including total_cost_usd and a per model cost breakdown. stream-json gives events line by line.
  • --allowedTools "Read,Edit,Bash" auto-approves tools. --permission-mode sets a baseline (for example acceptEdits, dontAsk, auto).
  • Warning for my study: --bare skips "auto memory, and CLAUDE.md". The docs say it "will become the default for -p in a future release". So I must not use bare mode, and I must check after every upgrade that CLAUDE.md is still loaded.
  • Without --bare, a -p session "runs the hooks in a project's .claude/settings.json and connects the servers in its .mcp.json, even in a folder you've never trusted". Cloned repositories must run in a sandbox container.
  • Isolation (from the verified dossier; re-check): a separate CLAUDE_CONFIG_DIR so my own ~/.claude/CLAUDE.md does not leak in; CLAUDE_CODE_DISABLE_AUTO_MEMORY=1; CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 can serve as a no file condition.

Codex (docs at learn.chatgpt.com/docs/non-interactive-mode, checked 21 Oct 2026):

  • codex exec "task" runs non-interactively. Progress goes to stderr, the final message to stdout.
  • "By default, codex exec runs in a read-only sandbox." Use --sandbox workspace-write to let it edit files.
  • --json prints a JSON Lines stream of events.
  • From the verified dossier: --ephemeral, --ignore-user-config, -m (model). Use a fresh CODEX_HOME per run so a global AGENTS.md does not leak in.

Reproducibility checklist for my runs.

  • Pin the CLI version and the full model ID. McMillan pinned Claude Code CLI 2.1.92 and ran it in --print mode.
  • Log per run: condition, task, run index, git hash, SHA-256 of the context file, exact model ID, tokens, turns, duration (McMillan logged all of these to SQLite).
  • Clean container per run, no git history (as Gloaguen did), same task text for every version.
  • Same file text for both agents: CLAUDE.md for Claude Code, AGENTS.md for Codex. Gloaguen did the same: "writing it to AGENTS.md for CODEX ... or to CLAUDE.md for CLAUDE CODE".
  • Mix the order of runs across versions so a model update cannot line up with one version.

Say it.

"A coding agent is a model inside a loop: the model asks for a tool call like reading a file or running tests, the harness runs it and feeds the result back, and everything it sees, including the context file, lives in a limited context window. For my experiment I run Claude Code with claude -p and Codex with codex exec from a script, with pinned versions, a clean container per run, and checks that the context file is really loaded, because bare mode in Claude Code skips CLAUDE.md."

My experience (if asked "Have you run them from scripts yourself?").

"I have not yet built a scripted container harness like the one in my plan. The pilot is where I build it."

6. Linters and formatters (Ruff, ESLint)

What they are.

  • A linter checks code for likely bugs and style problems without running it, and reports rule codes. Some problems it can fix automatically.
  • A formatter rewrites code layout (spaces, line breaks, quotes) into one fixed style. It does not judge logic.

Ruff (Python).

  • "An extremely fast Python linter and code formatter, written in Rust", made by Astral (the makers of uv). It can replace Flake8 (and many plugins), Black, isort, pydocstyle, pyupgrade and autoflake.
  • Commands: ruff check . (lint), ruff check --fix ., ruff format ..
  • Config in pyproject.toml under [tool.ruff] (or ruff.toml). Example:
[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "C90", "T20"]   # pycodestyle, Pyflakes, isort, mccabe, print statements

[tool.ruff.lint.mccabe]
max-complexity = 10
  • Rule codes I should recognise: F401 unused import, E501 line too long, I001 unsorted imports, C901 function too complex (McCabe), T201 print found.

ESLint (JavaScript and TypeScript).

  • The standard JS linter. Config in eslint.config.js (flat config). Run with npx eslint ..
  • Example rules: no-unused-vars, eqeqeq (use ===). TypeScript support via typescript-eslint. Formatting is usually left to Prettier.
// eslint.config.js
export default [
  { rules: { "no-unused-vars": "error", "eqeqeq": "error" } },
];

Why this matters for my plan.

  • Santos et al. [8] call rules that a linter already checks Lint Leakage, the most common configuration smell: 62 of 100 files. They quote advice that formatting and import order "are deterministic problems with deterministic solutions" for "Biome, ESLint, or Ruff".
  • RQ2 asks whether linter coverage changes how effective a rule is. To decide if a rule is "already enforced", I would check two things:
    1. Covered: the repo's linter config (pyproject.toml, ruff.toml, .flake8, setup.cfg, pre-commit config) enables a rule that matches.
    2. Actually run: the linter runs where the agent sees it (a pre-commit hook, a CI check, or a line in the context file telling the agent to run it).
  • In the real PR study I leave out cases where linter settings changed at the same time as the rule.

Say it.

"A linter flags likely bugs and style problems by rule code and a formatter just rewrites the layout; Ruff does both for Python and ESLint is the standard linter for JavaScript. Santos et al. found that 62% of files repeat rules a linter already checks, so in RQ2 I check whether a rule is covered by the project's linter config and whether that linter actually runs."

My experience.

"At Layerpath we use Biome and the TypeScript compiler. In Yuki for Mac I use ruff and strict mypy, with CI."

7. Static analysis

What it is.

  • Analysing code without running it. The opposite is dynamic analysis (tests, coverage, profiling).
  • Families:
    • linters (Ruff, Pylint, ESLint);
    • type checkers (mypy, pyright);
    • security scanners (Bandit for Python, Semgrep for many languages);
    • metric tools (radon and Lizard for complexity; DesigniteJava for smells);
    • platforms that combine many checks (SonarQube).
  • Warnings can be wrong (false positives) or missing (false negatives). Different tools disagree. So always fix one tool and one version, and report which.

Link to the lab.

  • The readability paper used radon for Maintainability Index, cyclomatic complexity, lines of code and Halstead metrics.
  • Agent READMEs used Lizard for cyclomatic complexity and lines of code.
  • Agentic Refactoring used RefactoringMiner to detect refactorings and DesigniteJava for metrics and "27 design and implementation smells". It lists tool errors as a threat: RefactoringMiner "is known to produce both false positives and false negatives".

In my plan (RQ3).

  • Count static analysis warnings in the new code, normalised by size (for example per 100 changed lines), and compare file versions on the same task.
  • Avoid circularity: leave out any check that encodes the rule. Example: if the rule is "use the logger, not print", drop T201 from the warning count, otherwise the rule "improves quality" by definition.

Say it.

"Static analysis means checking code without running it, with linters, type checkers, security scanners and metric tools, and each tool has false positives, so I fix the tool and version. In RQ3 I count warnings in the agent's new code, but I remove any check that encodes the rule itself, so the result is not circular."

8. Cyclomatic complexity

What it is.

  • McCabe's measure (1976) of how many independent paths go through a piece of code. More decision points, more paths, more tests needed, harder to understand.
  • Formula on the control flow graph: M = E - N + 2P
    • E = number of edges, N = number of nodes, P = number of connected parts (1 for one function).
  • Shortcut for one function: M = number of decision points + 1.

Worked example 1 (formula).

def grade(score):
    if score >= 90:
        return "A"
    elif score >= 75:
        return "B"
    return "C"
  • Nodes: (1) if score >= 90, (2) return "A", (3) elif score >= 75, (4) return "B", (5) return "C", (6) exit. N = 6.
  • Edges: 1→2, 1→3, 3→4, 3→5, 2→6, 4→6, 5→6. E = 7.
  • M = 7 - 6 + 2 x 1 = 3. Shortcut: 2 decisions (if, elif) + 1 = 3. radon, Lizard and mccabe all give 3 (I ran them).

Worked example 2 (tools disagree).

def ship_cost(order):
    if order.weight > 20:
        cost = 15
    elif order.weight > 5:
        cost = 8
    else:
        cost = 4
    for item in order.items:
        if item.fragile and not order.insured:
            cost += 2
    return cost
  • Decisions: if, elif, for, inner if = 4, plus the boolean and = 5.
  • radon: 6 (rank B). Lizard: 6. The mccabe package (used by Ruff's C901 and Flake8): 5. I ran all three on 21 Oct 2026.
  • Reason: radon adds +1 for each boolean operator (and, or); mccabe does not. Lesson: name the tool and keep it fixed.
  • radon's counting: +1 for if, elif, for, while, except, with, assert, comprehensions, and boolean operators; +0 for else and finally.
  • radon ranks: A 1 to 5 (low risk), B 6 to 10, C 11 to 20, D 21 to 30, E 31 to 40, F 41 and above.

Limits.

  • It grows with size, so compare per function or normalise by lines of code.
  • It does not measure naming, readability or design quality.
  • For RQ3, measure only the functions the agent added or changed, not the whole file.

Link to the lab.

  • Readability paper: in 403 readability related agent commits, "the Maintainability Index decreased in 56.1% of commits, while Cyclomatic Complexity increased in 42.7%".
  • Testing paper: AI written tests and human tests both have median complexity 1.00.
  • Voria et al. [9] plan to compute cyclomatic complexity changes of agent commits after context file changes.

Say it.

"Cyclomatic complexity counts the independent paths through code, E minus N plus 2P on the control flow graph, or simply the number of decisions plus one for a function. Tools count slightly differently, for example radon counts and and or but mccabe does not, so I fix one tool and measure only the functions the agent changed."

9. Code review

What it is.

  • Other developers read a change before it is merged, to find bugs, check design and style, share knowledge and keep the codebase consistent.
  • On GitHub it happens inside PRs: inline comments, then Approve or Request changes.
  • Useful measures: time to merge, number of review rounds, number and type of comments, merge or reject.

Link to the lab.

  • "On the Use of ChatGPT for Code Review", M. Watanabe et al., EASE 2024.
  • "RevToken: A Token-Level Review Recommendation", Morikawa et al., ICSME 2024.
  • The PR paper: 45.1% of merged agent PRs needed revisions, often for "adherence to project-specific standards".
  • Agent READMEs advises treating context files like configuration code: review them in PRs, use CODEOWNERS and versioning.

In my plan. Context file rules are partly a way to move review comments upstream: if reviewers keep writing "put tests in tests/", a rule tries to prevent it. In Year 2, my checker tool is evaluated by developers judging whether each warning is correct and useful, which is close to a code review task.

My experience. I review the changes Claude Code and Codex make at work and maintain CLAUDE.md / AGENTS.md files. One example: "Once an agent applied a database change directly instead of writing a migration file. The change worked, but it broke our migration history and blocked a deploy. So I added a rule to the instructions my coding agent reads: always write a migration file and let the deploy pipeline apply it, and never push changes straight to the shared database. I have not measured whether agents follow it every time, which is exactly my research question."

Say it.

"Code review is where other developers check a change before merge, and the lab's PR paper found that many agent PRs still needed revisions to fit project standards. A context file rule is an attempt to give the agent that review feedback before it writes the code, and my study measures whether that actually works."

10. Technical debt and self-admitted technical debt (SATD)

What it is.

  • Technical debt: shortcuts that make work faster now but cost extra later, like interest on a loan. The metaphor comes from Ward Cunningham (1992).
  • Self-admitted technical debt (SATD): debt that developers admit in comments, for example # TODO: this method is too complex, split it or # HACK: ....
  • The key paper is Potdar and Shihab, "An Exploratory Study on Self-Admitted Technical Debt", ICSME 2014 (it received a Most Influential Paper talk at ICSME 2024). Later work (Maldonado and Shihab, 2015) split SATD into types such as design, defect, documentation, requirement and test debt.

The lab's SATD line (a big lab topic).

  • Yonekura et al., ICPC 2025, "Leveraging Context Information for Self-Admitted Technical Debt Detection": existing SATD detectors produce many false positives; they analysed 137 false positive cases and proposed CASTI, which adds context information to CodeBERT.
  • Nakamura, Kashiwa, Lin, Iida, "Understanding Self-Admitted Technical Debt in Test Code" (TOSEM 2026 per the lab page; arXiv 2510.22249): 17,766 SATD comments from 50 repositories, 2,779 in test code; SATD in tests is common and "not directly associated with test smells"; a CodeBERT based classifier did best.
  • Yoshimoto et al., "Is Self-Admitted Technical Debt Tested?" (ESEM 2026 per the lab page; arXiv 2609.13485): 8 Java projects; 60.7% of SATD affected code is covered by tests, but only 3.4% of SATD removal commits add tests targeting the resolved debt.

Link to my plan.

  • Agent READMEs (Iida last author) has a recommendation titled "Define and measure context debt as a new form of technical debt". It asks future work to formalise context debt by finding "agent context file smells (e.g., ambiguous directives, conflicting role definitions)". So the lab itself already connects context files to its technical debt line.
  • A rule that agents ignore, or that no longer matches the code, is like a TODO comment nobody removes: it looks like control but costs attention. My checker in Year 2 is a small step toward measuring context debt.

Say it.

"Technical debt is the future cost of shortcuts, and self-admitted technical debt is when developers admit it in comments like TODO or HACK; the lab has a strong line of work on detecting SATD and on SATD in test code. Agent READMEs calls the context file version of this problem context debt, and a rule agents ignore is one kind of it, which is what my checker tool would flag."

11. Code smells and configuration smells

Code smells.

  • Signs in code that suggest a deeper design problem. Not bugs, but they make change harder. The common list comes from Fowler's book "Refactoring" (1999).
  • Examples: Long Method, Large Class (God Class), Duplicated Code, Feature Envy (a method uses another class's data more than its own), Long Parameter List.
  • Test smells, for example Assertion Roulette (many asserts with no message). The lab's testing paper names test smells as future work.
  • Detection tools: DesigniteJava (used in Agentic Refactoring), PMD, SonarQube.

Configuration smells.

  • Older meaning: smells in infrastructure configuration code (for example Puppet), see "Does Your Configuration Code Smell?" (Sharma, Fragkoulis and Spinellis, MSR 2016).
  • New meaning for agents: Santos et al. [8], "Configuration Smells in AGENTS.md Files", SCAM 2026. They reviewed 14 grey literature articles and 17 PRs, found six smells, and measured them in 100 popular repositories:
Smell Meaning (short) Found in
Lint Leakage Rules a linter or formatter already checks 62% of files
Context Bloat File too long (heuristic: 200 lines or more) 42%
Skill Leakage Rare, specialised instructions that belong in a skill file loaded on demand 35%
Blind Reference Points to another document without saying why or when to read it (see paper)
Init Fossilization Generated by /init and never updated (heuristic: only one commit) (see paper)
Conflicting Instructions Rules that contradict each other (see paper)
  • Detection: line count for Context Bloat, commit count for Init Fossilization, and an LLM prompt per smell (gemini-3.1-flash-lite, temperature 0) for the other four, with every hit reviewed by the first author.

In my plan. The Year 2 checker reuses these smell detectors where possible and adds warnings based on RQ2: rules agents tend to ignore, rules that conflict, rules a linter already covers.

Say it.

"A code smell is a sign of a design problem, like a very long method or duplicated code, and Santos et al. recently defined six smells for AGENTS.md files, with Lint Leakage in 62% of the files they studied. My Year 2 checker would reuse their detectors and add warnings from my own results, like rules that agents tend to ignore."

12. Refactoring

What it is.

  • Changing the structure of code without changing its behaviour, to make it easier to understand and change (Fowler).
  • Examples: Rename Variable or Method, Extract Method, Move Method, Inline Method, Change Variable Type.
  • Low level refactorings are small and local (rename, change type). High level ones change design (move classes, extract interfaces).
  • Detection: RefactoringMiner finds refactorings in commit history (Java mainly).

Link to the lab.

  • Agentic Refactoring (Horikawa, Li, Kashiwa, Adams, Iida, Hassan; arXiv 2511.04824, submitted to TOSEM, acceptance not verified): 15,451 refactorings in AIDev Java commits.
    • Agents explicitly targeted refactoring in 26.1% of commits.
    • Low level refactorings: 35.8% of agent refactorings vs 24.4% for humans. High level: 43.0% vs 54.9%.
    • Agents state maintainability as the purpose 52.5% of the time vs 11.7% for humans.
    • Smell counts "do not show FDR-significant reductions".
  • "How Does Test Code Differ From Production Code in Terms of Refactoring?", K. Horikawa et al., ICSME 2025.
  • "Evaluating Cross-Language Transfer for Refactoring Detection with Large Language Models", Liu et al., SANER 2026.

Link to my plan. The most impactful single rule in Guardrails [6] was "do not refactor unrelated code" (a 20 point drop in pass rate when removed). Unwanted refactoring is a real agent behaviour that rules try to control, and a rule like this could be checked by a script on the diff (are files outside the task touched?).

Say it.

"Refactoring means changing code structure without changing behaviour, like renaming or extracting a method, and the lab's Agentic Refactoring paper found that agents mostly make small, low level refactorings. Rules like do not refactor unrelated code are common in context files, so this is one kind of rule I would like to include if I can check it with a script."

13. Types of software maintenance

Classic types (Swanson 1976, extended in ISO/IEC 14764).

Type Meaning Context file example
Corrective Fix a fault Fix a wrong test command in CLAUDE.md
Adaptive Adapt to a changed environment Update the setup rules after moving from pip to uv
Perfective Improve quality, performance or features Reword a vague rule so it is clearer
Preventive Prevent future problems Add "never commit secrets or .env files"
  • SWEBOK v4, as used by Voria et al. [9], groups them into corrections (corrective, preventive, emergency) and enhancements (adaptive, perfective, additive). Voria et al. plan to classify context file changes this way and relate the categories to later code quality, using Corrective Commit Probability (CCP, Amit and Feitelson), "the share of corrective commits within a development period".

Related lab and outside results.

  • Sawada et al. [3] (EASE 2026): files created by agents had about half the commits of human files in the first month; on agent files the top commit types were feat 21.78%, refactor 14.19%, chore 13.35%, fix 11.73%; humans made 83.21% of the commits on agent files. Their own caution: "Practitioners should therefore not assume that low maintenance frequency alone indicates high code quality."
  • Xia and Miller (arXiv 2607.09902): agent code needed more corrective maintenance after merge (subdistribution hazard ratio 1.46), while the overall result (HR 1.11) was not significant. Their data is not AIDev and they do not study context files.

In my plan. In the real PR study I count later fix commits on merged agent code, as in [3], as one sign of corrective maintenance.

Say it.

"The classic maintenance types are corrective for fixing faults, adaptive for a changed environment, perfective for improvements, and preventive for avoiding future problems. Voria et al. plan to use these categories for context file changes, and in my real PR study I use later fix commits, which are corrective maintenance, as one sign of how much work agent code needs."

14. Rapid fire questions

"What is the difference between a linter and static analysis?"

"A linter is one kind of static analysis, focused on style and likely bugs with fixed rules. Static analysis is the wider family, including type checkers, security scanners and metric tools."

"Why Python only?"

"Python has good tools for checking rules and measuring quality, many AIDev repositories use it, and Gloaguen's benchmark is also Python, so I can compare. I state the scope clearly and release the scripts so other languages can be added."

"Claude Code reads CLAUDE.md and Codex reads AGENTS.md. Is that a fair comparison?"

"I give both agents the same text under the file name each one reads, which is also what Gloaguen et al. did. I compare file versions within each agent first, so differences between the two file names do not affect RQ1."

"How do you know the context file was loaded?"

"I avoid modes that skip it, like Claude Code's bare mode, and I keep the agent's logs for every run. In the pilot I can also add a harmless canary rule and check that the agent follows it, to confirm the file is read."

"What if the agent saw the PR during training?"

"I prefer PRs merged after the models' training cutoff and remove git history from the container. Gloaguen et al. compared instances before and after the cutoff and found no consistent difference, but I will still report the split."

"How is your study different from SWE-bench?"

"SWE-bench asks whether the agent solves the task; I keep the task fixed and change one rule in the context file. The question is whether the agent follows that rule and how the code changes, not only whether tests pass."

"What is a context file, simply?"

"It is a Markdown file in the repository, like CLAUDE.md or AGENTS.md, where developers write project rules for coding agents, such as how to run tests or where files go. The lab's papers show these files are common, change often, and mostly contain build, test and architecture information."
