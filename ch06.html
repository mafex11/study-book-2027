L1. On the Use of Agentic Coding Manifests: An Empirical Study of Claude Code

Basic facts

  • Authors: Worawalan Chatlatanagulchai (first author, Kasetsart University, Thailand), Kundjanasith Thonglek, Brittany Reid [Reid], Yutaro Kashiwa [Kashiwa], Pattara Leelaprute, Arnon Rungsawang, Bundit Manaskasemsak, Hajimu Iida [Iida, last author]. Kasetsart: authors 1, 2, 5, 6, 7. NAIST: Reid, Kashiwa, Iida.
  • Venue/year: PROFES 2025 (26th International Conference on Product-Focused Software Process Improvement), Short Papers and Posters track, Springer LNCS pp. 543 to 551, DOI 10.1007/978-3-032-12089-2_40. (The arXiv PDF does not print the venue; this comes from Crossref via the verified dossier.)
  • arXiv: 2509.14744 (v1, 18 Sep 2025).
  • Length: short paper, about 8 pages.

Say it in one breath

"In an early study of CLAUDE.md files (to the authors' knowledge, the first systematic analysis of their structure), 253 files from 242 GitHub repositories, they found that developers write shallow files, usually one main heading and a few sections, that mostly tell the agent how to build and run the project, implementation details and architecture, while security and performance are rare."

What they did

  • Data:
    • GitHub API search for files named Claude.md (any case), created between 24 Feb 2025 and 16 Jun 2025. The paper writes "Claude MCP" for the 24 Feb release; it means Claude Code (a naming slip).
    • Found "838 Claude.md files distributed in 806 different repositories".
    • Kept repositories with "at least 20 commits after introducing their Claude.md file" (the paper explains this as about five commits per month over four months).
    • Final: "253 Claude.md files from 242 repositories". They also "retrieved 1,249 commits in total". (my note) The results do not report any analysis of these commits.
  • RQ1: "How Are Agent Manifest Files Organized?" Counted Markdown headers (H1 to H6) and non-empty lines per section, not counting lines inside code blocks.

  • RQ2: "What Instruction Are Included?" Two-stage manual labelling:

    1. Took all H1 and H2 titles. Three LLMs (Claude, Gemini, ChatGPT) suggested candidate labels. One author picked or created labels; two authors reviewed. Result: 80 labels, merged by three inspectors into 20 core labels.
    2. Two inspectors labelled every file (more than one label per file allowed): "1,228 total label assignments across the 253 files, with 113 instances of disagreement". A third inspector joined to reach consensus. A new label, Build and Run, was added. Final: 15 labels.
    • Inspectors had 4 to 17 years of programming experience. No kappa is reported.

Key results (exact numbers)

  • Structure: median H1 = 1.0, H2 = 5.0, H3 = 9.0. "H4 appearing in only 37 documents and H5 in just 5" (out of 253). "We observed H6 only once in the entire corpus".
  • Answer to RQ1 (quote): "Agent manifest files are typically organized using a shallow hierarchical structure, with most documents starting from a single top-level heading and branching into a moderate number of H2 and H3 subsections."

  • Content (Table 1, % of files containing each category):

    Category % Category %
    Build and Run 77.1 AI Integration 15.4
    Implementation Details 71.9 Documentation and References 13.8
    Architecture 64.8 Performance 12.7
    Testing 60.5 Project Management 11.1
    System Overview 48.2 DevOps 9.5
    Development Process 37.2 Security 8.7
    Configuration and Environment 26.5 UI/UX 8.3
    Maintenance (spelled "Maintainance") 19.8

  • Their reading (quote): manifests "are primarily optimized to help agents execute and maintain code efficiently rather than address broader quality attributes or user-facing aspects."

  • 15.4% of files (AI Integration) "explicitly define the agent's role and describe its responsibilities within the project (e.g., reviewers)."

Limitations and future work they state

  • The paper has no Limitations or Threats to Validity section. I searched the full text for "limitation", "threat" and "validity": nothing.
  • (my note, not in the paper) Obvious limits: one agent only (Claude Code); a four-month window right after release; labels only mark whether a topic is present; no agent is run, so it says nothing about effects.
  • Section 5 "Future Direction" (quotes):
    • "Our future work will pursue the following two directions as well as involving more different agentic coding tools, such as Codex and Copilot."
    • Maintenance: "Future work could examine the evolution and decay of Claude.md files, revealing update frequencies, change-prone sections, and correlations with project development cycles or agent performance."
    • Impact: "A critical direction for future research is to empirically assess the direct impact of Claude.md files on the performance of the Claude agent and the productivity of developers utilizing it. This could involve controlled experiments where agents are tasked with identical coding challenges, but with varying qualities or completeness of agentic coding manifests. Metrics such as task completion time, code quality (e.g., bug count, adherence to style guides), number of iterations, and developer satisfaction could be measured."
  • What happened next: L2 took up the "more tools" and "Maintenance" directions. Neither L1 nor L2 ran the controlled "Impact" experiment.

How it relates to your proposal

  • What you build on:
    • Your sentence "most include build and test commands, implementation details and architecture notes [1, 2]" comes from Table 1 here (and Table 3 in L2).
    • The "Impact" direction is very close to your core study: identical tasks, different versions of the file, and outcomes that include "adherence to style guides" and code quality.
  • What is different:
    • L1 describes files. You run agents on them.
    • L1 suggests varying the overall "quality or completeness" of the file. You change one real rule at a time (removed, reworded, replaced by a neutral sentence) and keep the rest fixed.
    • L1 covers Claude Code only. You use Claude Code and Codex.
    • You measure compliance with that rule by script, plus tests, complexity and warnings. You do not measure completion time or developer satisfaction.

Careful (do not say)

  • Do not say L1 shows that CLAUDE.md files improve agent performance. It runs no agent.
  • 77.1% Build and Run is L1. In L2 the top category is Testing (75.9%).
  • It is a short paper, not a full paper.

Likely interview questions

Q1. "Our PROFES paper already lists controlled experiments as future work. So what is new in your plan?"

Yes, I read Section 5, and my core study is close to the Impact direction there. I came to the same need from my work. At Layerpath some rules in a prompt had no effect, and I only saw it when I measured. My version is narrower. I don't change the overall quality of the file. I change one real rule at a time, keep the rest of the file the same, and check with a script whether that rule is followed. I also check tests, complexity and static analysis warnings, and I run both Claude Code and Codex. So I see it as one concrete way to do the experiment your paper suggested.

Q2. "What did this paper find, and what can it not tell us?"

It looked at 253 CLAUDE.md files from 242 repositories. The files are shallow, with a median of one H1, five H2 and nine H3 headings. The most common content is Build and Run, 77.1%, then Implementation Details, 71.9%, and Architecture, 64.8%. Security is only 8.7%. So it tells us what developers write. It does not run any agent, so it cannot tell us which of these instructions change what the agent does. That is the part I want to study.

L2. Agent READMEs: An Empirical Study of Context Files for Agentic Coding

Basic facts

  • Authors: Worawalan Chatlatanagulchai (first author; Kasetsart University and NAIST in v2), Hao Li (Queen's University, Canada), Yutaro Kashiwa [Kashiwa], Brittany Reid [Reid], Kundjanasith Thonglek, Pattara Leelaprute, Arnon Rungsawang, Bundit Manaskasemsak, Bram Adams (Queen's), Ahmed E. Hassan (Queen's), Hajimu Iida [Iida, last author].
  • Venue/year: ACM TOSEM (Transactions on Software Engineering and Methodology), 2026. DOI 10.1145/3840295; accepted 13 Jul 2026, online 15 Sep 2026 (Crossref, via the verified dossier). The lab page lists "TOSEM, Oct. 2026".
  • arXiv: 2511.12884, v2 (9 Aug 2026). Your local PDF is v2. Use v2 numbers; the v1 abstract (Nov 2025) had different percentages.
  • Length: 38 pages with appendix.
  • It says it builds on L1: "Building on our prior work [14] which studied 253 context files for Claude Code".

Say it in one breath

"The large follow-up to the PROFES paper: 2,303 context files for Claude Code, Codex and Copilot from 1,925 repositories are long, hard to read and edited often through small additions, like configuration code, and they focus on testing, implementation details and architecture, while security (14.8%) and performance (14.5%) are rare."

What they did

  • Data:
    • Repositories from the AIDev dataset with at least 5 stars: 8,370 repositories.
    • GitHub API scan for CLAUDE.md, AGENTS.md and copilot-instructions.md (any case).
    • Result: "922 Claude Code files, 694 OpenAI Codex files, and 687 GitHub Copilot files across 1,925 repositories" (2,303 files).
    • Replication package: https://github.com/woraamy/Agent-Context-File-Analysis. Its README (checked 21 Oct) lists commit-history datasets and the final manual labels.
  • RQ1: "What are the characteristics of agent context files?" Size (word count), readability (Flesch Reading Ease, FRE, with the Textstat library), structure (Markdown headers). Mann-Whitney U test with Cliff's delta. They also measured cyclomatic complexity and lines of AI commits after adoption (Lizard), to check whether long files are explained by harder tasks.
  • RQ2: "How often do developers maintain agent context files?" Every commit that adds, deletes or changes a context file: 5,655 (Claude Code), 2,767 (Codex), 2,237 (Copilot). Commit counts, time between edits, words added and deleted. Plus a manual look at a random sample of 100 commits after adoption, with six labels (add a line or section, fix an instruction, delete a line or section, non-functional maintenance).
  • RQ3: "What instructions are included in agent context files?" Grounded-theory style coding:
    • Open coding seeded with H1/H2 titles. Three LLMs (Claude Opus 4.1, Gemini 2.5 Pro, GPT-5) suggested candidate labels; humans made every final decision. 61 initial labels.
    • Axial coding merged them into 16 categories.
    • Selective coding on a proportional sample of 332 files: "2,227 label assignments, with 438 disagreements, corresponding to an agreement rate of 80.3%". A third inspector resolved disagreements, giving "2,069 final label assignments".
  • RQ4: "To what extent can instructions in agent context files be classified automatically?" GPT-5 at temperature 1, multi-label, prompt with category definitions and examples, JSON output, scored against the 332 human-labelled files.

Key results (exact numbers)

RQ1 (characteristics)

  • Median length: Copilot 535.0 words, Claude Code 485.0, Codex 335.5. Copilot (d = 0.21) and Claude Code (d = 0.22) files are longer than Codex files, both small effect sizes (Cliff's delta).
  • FRE (higher means easier): Claude Code 42.39 ("difficult"), Copilot 44.39, Codex 51.41 ("fairly difficult").
  • FRE against human judgement on 100 files: Spearman rho = 0.19 (p = 0.05), a weak relationship. The authors conclude low FRE scores "partly reflect technical vocabulary and document structure rather than true difficulty".
  • Structure: median H1 = 1.0 for all; H2 median 6 to 7; H3 Copilot 12.0, Claude Code 11.0, Codex 9.0; "H5 headers appear in only 9 files, and H6 headers are nonexistent".

RQ2 (maintenance)

  • Files changed in more than one commit: Claude Code 67.0%, Copilot 59.8%, Codex 59.4%.
  • Median time between edits: Copilot 68.0 hours, Claude Code 23.8 hours, Codex 22.3 hours.
  • Deletions: median below 15.0 words for all. Claude Code commits add a median of 57.0 words.
  • Manual sample of 100 commits: "Some form of substantive instruction edit (adding, fixing, or deleting directives) appears in 92% of the sampled commits"; pure non-functional maintenance is the only label in 8%. Addition labels appear 78 times across 66 commits; fix:instructions appears in 32 of 100; deletion labels only 19 times.
  • Answer to RQ2 (quote): "Agent context files are actively maintained and a majority (59% to 67%) are modified in multiple commits ... evolution is driven mainly by small incremental additions rather than large-scale deletions or rewrites."

RQ3 (content, Table 3, % of files)

Category % Category %

Implementation Details 70.8 Debugging (new) 25.3
Architecture 68.1 AI Integration 24.1
Development Process 65.1 DevOps 18.4

Maintenance (new) 44.6 UI/UX 8.7

  • Maintenance and Debugging are new compared with L1.
  • Across the three agents the category shares are similar ("typically within 1% to 3%"). (Table 4 gives each category's share of all labels per agent, not % of files. For example, Debugging is in 25.3% of files in Table 3 but only 3.01% to 5.01% in Table 4.)

The indentation case study (most important for you)

  • One machine-checkable rule, 4-space indentation. Compliance in AI-authored commits before vs after the rule was added to the context file.
  • Claude Code repository (rsyslog): "208 violating lines out of 342 eligible added lines before the rule was introduced, a violation rate of 60.82%. Afterward, the rate dropped to 11.03% (939 of 8,516 lines)".
  • Copilot repository (NB-Core/lotgd): "from 20.17% (6,673 of 33,080 lines) before the rule to 7.57% (5,306 of 70,060 lines) afterward".
  • The authors' own caveat (quote): "Although two cases cannot establish causality, the consistent decline after introducing the rule supports our qualitative observations".
  • (my note) The paper's "about 50%" and "about 13%" are percentage points. The design says one project per agent, but only two cases are reported (no Codex case). The case study does not restate how AI-authored commits were identified. Section 4.1.2 describes it: Pydriller for Claude Code and Copilot, and PR metadata plus branch naming (GitHub REST API) for Codex. Commits that mixed several AI tools were excluded.

RQ4 (automatic classification)

  • GPT-5: micro precision 0.73, recall 0.86, F1 0.79.
  • Best: Testing 0.94, Architecture 0.93, Build and Run 0.92. Weakest: Project Management 0.42, AI Integration 0.48, Maintenance 0.56, UI/UX 0.56.

Limitations they state (Section 7)

  • Internal: manual classification can be subjective; two independent inspectors, 80.3% agreement, a third inspector resolved conflicts.
  • Construct:
    • Labels are binary, so "the frequency reported for a category represents only the prevalence of the topic, not the depth, complexity, or qualitative richness".
    • FRE was built for general prose: readers should "treat FRE scores in this context as a measure of surface-level lexical and syntactic complexity rather than as a direct measure of usability or clarity".
    • Headers are detected only as "#" followed by a space, so bold titles or horizontal rules are missed.
  • External: "the dataset remains limited, which constrains the generalizability of our findings. Future work should extend this analysis to include a larger number of files from various agentic coding systems."

Future work they state (Section 5.1, for researchers)

  1. Context debt: "Future work should formalize context debt by identifying specific agent context file smells (e.g., ambiguous directives, conflicting role definitions) and by developing metrics beyond standard readability scores to assess the maintainability of agent instructions."
  2. Structure ablation: "It remains an open research question whether removing these H1 and H2 headers, or altering their hierarchy, would significantly degrade an LLM's comprehension or its ability to execute tasks accurately." And: "Future work should move beyond binary presence or absence evaluations and conduct controlled ablation studies on the structural markers themselves." (Note: their ablation idea is about structure, not about single instructions.)
  3. Co-evolution and a linter: "Future work should analyze paired code-and-agent context file commits to establish a more direct co-evolutionary link and quantify the degree of coupling." A linter "could verify that the commands listed in the Build and Run section (63.0% prevalence) match the actual scripts in package.json or Makefile".
  4. NFR blind spot: "The research community should design new benchmarks or evaluation frameworks that explicitly test an agent's adherence to NFRs defined in agent context files." Tracking when NFR instructions get added in each commit "is left as future work".
  • For developers (5.2): treat context files as configuration-as-code, review them in pull requests, add NFR sections, version them, use CODEOWNERS. For tool builders (5.3): templates with the common categories; category-aware retrieval.

How it relates to your proposal

  • What you build on:
    • Your background sentence "the files grow through frequent small additions, and rules about security or performance are rare [2]" comes from RQ2 and RQ3.
    • Your real-PR study is a scaled-up version of their indentation case, with more repositories, more rule types, and human PRs as a comparison. You say this directly: "In [2], the authors report a before and after check of one indentation rule in two repositories."
    • The 16-category taxonomy can help you pick your ~30 rules from different categories. The GPT-5 classifier (F1 0.79) could help label rules at scale.
    • Their dataset and replication package are a starting point for finding repositories with context files.
    • Your Year 2 checker answers their call for "context debt" and "agent context file smells", and their linter idea.
    • "Rules are rarely deleted" motivates your question: if files only grow, developers need to know which rules actually work.
  • What is different:
    • L2 measures what is in the files (prevalence). You measure the effect of one rule on what the agent does and on the code.
    • L2 suggests ablating structure (headers). You ablate content (one rule). McMillan [7] already varied structure for one rule and found no detectable effect.
    • L2's evidence that agents follow rules is illustrative examples plus two observational cases. You test it under control.

Careful (do not say)

  • The top category in L2 is Testing 75.9%, not Build and Run (that is L1's 77.1%). Build and Run is 63.0% in L2.
  • Use v2 numbers. The v1 abstract had different ones (for example Build and Run 62.3%).
  • "About 50%" drop means percentage points (60.82% to 11.03%), not a relative 50%.
  • Do not credit it to NAIST alone. Say "your group's paper with Kasetsart and Queen's".
  • The text says "half of the files contain system overview", but Table 3 says 59.0%. Quote the table.

Likely interview questions

Q1. "Our paper already showed indentation violations dropped after the rule was added. Why do you need an experiment?"

That result was a big reason I wrote this proposal. In rsyslog the violation rate fell from 60.82% to 11.03%, and in lotgd from 20.17% to 7.57%. But your paper says itself that two cases cannot establish causality. Many things change over time. The model gets better, the linter may change, new people join. In my experiment I keep the task, the agent version and the rest of the file fixed, and change only the rule. Then a difference comes from the rule. I also want to repeat your before and after check on more repositories, with human PRs as a comparison.

Q2. "The paper suggests ablation studies on headers and structure. Why do you ablate single rules instead?"

I thought about it. A factorial study by McMillan varied file size, instruction position and file structure for one simple rule and found no detectable effect. So structure looks less promising to me. Your paper also shows that files mostly grow by additions, and deletions are small. So developers keep adding rules without knowing which ones work. A study at the level of single rules answers that more directly. If the lab thinks structure is more interesting, I could add it as a small side check.

L3. To What Extent Does Agent-generated Code Require Maintenance? An Empirical Study

Basic facts

  • Authors: Shota Sawada (first author; National Institute of Technology, Nara College; the lab site lists him as a Summer 2025 intern), Tatsuya Shirai (NAIST, PhD student in the lab), Yutaro Kashiwa [Kashiwa], Ken'ichi Yamaguchi (NIT Nara College), Hiroshi Iwata (NIT Nara College), Hajimu Iida [Iida, last author]. No Reid.
  • Venue/year: EASE 2026 (30th International Conference on Evaluation and Assessment in Software Engineering), Glasgow, 9 to 12 June 2026, 6 pages (printed on the PDF). Short Papers and Emerging Results track (per researchr, via the dossier).
  • arXiv: 2605.06464 (v2, 9 May 2026).
  • It is your reference [3].

Say it in one breath

"Following 508 agent-created and 508 human-created files in 100 popular repositories for six months, they found agent files got fewer and smaller later changes. The most common type of later change was feature additions (21.78%), while bug fixes were less common than on human files (11.73% vs 16.76%). Humans made 83% of the later commits on agent files."

What they did

  • Data:
    • AIDev: "more than 456,000 pull requests made by five autonomous coding agents ... from approximately 61,000 repositories", PRs from Dec 2024 to Jul 2025. They used the AIDev list of 2,807 repositories with more than 100 stars.
    • Took files marked "added" in agent PRs, then checked the agent really created them by committer name: "claude[bot]" (Claude Code), "Cursor Agent", "Copilot", "devin-ai-integration" (Devin).
    • Codex was excluded "because it does not appear as a commit owner, making it difficult to determine whether a commit was created by an agent or a developer".
    • Limited to 100 repositories (cost and API limits). Up to 10 AI files and up to 10 human files per repository, from the same period.
    • All commits up to 31 Jan 2026, so every file has at least six months of history. The first commit that created the file was excluded.
    • Final: 508 AI files and 508 human files; 1,543 commits on AI files and 1,695 on human files.
  • RQ1: "To what extent is AI-generated files maintained?" Commits per file per month for the first six months, and size of changes as a share of file size. Shown as violin plots.
  • RQ2: "What types of maintenance activities are applied to AI-generated files?" Commits classified with the Conventional Commits Classification System (CCS), which "achieves 77.95% precision".
  • RQ3: "Who maintains AI-generated files: AI agents or human developers?" Commit author is a bot or a human, by committer name.

Key results (exact numbers)

  • RQ1: "AI-generated files exhibited approximately half the commit count of human-generated files during the first month". "From the fourth month onward, the gap with human-generated files narrows." Changes to AI files are also smaller as a share of file size. (my note) I did not find a statistical test for RQ1 in the paper; the comparison is read from the plots.

  • RQ2 (Table 1, share of commits, AI files vs human files):

    Type AI files Human files
    feat 21.78% (336) 15.10% (256)
    refactor 14.19% 15.10%
    chore 13.35% 11.50%
    fix 11.73% (181) 16.76% (284)
    docs 10.76% 16.22%
    build 10.05% 8.02%
    test 6.09% 6.31%
    style 4.86% 3.95%
    ci 4.47% 4.54%
    perf 2.01% 2.24%

  • RQ3: on AI files, "83.21% of commits (1,284) were made by human developers, while only 16.79% (259) were made by AI agents". On human files, humans made 92.98% (1,576) and agents 7.02% (119).

  • Key warning in the Implications (quote): "Practitioners should therefore not assume that low maintenance frequency alone indicates high code quality."

Limitations and future work they state

  • Other explanations for low maintenance (Section 5): "developers may avoid modifying AI-generated code due to difficulty in comprehending it, or some generated files may not be actively exercised in production."
  • Internal: "We categorized maintenance activities by commit type but did not control for functional complexity". "File importance and intended usage are also uncontrolled: developers may avoid AI for critical files or apply it only in specific cases."
  • Construct: "The dataset covers the first six months after agentic coding tools were released, when developers are likely early adopters prioritizing feature development over maintenance. We also cannot detect AI-assisted code undeclared in commit messages, so human-generated files may include such code."
  • External: "We studied only 508 AI-generated files from 100 repositories, which limits generalizability. We also excluded Codex despite its many commits."
  • Future work (Conclusion): "Future research should extend the observation period beyond six months, compare maintenance patterns across different AI agents, investigate which code characteristics correlate with higher maintenance needs, and explore the development of maintenance-oriented agents that can reduce the human burden identified in this study."
  • Also (Section 6): "Future work should investigate whether code-level features such as cyclomatic complexity, coupling, and file size can serve as predictors of subsequent maintenance activity."

How it relates to your proposal

  • You cite it twice as [3]:
    • "Human developers do most of the later maintenance of code written by agents [3]" (the 83.21%).
    • "For merged agent code I will also count later fix commits, as in [3]".
  • What you build on: the method for later maintenance. Find code that agent PRs added, collect later commits that touch it over a fixed window (they used six months), classify commits with CCS, count fix commits. Their bot-committer-name check is one way to separate agent and human commits.
  • What is different:
    • Sawada compares AI files with human files. You compare agent code written with vs without a rule in the context file (before vs after the rule was added).
    • Sawada does not look at context files at all, and does not measure rule compliance.
  • Watch out:
    • Sawada dropped Codex because commit authorship is unclear. Your real-PR study works at the PR level (AIDev labels which agent opened the PR), but later commits inside a PR may be human. Say this openly if asked.
    • (my note) Fix commits were only 11.73% of commits on AI files (181 commits over 508 files). Later fix commits per PR will be rare, so you need many PRs to see any difference. That is one more reason to treat this measure as a supporting signal.

Careful (do not say)

  • 83% is the share of later commits on AI files made by humans. It is not "83% of agent code needs maintenance".
  • Do not say "agent code is high quality because it needs less maintenance". The paper itself warns against that reading.
  • Its related work says "9.9% of the generated methods are eventually deleted during review" (from the What to Cut paper). According to the verified dossier, that 9.9% holds only within PRs that had revisions; overall it was 2.6% (What to Cut, L6). Avoid quoting 9.9% alone.

Likely interview questions

Q1. "You say you will count later fix commits as in Sawada et al. How exactly?"

I would follow their steps. First I find the code that agent PRs added. Then I collect later commits that touch it over a fixed window. Their window was six months. Then I classify the commits with the Conventional Commits Classification System, which they used, and count the fix commits. I compare agent PRs merged before and after a rule was added. I treat it as one sign of later maintenance, not as a quality score, because the paper itself warns that low maintenance does not mean high quality.

Q2. "Sawada found agent files need less maintenance. Doesn't that mean agent code is already fine?"

I don't think we can say that yet. The paper itself says developers may avoid touching AI code they don't understand, or the file may not be used much. Also, humans made 83.21% of the later commits on agent files, and the most common type was feature additions. So people still carry the work. If a rule makes the first version closer to the project's conventions, it might reduce that work. In my study I can only show this as an association, in the real PR part, and I will say that clearly.

L4. On the Use of Agentic Coding: An Empirical Study of Pull Requests on GitHub

Basic facts

  • Authors: Miku Watanabe (first author, NAIST), Hao Li (Queen's), Yutaro Kashiwa [Kashiwa], Brittany Reid [Reid], Hajimu Iida [Iida, 5th author], Ahmed E. Hassan (Queen's, last author).
  • Venue/year: ACM TOSEM. The first line of the v3 PDF: "This manuscript is accepted at ACM Transactions on Software Engineering and Methodology (TOSEM)." DOI 10.1145/3798166 (dossier). The lab page lists "Dec. 2026".
  • arXiv: 2509.14745, v3 (9 Feb 2026); v1 was 18 Sep 2025. Your local PDF is v3. Some numbers changed from v1 (style and refactor shares).
  • Not cited in your proposal. Know it anyway: Iida, Kashiwa and Reid are all authors, and it recommends CLAUDE.md.
  • Replication package: https://github.com/mmikuu/OnTheUseOfAgenticCoding

Say it in one breath

"Comparing 567 Claude Code pull requests with 567 matched human pull requests in 157 repositories, they found agent PRs were merged less often (83.8% vs 91.0%), 54.9% of merged agent PRs went in unchanged, and the rest were revised mostly for bug fixes, documentation, refactoring and style."

What they did

  • Data:
    • GitHub GraphQL search for PRs whose description contains "Generated with Claude Code", from 24 Feb 2025 (Claude Code release) to 30 Apr 2025, in repositories with at least 10 stars: 797 PRs. 54 still open were removed: 743.
    • Human PRs: same author, same repository, similar time. The window was extended back to April 2024 to find enough matches. 176 agent PRs were dropped because no match was found.
    • Final: 567 Agentic-PRs and 567 Human-PRs across 157 repositories.
  • RQ1: "How do Agentic-PRs differ from Human PRs in terms of change size and purpose?" Manual multi-label classification of 213 merged agent PRs and 221 merged human PRs (sample sizes for 95% confidence, 5% margin), using the Zeng et al. commit categories (fix, feat, refactor, style, perf, docs, test, ci, build, chore). Label agreement 75.8%. Mann-Whitney U for size.
  • RQ2: "To what extent are Agentic-PRs rejected and why?" Merge rate (chi-squared test), time to merge (log-rank test), and manual reasons for the 92 rejected agent PRs (framework of Pantiuchina et al. plus open coding; 68.5% agreement, Cohen's kappa 0.4865).
  • RQ3: "What proportion of Agentic-PRs are accepted without revisions? If needed, to what extent?" Share merged with a single commit; revision effort (commits, files, lines).
  • RQ4: "What changes are required to revise Agentic-PRs?" Manual classification of the 214 revised agent PRs (64.1% agreement), plus "Co-Authored-By: Claude" in revision commits.

Key results (exact numbers)

  • RQ1 (Table 1, agent PRs vs human PRs): fix 31.0% vs 30.8%; feat 26.8% vs 27.6%; refactor 24.9% vs 14.9%; docs 22.1% vs 14.0%; test 18.8% vs 4.5%; build 10.8% vs 3.6%; style 7.5% vs 1.8%; ci 6.1% vs 7.2%; perf 5.2% vs 1.4%; chore 3.8% vs 10.4%.
    • Multi-purpose PRs: 39.9% (85 of 213) of agent PRs vs 12.2% of human PRs.
    • Initial size: median 2 files for both; agent PRs add 48 lines vs 24; PR description median 355 words vs 56.
  • RQ2 (Table 2): merged 475 of 567 = 83.8% vs 516 of 567 = 91.0% (chi-squared, p < 0.05). Median time to merge 1.23 h vs 1.04 h, no significant difference (log-rank).
    • Rejection reasons (Table 3, % of the 92 rejected agent PRs): no feedback 64.1%; implemented by other PRs or developers 12.0%; submission for verification only 5.4%; too large 3.3%; obsolete 3.3%; inactive 2.2%; non-optimal design 2.2%; 1.1% each for do not add value, increase complexity, no confidence in AI-generated code, introduce bugs, not in community interest, merge conflicts, not sure.
  • RQ3: merged with a single commit: 54.9% (261) of merged agent PRs vs 58.5% (302) of merged human PRs, not significant. Revised PRs have a median of 2 revision commits; no significant difference in files or lines.
  • RQ4 (Table 4, % of the 214 revised agent PRs, 45.1% of 475 merged): fix 47.7%; docs 29.0%; refactor 27.1%; style 23.4%; chore 21.0%; test 16.4%; feat 15.4%; build 14.0%; ci 7.0%; perf 1.4%.
    • 41.1% (88 of 214) of revised agent PRs had commits co-authored with Claude, covering 34.1% (298 of 873) of revision commits.
  • The CLAUDE.md recommendation (Section 5.2, quote): "We recommend that developers maintain a dedicated guideline file (e.g., CLAUDE.md, supported by Claude Code) that includes formatting rules, design principles, and architectural constraints."
  • Section 5.3 (quote): "The high rates of style (23.4%) and refactoring (27.1%) revisions indicate that generic models do not fully capture local conventions".

Limitations they state (Section 7)

  • Provenance: "relying on brittle text markers (like 'Generated with Claude Code') is insufficient for analyzing these hybrid workflows. Future research requires more fine-grained provenance tracking mechanisms". Also: "the presence of undisclosed AI-generated code would likely dilute the differences between the two groups".
  • Time window: human PRs reach back to April 2024; 42.0% (238 of 567) are in the same window as the agent PRs. A sensitivity check on that subset gave consistent results.
  • Construct: the role of MCP is not separated; excluding open PRs "creates a survival bias"; and "our reliance on PR acceptance as a primary success metric does not account for long-term code quality or maintainability."
  • External: only Claude Code; early users may be in an "enthusiastic phase".

Future work they state (Section 5.1 and 7)

  • "Quantify the socio-technical cost of building trust in Agentic-PRs."
  • "Create PR-centric benchmarks that reward alignment across code, documentation, and review resolution." Reason given: "Current benchmarks such as SWE-bench overlook documentation drift, style adherence, and reviewer negotiation".
  • "Instrument the entire human-AI workflow, not isolated tools."
  • "Future research should investigate the long-term stability and maintainability of agent-generated code through longitudinal analysis." (my note) Sawada (L3) is one later lab study in this direction.

How it relates to your proposal

  • Motivation you can use: almost half (45.1%) of merged agent PRs were revised, and the style (23.4%) and refactoring (27.1%) revisions are read as agents missing local conventions. The paper's own advice is to write those conventions into CLAUDE.md. Your question is the next step: if developers write them down, does the agent follow them?
  • Their call for benchmarks that check "style adherence", not only tests, matches your outcomes: rule compliance plus tests and quality.
  • Your tasks are replays of merged PRs, the same kind of real PRs studied here.
  • What is different: L4 observes real PR outcomes (merge, revisions) and knows nothing about the context files in those repositories. You control the context file and measure compliance with one rule.
  • Consider citing it in the future as evidence that convention problems are common in agent PRs.

Careful (do not say)

  • "adherence to project-specific standards" is a phrase in the abstract, not a coded category. The coded numbers are style 23.4% and refactor 27.1%.
  • Use v3 numbers (23.4% and 27.1%). v1 said 22.1% and 25.7%.
  • 54.9% is of merged agent PRs (475), not of all 567.
  • Iida is not last author here; Hassan is.
  • (my note) Section 5.1 says "only 2.2% of rejected Agentic-PRs explicitly cited 'lack of confidence'", but Table 3 gives 1.1% (1 PR). If asked, quote Table 3.

Likely interview questions

Q1. "What does our PR study tell you about context files?"

It found that 45.1% of merged Claude Code PRs were changed before merge. Among those, 23.4% had style fixes and 27.1% had refactoring. The paper reads this as agents not capturing local conventions, and it recommends a CLAUDE.md with formatting rules, design principles and architecture constraints. My question starts right there. If developers write those rules down, does the agent actually follow them, and does the code get better? I see this at work too: once an agent applied a database change directly instead of writing a migration file, which broke our migration history and blocked a deploy, so I added a rule to our agent instructions to always write a migration file.

Q2. "Why not use merge rate as your outcome, like this paper?"

Merge depends on many things outside the code. In this paper, 64.1% of rejected agent PRs were closed with no comment, and the most common known reason was that another PR solved the same problem, 12.0%. The paper also says merge does not capture long-term quality. So I want outcomes closer to the rule: whether the code follows it, test results, complexity and warnings. In the real PR part I add later fix commits, as in Sawada et al.

L9. How Do Developers Maintain and Evolve Their Agents' Instructions? An Empirical Study

Basic facts

  • Authors: Gianmario Voria (first author, University of Salerno, Italy), Alfonso Cannavale, Andrea De Lucia, Yutaro Kashiwa [Kashiwa, the only NAIST author], Gemma Catolino, Fabio Palomba (last author, Salerno). No Iida, no Reid.
  • Venue/year: ICSME 2026, Registered Reports track (Stage 1). I checked the ICSME 2026 Registered Reports page on 21 Oct 2026: the paper is in the accepted list, and the page says "Before September 11, 2027: Authors submit a full Stage 2 paper to EMSE." The arXiv PDF itself does not name the venue (it calls itself "This report").
  • arXiv: 2606.25257 (v1, 24 Jun 2026). 7 pages.
  • It is your reference [9].
  • It is a plan. There are no results yet.

Say it in one breath

"A registered report from Salerno with Assoc. Prof. Kashiwa that plans, with no results yet, to sort changes to CLAUDE.md, AGENTS.md and copilot-instructions.md files into software maintenance types, and to test whether each type is associated with the quality of the agent commits that follow it and with when and how often changes happen."

What they plan

  • Main hypothesis (quote): "We hypothesize that Agent Context Files act as evolving governance artifacts in agent-enabled software development, and that their modifications are not arbitrary but systematically reflect developers' attempts to control and adapt agent behavior."
  • Data:
    • AIDev ("repositories (116,211) and pull requests (932,791)") plus the L2 dataset of "2,303 context files across 1,925 repositories".
    • Only Claude Code, Codex and Copilot (the agents that have these files).
    • Feasibility: "over 10,000 ACF-modifying commits"; a first pipeline "extracted 10,763 commit snapshots with context files, 18,213 commits with file metadata, and 8,600 commits with intersecting information".
    • Agent commits identified with the AIDev authors' procedure (author ids, commit message patterns, naming), which they call "a best-effort approximation".
    • Only the main repository-level files; skills and other instruction files are out of scope.
  • RQ1: "To what extent can changes to Agent Context Files be characterized according to classical software maintenance categories, and how are they distributed?"
    • Inductive coding of a representative sample of commits that change the file (commit message, diff, before and after versions). At least two annotators; Cohen's kappa of at least 0.70 required before going on.
    • Then map the categories to SWEBOK v4 maintenance types: corrective, preventive, adaptive (split into adaptive-correction and adaptive-enhancement), perfective, additive.
    • Remaining commits labelled by an LLM-as-judge, checked on a random sample.
    • Chi-square goodness-of-fit tests; post hoc tests with Holm-Bonferroni correction.
  • RQ2: "Do different types of Agent Context File changes exhibit differences in their association with code quality outcomes in subsequent code evolution?"
    • Window: all agent-generated commits between one change to the file (N) and the next (M) are linked to change N.
    • Outcomes: change in cyclomatic complexity, lines of code and coupling between each agent commit and its parent (following Trautsch et al.), averaged per window; and Corrective Commit Probability (CCP), the share of corrective commits in the window.
    • Kruskal-Wallis, then pairwise Wilcoxon rank-sum with Holm-Bonferroni, effect size with Cliff's delta.
  • RQ3: "Do different types of Agent Context File changes exhibit distinct temporal and frequency patterns throughout the development lifecycle?" Relative timing (by commit position and by time) and frequency (per 100 commits, per day).
  • Confounders: commit size, file size, repository size, activity level; programming language recorded, with language-stratified analysis where possible.

Key results

  • None yet. It is a Stage 1 plan. The numbers above are dataset sizes, not findings.

Limitations they state (Section IV)

  • Internal (quote): "A key threat is linking code quality outcomes to ACF changes, as ACFs contain heterogeneous instructions and modifications may affect only parts of the file, limiting causal interpretation. To mitigate this, we adopt a window-based design and control for confounders (commit size, ACF size, repository size, activity level), framing results as associations rather than causation."
  • Identifying agent commits "relies on heuristics".
  • "because ACFs govern heterogeneous aspects of development, some categories of modifications may have only indirect or limited influence on the selected quality measures, potentially reducing the strength of observable associations."
  • Construct: "Code quality is multifaceted, and our use of structural and process-level metrics captures only part of it."
  • External: public repositories may not represent industry; the analysis is "limited to agents for which both ACFs and agent-generated commits are available (Codex, Copilot, Claude)".
  • Future work: the report is itself the plan. It says the taxonomy will give "a theoretically grounded framework for future studies on governance artifacts in agentic settings", and practitioners will get guidance "on when and how to evolve ACFs".

How it relates to your proposal

  • You cite it: "A registered report by a team including Assoc. Prof. Kashiwa plans to relate changes in context files to code quality [9]." It is the closest lab-linked work to yours. Expect Kashiwa to ask about it.
  • What you can reuse: the window idea; their quality measures (complexity deltas, CCP); their statistics recipe (Kruskal-Wallis, Cliff's delta, Holm-Bonferroni); their change taxonomy, to label how a rule was edited.
  • What is different:
    • Unit: they study whole change events (one commit that edits the file, labelled corrective, additive and so on). You study one rule.
    • Design: they mine history and report associations. Your core study is a controlled experiment where only the rule changes, so a difference can be attributed to the rule.
    • Outcome: they measure the general quality of the agent commits that follow. You measure compliance with that specific rule, by script, plus tests, complexity and warnings.
    • Overlap risk: your supporting real-PR study is the part closest to theirs. Keep it narrow: specific checkable rule types, compliance with that rule, human PRs as a comparison.
  • Their own main threat (many instructions in one file, partial edits, limited causal interpretation) is exactly what a single-rule controlled experiment addresses. Say this politely, as "complementary", never as "better".

Careful (do not say)

  • Never say "Voria et al. found ...". There are no results.
  • Iida is not an author. Kashiwa is the only NAIST author.
  • Venue: ICSME 2026 Registered Reports (Stage 1); the Stage 2 paper goes to the EMSE journal.
