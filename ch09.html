3.1 Agent READMEs: An Empirical Study of Context Files for Agentic Coding (TOSEM 2026) [12]

  • Citation: W. Chatlatanagulchai, H. Li, Y. Kashiwa, B. Reid, K. Thonglek, P. Leelaprute, A. Rungsawang, B. Manaskasemsak, B. Adams, A. E. Hassan, H. Iida. ACM TOSEM, 2026. arXiv:2511.12884 (local L2 is v2). DOI 10.1145/3840295 (via Crossref, per GUIDE_1). Your reference [2].
  • Problem: what is in CLAUDE.md, AGENTS.md and copilot-instructions.md files, how they are maintained, and whether their content can be classified automatically.
  • Method: AIDev repositories with at least 5 stars (8,370): "922 Claude Code files, 694 OpenAI Codex files, and 687 GitHub Copilot files across 1,925 repositories". RQ1 size, readability and headers; RQ2 every commit that touches a file, plus 100 sampled commits; RQ3 grounded-theory coding of 332 files into 16 categories (agreement 80.3%); RQ4 a GPT-5 classifier.
  • Results:
    • Files changed in more than one commit: 59.4% (Codex) to 67.0% (Claude Code). Growth comes "mainly by small incremental additions".
    • Content (% of files): Testing 75.9, Implementation Details 70.8, Architecture 68.1, Development Process 65.1, Build and Run 63.0; Security 14.8, Performance 14.5.
    • GPT-5 classifier: micro F1 0.79.
    • Indentation case: in rsyslog (Claude Code), "208 violating lines out of 342 eligible added lines before the rule was introduced, a violation rate of 60.82%. Afterward, the rate dropped to 11.03% (939 of 8,516 lines)". In NB-Core/lotgd (Copilot), "from 20.17% (6,673 of 33,080 lines) before the rule to 7.57% (5,306 of 70,060 lines) afterward".
    • The paper also writes that its examples suggest "agents actively parse and stick to the project-specific rules provided by developers".
  • Limitations they state: "two cases cannot establish causality"; labels are binary; "the dataset remains limited". Future work: "context debt" and "agent context file smells", ablation of structure (headers), a linter for Build and Run commands, benchmarks for NFR adherence.
  • Why it matters to you: your real PR study scales up this indentation case, and your experiment tests the "stick to the rules" claim one rule at a time. Their 16 categories could describe which kinds of rules your results cover; this is not in your proposal, so treat it as an open question to her (section 7, Q3).

3.2 On the Use of Agentic Coding Manifests: An Empirical Study of Claude Code (PROFES 2025) [13]

  • Citation: W. Chatlatanagulchai, K. Thonglek, B. Reid, Y. Kashiwa, P. Leelaprute, A. Rungsawang, B. Manaskasemsak, H. Iida. PROFES 2025, Short Papers and Posters, LNCS pp. 543 to 551. DOI 10.1007/978-3-032-12089-2_40. arXiv:2509.14744 (local L1). Your reference [1].
  • Problem: how CLAUDE.md files are structured and what instructions they hold.
  • Method: GitHub API search for Claude.md files created 24 Feb to 16 Jun 2025 (838 files in 806 repositories); kept repositories with at least 20 commits after the file was added: "253 Claude.md files from 242 repositories". Headers counted; manual labelling into 15 labels (113 disagreements in 1,228 label assignments).
  • Results: shallow structure (median H1 1.0, H2 5.0, H3 9.0). Build and Run 77.1%, Implementation Details 71.9%, Architecture 64.8%, Testing 60.5%; Security 8.7%.
  • Limitations: the paper has no threats to validity section (I searched the text). Future work names "controlled experiments where agents are tasked with identical coding challenges, but with varying qualities or completeness of agentic coding manifests", with metrics such as "code quality (e.g., bug count, adherence to style guides)", and also "qualitative studies, such as developer interviews or surveys".
  • Why it matters to you: your core study is close to this "Impact" future work, and the same paragraph names developer interviews or surveys; she has run user studies and surveys [15, 16]. Do not raise this section yourself; if asked, use C48 (section 6a, Q11).

3.3 On the Use of Agentic Coding: An Empirical Study of Pull Requests on GitHub (TOSEM 2026) [14]

  • Citation: M. Watanabe, H. Li, Y. Kashiwa, B. Reid, H. Iida, A. E. Hassan. ACM TOSEM, 2026. DOI 10.1145/3798166 (researchmap). arXiv:2509.14745 (local L4 is v3). Not cited in your proposal.
  • Problem: how Claude Code pull requests differ from human ones, how often they are accepted, and what revisions they need.
  • Method: PRs whose description contains "Generated with Claude Code" (24 Feb to 30 Apr 2025), matched with human PRs by the same author in the same repository: 567 agent PRs and 567 human PRs in 157 repositories. Manual multi-label classification; chi-squared and log-rank tests.
  • Results: merged 83.8% (agent) vs 91.0% (human). 54.9% of merged agent PRs went in without revision. Of the 214 revised agent PRs: fix 47.7%, docs 29.0%, refactor 27.1%, style 23.4%. The paper recommends "a dedicated guideline file (e.g., CLAUDE.md, supported by Claude Code) that includes formatting rules, design principles, and architectural constraints".
  • Limitations they state: "relying on brittle text markers (like 'Generated with Claude Code') is insufficient"; excluding open PRs "creates a survival bias"; PR acceptance "does not account for long-term code quality or maintainability"; Claude Code only.
  • Why it matters to you: it supports your question: the paper tells developers to write conventions into CLAUDE.md, and you test whether agents then follow them and whether code quality changes.

3.4 NCQ: Code Reuse Support for Node.js Developers (IEEE TSE 2023) [15]

  • Citation: B. Reid, M. d'Amorim, M. Wagner, C. Treude. IEEE TSE 49(5): 3205 to 3225, 2023. DOI 10.1109/TSE.2023.3248113. arXiv:2101.00756 (her site's PDF is the arXiv v3 file). Presented in the ESEC/FSE 2023 Journal First track. [5, 7]
  • Problem: finding and trying npm packages is slow, and most README examples do not run.
  • Method:
    • Dataset: 2,161,911 code snippets from 620,221 npm READMEs; extraction checked on 384 READMEs by two authors (kappa 0.72).
    • Survey via Prolific: 680 responses, 55 passed all programming questions.
    • Study 1 (NCQRetrieval): 10 developers hired online, USD 40 each, about 1 hour. Baseline: the same tool with search turned off, plus the web. Five tasks from Stack Overflow questions, balanced assignment (each task done by 2 people per treatment). Recorded remote sessions, tool logs, Likert questions and 14 TAM questions.
    • Study 2 (full NCQ): 10 developers recruited and screened on Prolific. Baseline: VS Code plus web.
  • Results:
    • Study 1: 7 of 10 participants faster with the tool; median 748 s vs 936 s. Median time to the final package 133 s vs 250 s. All 10 agreed the tool was helpful, vs 60% for the baseline.
    • Study 2: 6 of 10 faster; median 847 s vs 849 s (almost equal). Median time to the final package 57 s vs 380 s. Six of ten agreed NCQ was helpful; two disagreed.
    • Code correction: 33% (27/81) of snippets participants retrieved had errors fixed; linting errors fell, but "we saw no reduction in runtime errors".
  • Limitations they state: order and familiarity (baseline first, then tool); the demo may have shaped tool use; remote sessions; "We cannot claim generalisability beyond Node.js"; "We cannot conclude that improvements in performance between baseline and tool were due to any specific techniques".
  • Why it matters to you: her template for a tool evaluation, and the model for your Year 2 checker study. In Study 2 the median task time was almost the same (847 s vs 849 s), but time to the final package was much shorter (57 s vs 380 s). The paper explains the lower ratings in Study 2 by more skilled, screened participants and a more familiar baseline, and concludes that NCQ "still performs well" against VS Code (Sec. 11). Do not tell her the gain disappeared.

3.5 Software Engineering User Study Recruitment on Prolific: An Experience Report (RoPES 2022) [16]

  • Citation: B. Reid, M. Wagner, M. d'Amorim, C. Treude. RoPES 2022 (workshop at ICSE 2022). arXiv:2201.05348.
  • Problem: many Prolific users who say they can program cannot.
  • Method: a screening survey (prescreening validation, programming questions adapted from Danilova et al., an attention check), then video sessions.
  • Results: 680 responses. 33% gave answers inconsistent with their prescreening; 206 said they program in Node.js; only 55 passed all questions. 14 booked a session, 10 succeeded, and 4 withdrew, for reasons including "anxiety programming under observation". Total cost GBP 193. "Only 12% of eligible participants ... and only 27% of participants who self-reported as programming in Node.js, met our criteria."
  • Recommendations: do not rely on self-reported skill; validate prescreeners; always pilot; state requirements clearly and show an example task.
  • Why it matters to you: if you evaluate the checker with developers, you need people who really maintain context files. Show her you know this risk.

3.6 Thesis Chapter 5: Copilot vs Stack Overflow (2023) [17]

  • Citation: B. Reid, "Improving Developer Efficiency through Code Reuse", PhD thesis, University of Adelaide, 2023, Ch. 5. https://hdl.handle.net/2440/139921. The chapter is based on "Copy-Paste vs. Code Generation: Contrasting Stack Overflow and GitHub Copilot" by Reid, Earl Barr, Wagner and Treude, "Being revised for submission to IEEE Transactions on Software Engineering" at the time. [UNVERIFIED] I found no published version on her site, Scholar or DBLP.
  • Problem: how LLM code completion (Copilot) compares with copy-paste from Stack Overflow, for output quality and for how queries are written.
  • Method: 2,628 queries (Java and Python) from Stack Overflow searches, LeetCode and HumanEval; snippets from Copilot and from Stack Overflow via Google; about 30,000 snippets released. Measures: count, diversity, length, comments, imports, errors, manual relevance, and query variants.
  • Results: Copilot gives at least one snippet in 99.81% of queries; Stack Overflow returns nothing in 11.83%. Syntax errors: Copilot 10.46% vs Stack Overflow 31.43%. Directly addresses the query: 59% vs 6%. In Ch. 6 she notes that "our prompt location impacted the types of snippets we could generate; no Java Copilot snippet included an import statement".
  • Why it matters to you: in Ch. 5 the place where Copilot was asked to complete code (inside a Java method) limited what it could produce: no Java Copilot snippet had an import. This is about where the model is invoked, not about where an instruction sits in a long prompt. Do not link it to BrandMemory. She also released her outputs because the Codex API was being discontinued, which supports your plan to keep every agent trace and diff.

3.7 Using the TypeScript compiler to fix erroneous Node.js snippets (SCAM 2023) [18]

  • Citation: B. Reid, C. Treude, M. Wagner. SCAM 2023, pp. 220 to 230. DOI 10.1109/SCAM59687.2023.00031. arXiv:2308.12079.
  • Problem: linters such as ESLint often report only one parse error and cannot fix much.
  • Method: Node Code Correction (NCC): TypeScript compiler errors, TypeScript codefixes, targeted fixes and line deletion, run on more than two million npm snippets, then compared with Stack Overflow edit pairs.
  • Results: "73.7% of the code snippets in NPM documentation have errors; with the use of NCC's corrections, this number was reduced to 25.1%." TypeScript reports 6.8 errors per snippet vs 1.3 for ESLint. Of 1,099 Stack Overflow snippets that developers fixed by hand, NCC could fix 66.06%.
  • Limitation: neither tool "can accurately represent the runnability of the code".
  • Why it matters to you: she knows the limits of static analysis as a proxy for quality. Expect a question on whether complexity and warnings really measure quality in RQ3 (C20).

3.8 Detecting and Characterizing Low and No Functionality Packages in the NPM Ecosystem (PROFES 2025) [19]

  • Citation: N. Tevarut, B. Reid (corresponding author), Y. Kashiwa, P. Leelaprute, A. Rungsawang, B. Manaskasemsak, H. Iida. PROFES 2025, pp. 552 to 560. arXiv:2510.04495.
  • Problem: trivial packages and "data-only" packages (no executable logic) may carry security risk.
  • Method: random sample of 3,281 npm packages (3,220 after filtering), metrics from cloc and typhonjs-escomplex, vulnerabilities from npm audit. A rule-based command-line detector. Evaluation on 250 random packages labelled by one researcher, with ambiguous cases cross-checked by two LLMs.
  • Results: 577 packages (17.92%) trivial; 40 data-only (1.24%). Trivial vs non-trivial vulnerabilities: Mann-Whitney p = 0.0000000013 but Cliff's delta -0.1091, "a negligible difference". Detector: "94% accuracy (macro-F1 0.87)" in the abstract, and "94% accuracy and 0.93 weighted F1" in the evaluation, with lower recall for data-only (0.67) "due to the small sample size".
  • Limitations they state: one labeller; rule-based heuristic; small number of data-only cases.
  • Why it matters to you: the closest thing to your rule checkers. Report per-rule precision and recall, not one accuracy number, and effect sizes next to p-values.

3.9 The SECURITY.md papers (SANER 2025, PROFES 2025, EMSE 2026) [20, 21, 22]

  • Citations:
    • S. Kancharoendee, T. Phichitphanphong, C. Jongyingyos, B. Reid, R. G. Kula, M. Choetkiertikul, C. Ragkhitwetsagul, T. Sunetnanta. "On Categorizing Open Source Software Security Vulnerability Reporting Mechanisms on GitHub." SANER 2025 (ERA). DOI 10.1109/SANER64311.2025.00076.
    • M. Choetkiertikul et al. (with Reid). "Security by documentation? characterizing GitHub SECURITY.md policy and their adoption in Python libraries." EMSE 31(3), 65, 2026. DOI 10.1007/s10664-025-10794-z. (abstract and method section read)
    • R. Kanaji, B. Reid, Y. Kashiwa, R. G. Kula, H. Iida. "An Empirical Study of Security-Policy Related Issues in Open Source Projects." PROFES 2025. DOI 10.1007/978-3-032-12089-2_43. arXiv:2510.05604.
  • Problem: does a policy file in the repository change how people report vulnerabilities, and is it linked to better security practice?
  • Method and results:
    • SANER 2025: 679 PyPI repositories, about 302 with a policy. RQ2 asks "Do the developer's practices align with the security policy?": issues dropped where private channels were defined, but "787 security-related issues were still reported through GitHub Issues across 58 repositories", mostly by external contributors. OpenSSF Scorecard aggregate 5.93 with a policy vs 3.95 without (p < 0.001).
    • EMSE 2026: same 679 libraries; "projects with security.md shows stronger recommended security practices". It also compares SonarQube code quality (bugs, vulnerabilities, smells) between the 303 projects with a policy and the 376 without, so it is an observational version of your RQ3 question. In its data description, projects with a policy "generally have higher counts of bugs and vulnerabilities but tend to have fewer code smells".
    • PROFES 2025: 711 sampled issues (521 relevant; Cohen's kappa 0.958). 79.5% were requests to add the file. Five issues asked how to report a vulnerability, "indicating confusion about the appropriate reporting channel". Conclusion: SECURITY.md "can also increase confusion and burden".
  • Limitations they state (PROFES): unobserved factors such as size and popularity; closed issues only.
  • Why it matters to you: the same shape as your study, for humans: a file tells people what to do; do they comply; is it linked to quality? Her group could only observe. With agents you can experiment.

3.10 Using LLMs for Security Advisory Investigations: How Far Are We? (SIML 2025, Student Best Paper) [23]

  • Citation: B. F. Abdullah, Y. S. Nugroho, B. Reid, R. G. Kula, K. Shimari, K. Matsumoto. SIML 2025. DOI 10.1109/SIML65326.2025.11080876. arXiv:2506.13161. Student Best Paper Award. [1, 6]
  • Method: 100 real and 100 fake CVE IDs given to ChatGPT; manual labelling of the generated advisories.
  • Results: plausible advisories for 96% of real and 97% of fake IDs; when an advisory was fed back, the model gave a fake CVE ID in 6% of cases from real advisories. The authors note responses were "highly sensitive to the phrasing of prompts".
  • Why it matters to you: another of her papers where wording changed LLM output. Your RQ2 tests wording under control.

3.11 Evaluating Cross-Language Transfer for Refactoring Detection with Large Language Models (SANER 2026 ERA) [25]

  • Citation: S. Liu, N. Suwanachote, Y. Kashiwa, B. Reid, H. Iida. SANER 2026, pp. 216 to 221. Abstract only; no full text found.
  • Result (abstract): Java examples used to detect refactorings in Python beat zero-shot prompting ("Avg. F1 0.501 vs. 0.430") and "nearly matches" native Python few-shot prompting (0.506).
  • Why it matters to you: LLMs as research instruments, scored against labels. If she asks why you use scripts, not LLMs, to check compliance, this is the contrast.

6. Questions she could ask you, with short model answers

6a. About your proposal

Q1. Our Agent READMEs paper already showed fewer indentation violations after the rule was added. What does your experiment add? (C49)

Your check is the closest real evidence to my question. In rsyslog the violation rate fell from 60.82% to 11.03%, but the paper says two cases cannot establish causality. In my experiment the task, the agent version and the rest of the file stay the same, and only the rule changes. I also want to repeat your before and after check on more repositories, with human pull requests as a comparison.

Q2. How do you know your rule checkers are correct? (C19)

Before any agent run, I check each script by hand on at least 20 real examples and report how often it matches my count. If I find errors, I fix the script and check more. I would report precision and recall for each checker, as your npm detector paper reported per-class results. If a checker stays unreliable, I drop that rule.

Q3. What share of real rules can a script check? Isn't that a small and easy subset? (C12)

I do not know the share yet. Counting it is one of the first steps of the pilot, and I will report it. My results will speak only for script-checkable rules, not for design or process rules.

Q4. How will you find repositories and tasks? Will there be enough pull requests whose tests fail before and pass after? (C13, C14, C36)

I start from Python repositories in AIDev that have a CLAUDE.md or AGENTS.md and tests that run in a container. A task is a merged pull request whose own tests fail before and pass after it. I do not know yet how many exist, so the pilot on two repositories counts them first.

Q5. Why only Python? Would rules work the same in npm projects? (C57)

Python has good tools for my measures, such as pytest, radon and ruff, and the Gloaguen benchmark is also Python, so I can compare cost and setup. I would not claim anything for other ecosystems. JavaScript projects often have ESLint configs, so the linter variable might behave differently there; that would be a good next study.

Q6. How will you evaluate the Year 2 checker with developers? How many, and how will you recruit them? (C55)

A small first study: developers look at each warning and say whether it is correct and whether it is useful. I would like to recruit maintainers of the repositories I study, because they know their own file, and screen them as your Prolific report suggests, not by self-report. I do not know the right size yet, and I would really value your advice on it.

Q7. What would you compare the checker against?

I am not sure yet. One option is to compare the new RQ2-based warnings with the reused Santos et al. detectors alone, on the same files, with developers rating warnings without knowing which part produced them. In your second NCQ study you compared the tool with VS Code plus web search, a tool developers already use. That is the kind of baseline I would want.

Q8. In the real PR study, how do you tell agent work from human work? (C35)

AIDev labels each pull request by the agent that opened it, so I work at the pull request level. Commits inside a pull request may still be human, and your PR paper warns that text markers like "Generated with Claude Code" are brittle. So I state this as a threat and keep the main claims for the experiment.

Q9. Why not use an LLM to judge compliance, as Agent READMEs used GPT-5 to classify content? (E11)

For classifying content at scale, an LLM made sense, and your paper reports its F1 of 0.79. For compliance I need a measure that gives the same answer every time and that anyone can rerun on my saved diffs. A script does that for checkable rules. I could still use an LLM to help find candidate rules in files, with a human check.

Q10. Three runs per version and about 30 rules. Will a significant result mean anything? (C25, C26)

The main test pools all rules, with task and rule as random effects, so it does not rest on three runs of one rule. For single rules I would report the size of the change with an interval and correct for testing many rules. Your npm paper shows why: a tiny p-value with a negligible Cliff's delta. The pilot sets the number of runs.

Q11. Isn't this just the future work of our Manifests paper? (C48)

I read that section, and I was glad to see it. I came to this question from my own work, where some rules had no effect. My plan is narrower: I test single real rules, one at a time, on real tasks from the same repositories, and I measure with scripts both whether agents follow each rule and how the code quality changes.

6b. About her work

Q12. What did you think of Agent READMEs? Is there anything you would do differently? (E6, E7)

The finding I use most is that files grow through small additions and are rarely cleaned up, because it means developers keep adding rules without knowing which ones work. The indentation case was the most useful part for me. The paper also says the examples suggest agents stick to the rules; I would like to test that one rule at a time. I would not call that a disagreement, more the next step.

Q13. Which of our categories would your rules fall into?

I expect most in Implementation Details, like naming, style and logging rules, and in Testing, like where new tests go. Build and Run instructions are mostly commands, which I cannot check in the code. I could label each rule with your categories, so it is clear which kinds of rules my results cover.

Q14. What did you learn from our pull request paper? (C51)

That 45.1% of merged Claude Code pull requests were revised, and among those, style changes were in 23.4% and refactoring in 27.1%. The paper reads this as agents missing local conventions and recommends a CLAUDE.md with formatting rules and design principles. My question starts there: if developers write those rules down, do agents follow them?

Q15. What would you take from NCQ for your own tool study?

Three things. Compare with a tool developers already use, as your second study did with VS Code. Log what participants do, not only what they say. And screen participants for real skill, as your Prolific report showed.

Q16. What did you take from the Prolific report?

Not to trust self-reported skill: only 27% of people who said they program in Node.js passed your checks. Pilot the recruitment, and show an example task. For my study, I would screen for people who really maintain a context file, for example by asking for one rule from their own file.

Say the Prolific report answers (the last sentence of Q15 and all of Q16) only after you have read the report. It is not on your reading list yet (question bank B22).

I see the same shape. A file tells people what to do, and the question is whether they comply. The PROFES paper with Kanaji also found a few issues where people were unsure which reporting channel to use. For agents I can do what is hard with people: change the file and rerun the same task.

Agent READMEs lists context debt and context file smells as future work. My Year 2 checker is one small step there, based on what agents actually ignore. Later, the same experiment could cover copilot-instructions.md, which your paper also studied.

Yes. Besides the context file papers, I read NCQ most carefully, because I want to evaluate a tool with developers.
