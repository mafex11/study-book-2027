L5. Agentic Refactoring: An Empirical Study of AI Coding Agents

  • Authors: Kosei Horikawa (PhD student), Hao Li (Queen's), Yutaro Kashiwa (Assoc. Prof.), Bram Adams (Queen's), Hajimu Iida (Prof.), Ahmed E. Hassan (Queen's)
  • Venue: ACM TOSEM, accepted according to the lab site. The arXiv comment says "Submitted to ACM Transactions on Software Engineering and Methodology (TOSEM)". Kosei Horikawa's SD lab profile (https://sdlab.naist.jp/en/authors/kosei-horikawa/, checked 21 Oct 2026) lists it as "ACM Transactions on Software Engineering and Methodology (TOSEM), 2026. Just Accepted." No DOI or volume exists yet. Say "accepted at TOSEM, according to the lab site".
  • arXiv: 2511.04824 (v1, 6 Nov 2025). Replication package: https://github.com/Mont9165/Agent_Refactoring_Analysis

One breath summary

This is the first large study of refactoring by coding agents in real Java projects. Agents refactor often, mostly with small local edits like renames and type changes, and they say they do it for maintainability. The measured quality gains are small, and design smells do not really go down.

What they did

  • Data. They started from AIDev and used the GitHub REST API to mine all commits of the agent PRs (1,311,057 agentic commits).
  • Java only. They kept non-merge commits that change at least one .java file, so they could use mature Java tools.
  • Dropping toy projects. GPT-4.1-mini labelled each repo from its README as production grade, specialized, toy or uncertain. They checked every "toy" label by hand and found 7 wrong. After removing forks, they had 1,613 projects, 14,998 commits and 12,256 PRs.
  • Finding refactorings. They used RefactoringMiner 3.0.11, which knows 103 refactoring types.
  • Defining an "agentic refactoring commit". RefactoringMiner must find at least one refactoring, AND the commit message must match a self-affirmed refactoring pattern. There are 87 patterns, taken from AlOmar et al., such as "refactor", "cleanup" and "renam".
  • RQ2, levels. They grouped the 103 types into three levels and compared them with human data from earlier work:
    • high level: 58 types that change only signatures;
    • medium level: 21 types that change signatures and bodies;
    • low level: 24 types that change only bodies.
  • RQ3, purpose. GPT-4.1-mini put each refactoring commit into one of Kim et al.'s purpose categories. They checked these labels against human labels.
  • RQ4, quality. They ran DesigniteJava before and after each commit:
    • metrics: LOC, cyclomatic complexity, WMC, fan-in, fan-out, LCOM and DIT, plus 27 design and implementation smells;
    • tests: Wilcoxon signed-rank with Benjamini-Hochberg FDR correction, effect sizes, and Kruskal-Wallis across groups.

Key results (exact numbers)

  • Dataset size: 15,451 refactoring instances in 14,998 commits, 12,256 PRs and 1,613 repos. The arXiv abstract page says 14,988 commits, but the PDF says 14,998 throughout, so use the PDF number.
  • Which agents:
    • Codex made 89.3% of the commits (94.3% of PRs).
    • Devin made 5.7% and Cursor 4.4%.
    • Claude Code made only 0.6% (86 commits, 27 PRs).
    • The text once gives Cursor as 2.8%. That is its share of PRs, not commits.
  • Merge rate: 86.9% of the PRs were merged.
  • RQ1, how common:
    • 26.1% of commits (3,907 of 14,998) are agentic refactoring commits. They hold 7,127 refactoring instances (46.1%).
    • The other 8,324 instances (53.9%) are in commits whose messages do not say "refactor". These are tangled commits.
    • Commits that state refactoring contain more refactorings each (Mann-Whitney p ≤ 0.001, Cliff's d = 0.838, large).
  • RQ2, levels (agent vs human):
    • high level: 43.0% vs 54.9%;
    • medium level: 21.2% vs 20.7%;
    • low level: 35.8% vs 24.4%.
    • The top agent types are Change Variable Type 11.8%, Rename Parameter 10.4% and Rename Variable 8.5% (30.7% together).
  • RQ3, purpose (agent vs human):
    • maintainability 52.5% vs 11.7%;
    • readability 28.1% vs 25.7%;
    • duplication 1.1% vs 13.7%;
    • repurpose or reuse 4.6% vs 12.9%;
    • testability 5.2% vs 10.0%.
    • Label checks: kappa between the two humans was 0.83; kappa between GPT-4.1-mini and the humans was 0.77.
  • RQ4, quality:
    • Smells. The median change is 0.00. Design smells were 77.50 before and after; implementation smells went from 355.50 to 356.00. Effect sizes are negligible (Cohen's d = -0.027 and -0.026).
    • The paper contradicts itself on smells. Finding 8 says the change is "statistically significant but negligible", but the RQ4 summary box says smells "do not show FDR-significant reductions". The safe line is "no practical reduction in smells".
    • Medium-level refactorings: Class LOC median change -15.25, WMC -2.07, method LOC -1.79.
    • Low-level refactorings: method LOC -0.42, but method cyclomatic complexity +0.08.
    • Single types: Extract Subclass gave Class LOC -87.5 and WMC -11.5. Split Class gave Class LOC -16.0 and WMC -4.0.

Stated limitations and future work

  • Internal validity: RefactoringMiner and DesigniteJava make false positives and negatives, and the GPT-4.1-mini labels are not perfect (kappa 0.77).
  • Construct validity: agentic commits are found from keywords and author information. The authors cannot tell how much a human edited before committing, so they call the study "human-AI collaborative refactoring".
  • External validity: open-source only, and Java only.
  • Future work (Section 5):
    • Measure the review cost of implicit refactoring through "review comments, merge latency, and revert rates".
    • Build benchmarks for high-level refactoring.
    • "study the disconnect between agentic refactoring and measured quality outcomes".
    • Run longitudinal studies of "defect density, post-release defects, and effort for future modifications".
    • For tool builders: keep refactoring separate from feature work ("commit hygiene"), and give agents smell detectors such as DesigniteJava, for example through MCP.

Relation to your proposal

  • It is the lab's template for measuring quality before and after an agent change: tool metrics, paired non-parametric tests, FDR correction and effect sizes.
    • Your RQ3 uses the same kind of measures (complexity, static analysis warnings).
    • Lesson: with many data points, many results come out "significant" but negligible. Always report effect sizes.
  • Agents change code beyond the task (tangled changes). In your experiment, this extra change could move complexity and warnings.
    • You compare file versions on the same task, so the task itself is held fixed.
    • You can also report diff size.
  • "Do not refactor unrelated code" is one of the negative rules whose removal lowered the pass rate in Guardrails [6].
    • If you can check it with a script, this paper is a good reason to include it. One example check: lines changed outside the files the reference PR touched.
    • Decision: it could be one of my 30, if a small script can check it. I will decide after the pilot.
  • The agent mix in AIDev is very uneven (Claude Code made 0.6% of commits here). For your real-PR study, count agent PRs per agent early. Your plan already starts with this "count first" step.
  • Same construct problem as your real-PR study: it is not always clear who wrote a commit.

Likely questions

Q: What did our refactoring paper find, and what does it mean for your RQ3? A: Agents refactor a lot. 26.1% of the Java commits clearly target refactoring, but most edits are low level, like renames and type changes. The gains are small. Class size and WMC drop for medium-level changes, but smells do not really go down. I take two lessons. First, I will report effect sizes, because with a large sample even tiny changes come out significant. Second, agents change code outside the task. 53.9% of the refactorings were in commits that did not say refactor. In my design, both file versions run the same task, so this extra change shows up in both arms. I will also report diff size.

Q: AIDev is mostly Codex. Is that a problem for your real-PR study? A: Yes, it can be. In your paper Codex made 89.3% of the commits and Claude Code only 0.6%. So my first step is to count, for each agent, how many repositories have enough agent PRs before and after a rule was added. If Claude Code has too few, I report the real-PR part for Codex only. The controlled experiment still covers both agents, because I run them myself.

L6. What to Cut? Predicting Unnecessary Methods in Agentic Code Generation

  • Authors: Kan Watanabe (master's student), Tatsuya Shirai (PhD student), Yutaro Kashiwa, Hajimu Iida. All four are SD lab members.
  • Venue: MSR 2026 Mining Challenge (Rio de Janeiro, April 2026), 5 pages, DOI 10.1145/3793302.3793591. It won the Distinguished Mining Challenge Paper Award; the lab news post says 3 of 116 submissions won.
  • arXiv: 2602.17091 (19 Feb 2026). Replication package: https://github.com/kan0803/predict-deletion-method

One breath summary

Some methods that agents add in a pull request are deleted before merge, and the deleted ones are longer and have longer names. A Random Forest on 23 simple features ranks them well (AUC 0.871, far above GPT-4o), but its precision is very low.

What they did

  • Data. They took agent PRs from AIDev (the paper describes AIDev as 33,596 PRs by five agents) and kept merged PRs that change Python code: 1,664 PRs from 197 projects.
  • Snapshots. For each PR they took three snapshots: base, PR creation and merge. They listed every method with Python's ast module.
    • "Added" = present at PR creation but not in the base.
    • "Deleted" = added, but gone at merge.
  • Renames and moves. They ran ActRef, a Python refactoring detector with a reported 78% precision and 91% recall, on every pair of consecutive revisions. This way a renamed or moved method is not counted as deleted.
  • 23 features in three groups:
    • size: lines, characters, tokens, docstring words, words in the method name;
    • method type: getter, setter, test, private, dunder, has a return value;
    • contents: parameters, variables, calls, prints, comment ratio, radon cyclomatic complexity, Halstead volume, nesting depth, try-except, constants.
  • RQ1: Mann-Whitney U test and Cliff's delta.
  • RQ2: Random Forest with undersampling and 10-fold cross-validation. They compared it with random guessing and with GPT-4o, which was asked to predict "deleted" or "survived".

Key results (exact numbers)

  • How many are deleted:
    • 12,343 methods were added at PR creation. 97.4% survived and 2.6% (323) were deleted: 1.0% because the whole file was deleted, 1.6% on their own.
    • 75.6% of PRs had no revisions at all.
    • In the 397 PRs that had revisions (3,257 methods), 9.9% were deleted: 6.0% at method level and 3.9% at file level.
    • The paper: "the following analysis, including RQ2, excludes file-level deletions". So the feature comparison and the prediction model use the 1.6% method-level deletions as the positive class. The random baseline's precision of 0.015 matches that rate.
  • What deleted methods look like: 18 of the 23 features differ significantly. The largest effect sizes are words in the method name (delta 0.44), character length (0.40) and lines of code (0.30). Deleted methods are longer and have longer names.
  • Prediction (Table 2):

AUC 0.500 0.621 0.871
Accuracy 0.498 0.836 0.735
Precision 0.015 0.002 0.049
Recall 0.475 0.026 0.825
F1 0.029 0.004 0.092
  • Most important features: method_name_words 0.16, char_length 0.14, tokens 0.09. Method type features such as getter or private were weak.
  • The GPT-4o example: GPT-4o praised one method for its type hints and clean style, but that method was deleted. The authors write: "LLMs conflate local code quality with system-level necessity."
  • Small inconsistency: the text gives the standard deviation of method_name_words importance as 0.009, but Table 3 says 0.015.

Stated limitations and future work

  • Internal validity: ActRef can mislabel methods, which adds noise to the labels.
  • Construct validity:
    • Only deletions between PR creation and merge count, so later deletions are missed.
    • A deletion does not always mean the code was bad. Requirements change, designs change, and code gets merged with existing code.
    • The features may miss the real reasons for a deletion.
  • External validity: Python only, and some features (dunder methods) are Python-specific.
  • Future work: add measures of redundancy against the existing code base, "semantic similarity with other methods and duplicate functionality detection".

Relation to your proposal

  • It shows a second cost of agent code: extra code that reviewers have to read and then delete. This sits next to your RQ3 (quality of agent code).
  • It supports script checks over an LLM judge. GPT-4o judged local style rather than what the project needed, and its recall was 0.026. This backs your choice to check compliance with scripts. Cai et al. [12] used an LLM judge.
  • Its method tracking is close to what your checkers need. Tracking methods with ast across snapshots is the same job your rule checkers do: find the new code in the agent's diff and check only the "applicable places".
  • Lesson for your Year 2 checker: when the base rate is low, a good AUC can hide a tool nobody can use. Report precision, and ask developers whether each warning is correct and useful, as your plan already says.

Likely questions

Q: This paper reached AUC 87.1%. Is that a good model? A: It ranks well, but precision is 0.049. So only about 1 in 20 flags is a real deletion. The base rate is very low. Only 2.6% of added methods were deleted overall, and the model predicts only the 1.6% deleted at method level, because file-level deletions are excluded. For a reviewer tool I would also want precision in the top few flags, or the review time saved. I take the same lesson for my checker. I will report precision, and I will ask developers whether each warning is right and useful.

Q: GPT-4o did badly here. What does that mean for your study? A: GPT-4o looked at local style, like type hints and naming, and said the method was fine. It could not see whether the project needed it. My compliance check is about concrete things in the code, like where a test file goes. A script is more reliable and cheaper for that. I also check each script by hand on at least 20 examples. So I avoid an LLM judge for compliance.

L7. Do AI Agents Really Improve Code Readability?

  • Authors: Kyogo Horikawa (National Institute of Technology, Nara College; not on the SD lab member list), Kosei Horikawa (PhD student), Yutaro Kashiwa, Hidetake Uwano (NIT Nara College), Hajimu Iida
  • Venue: MSR 2026 Mining Challenge, 5 pages, DOI 10.1145/3793302.3793590
  • arXiv: 2603.13723 (14 Mar 2026)

One breath summary

Agent commits that say they improve readability are rare, about 0.3% of all agent commits. They mostly target complex logic and documentation. By standard metrics, they usually make code bigger and lower the Maintainability Index.

What they did

  • Data. AIDev plus the GitHub REST API gave 1,382,314 agent commits.
  • Keyword filter. They searched commit messages (ignoring case) for 8 keywords: "readability", "readable", "understandability", "understandable", "clarity", "legibility", "easier to read" and "comprehensible". This gave 4,115 commits.
  • Python filter. They kept commits that change at least one Python file: 577.
  • RQ2. They took a random sample of 231 commits (95% confidence, 5% margin of error). Two authors sorted each commit into the 8 readability smells of Oliveira et al. (closed card sort, more than one label allowed). A third person settled disagreements.
  • RQ3. 403 of the 577 commits had code that parsed before and after the change.
    • They computed radon metrics: Maintainability Index (MI), cyclomatic complexity (CC), LOC, LLOC, SLOC, comment lines, and Halstead volume, difficulty and effort.
    • They used the Wilcoxon signed-rank test (p < 0.01) and Cliff's delta.

Key results (exact numbers)

  • RQ1, how common: 4,115 commits, about 0.3% of all agent commits. "readability" appears in 50.1% of them and "clarity" in 48.7%.
  • RQ2, what agents fix (agent vs human, human data from Oliveira et al.):
    • complex, long or inadequate logic: 42.4% vs 18.2%;
    • incomplete or inadequate code documentation: 24.2% vs 22.3%;
    • bad identifier: 14.3% vs 20.3%;
    • inconsistent formatting: 14.3% vs 10.9%;
    • inadequate logging: 12.6% vs 4.7%;
    • unnecessary code: 10.0% vs 13.2%.
    • Agreement: 94.7% at label level, micro kappa 0.80 (98 of 1,832 labels disagreed).
  • RQ3, what happens to the metrics (Table 3):
    • LOC: mean +27.61, median +6.00, effect size 0.64;
    • SLOC: median +2.60, effect size 0.60;
    • CC: mean +3.13, median 0.00, effect size 0.63;
    • MI: mean -3.25, median -0.12, effect size -0.35.
    • MI fell in 56.1% of commits and LOC rose in 71.5%. CC rose in 42.7% of commits, stayed the same in nearly half, and improved in only 9.7%.
  • Two things to know about these results:
    • The Wilcoxon test drops pairs with zero difference, so a metric can be "significant" even when its median change is 0.
    • The conclusion says "403 readability-related PRs", but they are commits.

Stated limitations and future work

  • Internal validity: manual classification is subjective.
  • Construct validity:
    • Commits can be tangled, so some metric changes may come from other edits.
    • MI and CC "may not fully capture all aspects of readability, such as clarity of intent and logical flow".
  • External validity: the sample is small (0.3%) and Python only. Future work should cover "additional languages and broader keyword sets".
  • Future research:
    • Build "readability-focused agents that incorporate qualitative evaluations and consider long-term maintainability".
    • Tool builders should add "quality-checking agents" that watch Halstead metrics and LOC and reject refactorings that make code harder to understand.
    • Verification should go "beyond functional correctness".

Relation to your proposal

  • It is the lab paper closest to your RQ3 measures: Python, radon and cyclomatic complexity.
  • Main lesson: a metric can move against what the agent meant to do. Adding docs or splitting code adds lines, and then MI falls. So:
    • Report each metric on its own, not one combined score. Your plan uses cyclomatic complexity and warnings, not MI, which is good.
    • Watch for rules that push a metric just by being followed. A rule like "write a docstring for every function" adds lines, so for that rule, size metrics partly measure the rule itself. Handle this the same way your plan handles lint checks that encode the rule: drop them.
  • Keyword search over commits is fragile and gives small samples. Your real-PR study will face the same problem when it looks for the commits where rules were added.
  • Their call to go "beyond functional correctness" matches your RQ3, which looks past test pass rates.

Likely questions

Q: In our readability paper, MI got worse even when agents tried to improve readability. How will you read your quality metrics? A: That paper taught me a metric can move against what the agent meant to do. Adding comments or splitting code adds lines, and then MI goes down. So I will report each metric on its own, mainly cyclomatic complexity and static analysis warnings, not one combined score. Some rules add lines by themselves, like "write a docstring for every function". For those rules, I treat size metrics as partly measuring the rule, the same way I drop lint checks that encode the rule. I also compare file versions on the same task, so the task stays the same.

Q: Metrics miss clarity of intent. Will you use human judgment? A: The paper says MI and CC miss clarity of intent, and I agree. A full human study is too big for my two years, so I do not promise one, and I will state clearly that my metrics do not measure clarity of intent. The human judgment in my plan comes in Year 2, when I ask a few developers whether each warning of my checker is correct and useful.

L8. Testing with AI Agents: An Empirical Study of Test Generation Frequency, Quality, and Coverage

  • Authors: Suzuka Yoshimoto (master's student), Shun Fujita (listed as an SD lab alumnus, master's course), Kosei Horikawa (PhD student), Daniel Feitosa (University of Groningen), Yutaro Kashiwa, Hajimu Iida
  • Venue: MSR 2026 Mining Challenge, DOI 10.1145/3793302.3793620
  • arXiv: 2603.13724 (14 Mar 2026). Replication package: https://github.com/suu-y/AI-human-test-comparison

One breath summary

In 10 TypeScript projects where agents add many tests, agents wrote 16.4% of the commits that add tests. Their tests are slightly longer, with more assertions and simpler logic. In the 3 projects where coverage could be measured, their coverage gains were about as good as the humans'.

What they did

  • Language and framework. They chose TypeScript (22.4% of agent PRs in AIDev) and the vitest framework (179 projects, 44.8% of the 400 TypeScript projects with a detectable test framework).
  • Projects. They picked the 10 vitest projects with the most test additions by AI. The reason for keeping it small: measuring coverage needs manual setup for each repo.
  • Commits. They took commits from each repo's AIDev activity window through the GitHub API, excluding merge commits and keeping those that touch test files. A "test addition commit" must add new test(, it(, describe( or similar lines.
  • Authorship. They used the committer name, then the AST plus git blame. A commit counts as AI only if every line of every added test method was written by an agent.
  • RQ2. On the latest release they measured, for each test method:
    • effective LOC;
    • number of assertions (expect());
    • cyclomatic complexity (from the Babel AST).
    • They compared AI and human tests with the Mann-Whitney U test, and plotted CodeBERT embeddings with t-SNE.
  • RQ3. They measured statement and branch coverage at the parent commit and at the test-adding commit.

Key results (exact numbers)

  • RQ1, how many test commits are AI: of 2,232 test-adding commits in the 10 projects, 16.4% were by AI (366, from Table 1).
    • Large projects: cal.com 14.4% (129 of 894), azure-sdk-for-js 1.9% (7 of 366).
    • Agent-heavy projects: total-typescript-monorepo 100% (26 of 26), capgo 83.3%, alchemy 71.1%.
    • Their summary: "up to 100% in agent-heavy projects, but typically 10% to 15%".
  • RQ2, what the tests look like (9 projects; one was dropped because humans had removed or changed its AI tests):
    • Effective LOC: median 12.0 (AI) vs 11.0 (human), p < 0.001 but a negligible effect (Cliff's delta -0.12). The longest test was 87 lines (AI) vs 699 (human).
    • Assertions: median 2.00 (AI) vs 1.00 (human), p < 0.001. The authors warn about the "Assertion Roulette" test smell.
    • Cyclomatic complexity: median 1.00 for both; mean 1.09 (AI) vs 1.31 (human). Significant in only 2 of 9 projects.
  • RQ3, coverage (only 3 projects, 531 commits):
    • liam: AI (N = 18) statement +0.072, branch +0.074; human (N = 143) -0.090 and -0.142.
    • appkit: AI (N = 28) +0.030 and +0.183; human (N = 221) -0.001 and +0.008.
    • helper: AI (N = 13) 0.000 and +0.006; human (N = 108) 0.000 and +0.213.

    • The paper gives these values in "pts". The changes are very small.

Stated limitations and future work

  • No threats section. The paper has no separate threats section, but it states these limits in the method:

Relation to your proposal

  • You can reuse its authorship method. Committer name plus git blame can separate agent code from human code in your real-PR study.

L10. AgentLogs: A Dataset for Opening the Black Box of GitHub's Cloud Agent

  • Authors: Jonan Richards (Radboud University), Kosei Horikawa (PhD student), Youmei Fan (NAIST; not on the SD lab member list), Yutaro Kashiwa, Mairieli Wessel (Radboud University)
  • Venue: not stated in the PDF or on arXiv. It is a short IEEE-style dataset paper. Do not name a venue.
  • arXiv: 2608.29204 (29 Aug 2026). Data: https://huggingface.co/datasets/risenlab/agentlogs (v0.2). Code: https://github.com/risenlab/agentlogs

One breath summary

A public dataset of the full step-by-step logs of GitHub's Copilot cloud agent: 307,416 tasks, 549,239 sessions and about 64 million log entries. It shows not only what agents produce but how they work: prompts, reasoning, tool calls and token use.

What they did

  • Repos. They started from SEART GitHub Search: 1,812,362 public repos with over 10 stars (accessed 10 July 2026).
  • Collection.
    • They used the GitHub REST API to get agent task IDs.
    • They then used undocumented GitHub Copilot API endpoints to get task and session metadata and the full session logs.
    • They argue that GitHub's Acceptable Use Policies allow this, and they kept within the rate limits.
    • They collected the data between 10 and 17 July 2026.
    • This version does not fetch metadata for linked PRs, branches or workflow runs.
  • Release.
    • Parquet tables: repositories, agent_tasks, agent_sessions, agent_session_logs and users.
    • Example scripts for DuckDB, Polars and streaming, and a PyPI package, risenlab-agentlogs.
    • Licences: MIT for the code, CC BY 4.0 for the data.

Key results (exact numbers)

  • Coverage: of 1,812,362 repos scanned, 35,810 (1.98%) have agent tasks.
  • Size:
    • 307,416 tasks;
    • 549,239 sessions;
    • 64,255,174 log entries (56.0 GB);
    • 33,573 users;
    • in total, 66,957,764 records and 56.7 GB.
  • Models: tasks can use repository-defined custom agents, or third-party models such as Claude and Codex on the Copilot platform.
  • Example log: claude-sonnet-4.6 answers a review comment. The log records token use, including cached tokens: in one step, 33,268 of 33,750 prompt tokens were cached.

Stated limitations and future work

  • No limitations section. The scope limits it states:
    • one platform (the Copilot cloud agent);
    • repos with over 10 stars only;
    • no linked PR or CI metadata yet.
    • Also, the data comes from undocumented endpoints.
  • Suggested research questions:
    • 1a. What workflow patterns (explore, edit, test) do agents follow, by task type?
    • 1b. "How do agents make use of repository provided context (e.g., custom instructions and skills), and is such context associated with different behavior and outcomes?"
    • 2a. How do agents respond to reviewer feedback?
    • 2b. How does developer usage change over time?
    • 3a. What characterizes the 1.98% of repos that adopt agents?
    • 3b. How do the models compare, and how has usage grown?

Relation to your proposal

  • Their question 1b is your question, seen from logs. AIDev shows outcomes (PRs). AgentLogs shows the process: whether the agent saw the instructions, and what it did next.
  • Rules that name a command can be checked in tool calls. This is your "specificity" property. If a rule says to run a certain test command, you can search the session log for that command. This links to the Skill Evolution finding [11]: adding a checkable rule helped mainly when the rule names a command or path.
  • Design idea for your own runs. Save the full agent trace for every run (Claude Code and Codex can both output JSON). Then you can see when the agent read the context file and where it broke the rule.
  • Your own experience fits. You have read Claude Code and Codex session logs yourself while building a small tool. And Yuki 2.0 logs every model call, tool call and result as JSONL, which is the kind of trace you plan to save.
  • Caution. This dataset is about Copilot, not Claude Code or the Codex CLI, and Copilot reads its own instruction files. Check which files before claiming any overlap. Checked: per the GitHub changelog of 28 Aug 2025, the Copilot coding agent reads AGENTS.md (root and nested), .github/copilot-instructions.md and .github/instructions/**/*.instructions.md, and also CLAUDE.md and GEMINI.md (https://github.blog/changelog/2025-08-28-copilot-coding-agent-now-supports-agents-md-custom-instructions). So AGENTS.md and CLAUDE.md files can also guide Copilot, but Copilot reads its own files too.

Likely questions

Q: How could you use AgentLogs in your work? A: In two ways. First, as a real-world check. Their question 1b asks how agents use repository context. I could take sessions in repos that have instruction files, and check whether the tool calls follow rules that name a command, like a test command. Second, as a model for my own logging. I will save the full trace of each run, with every tool call and token count. Then I can see whether the agent read the file and where it broke a rule. I have done similar logging before. Q: What are the limits of this dataset? A: It covers one platform, Copilot's cloud agent, and the logs come from undocumented endpoints, so the format may change. It shows process, not code quality. To study quality you have to join it with PR data, and this version does not fetch PRs. L11. Agentic Software Engineering: Foundational Pillars and a Research Roadmap (SASE)

  • Authors: Ahmed E. Hassan, Hao Li, Dayi Lin, Bram Adams (all Queen's University), Tse-Hsun Chen (Concordia), Yutaro Kashiwa (NAIST), Dong Qiu (Huawei Canada)
  • Venue: the PDF says "Manuscript submitted to ACM". The venue is not verified.
  • arXiv: 2509.06216 (v1 7 Sep 2025, v3 24 Jun 2026)

One breath summary

A vision paper with no new data. It argues that software engineering must split into "SE for Humans" and "SE for Agents". It proposes a command center for human "agent coaches" (ACE), a workbench for agents (AEE), and version-controlled artifacts such as BriefingScript, LoopScript and MentorScript. It names CLAUDE.md and AGENT.md as an early, grassroots form of MentorScript.

What they did

  • Autonomy levels, like the levels for self-driving cars:
    • Level 0: manual coding;
    • Level 1: token assistance;
    • Level 2: task-agentic (Copilot);
    • Level 3: goal-agentic (Claude Code, Codex, Devin, Jules);
    • Level 4: specialized domain autonomy;
    • Level 5: general domain autonomy.
  • Agency vs autonomy. Agency means carrying out a given plan. Autonomy means making the plan.
  • Evidence review. They reviewed evidence that "passing tests alone is no longer enough" and that agent PRs are often not ready to merge.
  • Motivating example. A developer spends about 1.5 hours writing specs for 7 tickets. Agents produce 28 PRs, 4 per ticket. 4 tickets pass in one go and 3 need another round.
  • Five activities and their artifacts:
    • Briefing Engineering: the BriefingScript (goal, success criteria, context, strategy, gotchas).
    • Agentic Loop Engineering: the LoopScript (the workflow and how strict it is).
    • AI Teammate Mentorship Engineering: the MentorScript, "mentorship-as-code", a version-controlled rulebook of team norms.
    • Agentic Guidance Engineering: Consultation Request Packs (CRP), Merge-Readiness Packs (MRP) and Version Controlled Resolutions (VCR).
    • AI Teammate Lifecycle and Infrastructure Engineering: agent memory and agent-native tools.
  • The Merge-Readiness Pack must prove five things:
    • functional completeness;
    • sound verification;
    • "exemplary SE hygiene" (static analysis, linting, complexity);
    • clear rationale;
    • full auditability.
  • Appendix: YAML examples of a BriefingScript, a CRP and an MRP for adding API rate limiting.

Key results (exact numbers)

  • This is a vision paper. Every number in it is cited from other studies, for example:
    • 29.6% of "plausible" SWE-bench fixes had regressions or were wrong when retested.
    • The true solve rate of GPT-4 fell from 12.47% to 3.97% after a manual audit.
    • 83.8% of Claude Code PRs were merged (from the lab's PR paper).
    • AIDev holds 932,791 agent PRs in 116,211 repos (cutoff 1 Aug 2025).

Stated limitations and future work

  • The authors' own caveat: the paper is "intentionally visionary", "not a definitive solution", and a "conceptual scaffold".
  • Roadmap items that matter most for you (Sections 7.3 and 8.1):
    • "Quality Assurance for Mentorship Rules. If mentorship becomes code, it needs linting, testing, conflict detection, and regression checks. Researchers should study how to verify that new rules improve agent behavior without causing unintended changes elsewhere."
    • MentorScript rules should pass "quality gates, including linting, unit testing, and conflict detection", and every agent action should be traceable to the rules it considered.
    • On CLAUDE.md and AGENT.md: "the community has no consensus on what such files should contain or the appropriate level of detail".
    • "Economics of Agent-First Code": for example, whether DRY still holds for agents. These claims "need empirical and economic models rather than anecdotes".
    • The observability gap: CLI sessions are lost in "a terminal's scroll-back buffer", and mentorship is not linked to code in version control.

Relation to your proposal

  • Your study is an empirical test of their "quality assurance for mentorship rules":
    • RQ1 asks whether a rule improves agent behavior (compliance with the rule vs without it).
    • RQ3 asks whether the rule causes "unintended changes elsewhere" (in code quality).
    • The Year 2 checker is a first step toward "linting" and "conflict detection" for rules.
  • Same measures. The "SE hygiene" evidence in their MRP (static analysis, linting, complexity) is the same kind of measure as your RQ3.
  • Same reproducibility idea. Their "full auditability" (frozen versions and saved trajectories) matches your fixed agent versions, clean containers and saved traces.
  • A short personal link. Your Magic Editor returns each edit as a schema-validated action that is applied only after the user approves it. That is close to their idea of structured, reviewable agent output. Use it as a quick link from your work, not as a research claim.
  • Who the authors are. Hassan and Hao Li built AIDev, so this group is the lab's main outside partner on agent studies.

Likely questions

Q: Have you read the SASE roadmap? Where does your work fit? A: Yes. They call CLAUDE.md and AGENTS.md an early form of MentorScript. In the roadmap they say rules need testing and regression checks. They also say we should check that a new rule improves agent behavior without changing other things by accident. My RQ1 tests the first part: does a rule change behavior? My RQ3 looks at changes elsewhere, in code quality. The Year 2 checker is a small step toward linting rules.

Q: Do you agree that developers become "agent coaches"? A: Partly, from my own work. At Layerpath I spend real time writing context files and reviewing what agents change. But today we add rules by feel, and nobody knows which ones work. That is why I want to measure it. In Magic Editor I also made every edit a checked action that the user must approve, which is close to their idea of reviewable output.

L12. CAM: A Causality-based Analysis Framework for Multi-Agent Code Generation Systems

  • Authors: Zongyi Lyu (HKUST), Zhenlan Ji (NAIST, SD lab Assistant Professor since April 2026; co-corresponding author), Songqiang Chen (HKUST), Liwen Wang (HKUST), Yuheng Huang (University of Tokyo), Shuai Wang (HKUST), Shing-Chi Cheung (HKUST; co-corresponding author)
  • Venue: ISSTA 2026, published in Proc. ACM Softw. Eng. Vol. 3, No. ISSTA, Article ISSTA147 (Oct 2026), DOI 10.1145/3832238. The work is led by HKUST; it is not an Iida paper.
  • arXiv: 2602.02138 (v3, 20 Jul 2026). Code: https://github.com/zongyiLyu/CAM

One breath summary

CAM finds which intermediate outputs of a multi-agent code generator (MetaGPT) actually cause correct code. It replaces each output, or a small group of outputs, with a realistic wrong version and checks whether the final code fails. The problem statement and the data-structure design matter most, and some outputs matter only in combination. The ranking helps repair failures (73.6%) and cut tokens (up to 33.6%).

What they did

  • Why they built it:
    • They checked 100 MetaGPT failures by hand. 83 came from flawed intermediate outputs (78 fixed after correction), 12 from overthinking (4 fixed) and 5 from underthinking (2 fixed).
    • Asking an LLM which output caused a failure works badly. Accuracy: GPT-4o 41.0%, Qwen-2.5-Coder 37.0%, DeepSeek-Coder-V2 34.0%. The authors think LLMs pick outputs "merely correlated with failures rather than actually causing them".
    • The usual "all-but-one" ablation removes a whole agent at a time. That mixes up the effects of the agent's different parts.
  • Method, based on actual causality (Halpern). A cause must actually happen (AC1). The outcome must change when the cause changes (AC2, counterfactual dependence). The cause must be minimal (AC3).
    • Features. They split MetaGPT's outputs into 12 features in 4 categories: Specification (3), Analysis (4), Design (2) and Dependency (3).
    • Causal graph. The graph is a DAG that follows the order of the workflow. They used each feature's final value so the graph has no cycles.
    • Interventions. An LLM rewrites one feature into a plausible but wrong version, which is then put back in place of the original. They rejected random noise, rule-based edits and plain deletion ("direct text deletion causes information loss without reflecting plausible failures"). In a check of 100 sampled interventions, 99 were judged coherent and realistic.
    • Search. Single features first, then groups of up to 5 features. The search is guided by "influence sets": which other features change after an intervention, judged by sentence-embedding similarity below 0.5. The budget is 100 runs per problem. A group size is abandoned after 10 tries that find nothing.
    • Feature responsibility (FR). For each problem, every important group adds (1/size)^2 to each feature in it, and the result is averaged over problems. So small groups count more.
  • Setup:
    • system: MetaGPT;
    • benchmarks: HumanEval-ET, MBPP-ET, CodeContest and CoderEval;
    • models: GPT-4o-mini, DeepSeek-Coder-V2 and Qwen-2.5-Coder-14B;
    • temperature 0, with stability checked across three runs;
    • extensions: CAM run on Self-Collab (with PairCoder and MapCoder discussed for the categorization only) and a DeepSeek-R1 backend.
  • Validation. Two annotators ranked the features on a 15% sample (weighted kappa 0.87). Kendall's correlation between CAM's rankings and the human rankings was 0.76 to 0.91.

Key results (exact numbers)

  • Top features:
    • Req_Stat (the problem statement) and Data_Struct (the data structures) are in the top 5 in all 12 settings.
    • Implement and Language are in the top 5 in 10 settings, and Program_Lang in 8.
    • Dependency features rarely matter (File_List and Share_Know: 0).
  • Context-dependent features:
    • For Program_Lang, only 21.2% of its important groups are the feature alone. In 78.8% it matters only together with other features.
    • The authors' advice: quality assurance should add "cross-feature consistency checks", not only checks of each module on its own.
  • Share of FR by group size: size 1 81.6%, size 2 15.9%, size 3 1.5%, size 4 0.7%, size 5 0.2%. So groups of two or more give 18.4%.
  • Hybrid backend (GPT-4o-mini, with DeepSeek-Coder for the design stage), Pass@1:
    • CodeContest: 0.1264 vs 0.1178 for GPT-4o-mini alone. This is the "up to 7.3%", and it is a relative gain.
    • CoderEval: 0.3645 vs 0.3478.
    • LiveCodeBench: 0.8216 vs 0.8148.
    • MBPP: 0.6904 vs 0.6979, slightly worse.
  • Repair. Improving the top 3 ranked features fixed 73.6% of the sampled failures (18 per setting). The baselines fixed less: random choice 27.8%, earliest outputs first 36.6%, longest outputs first 39.4%. The paper says this refinement took substantial manual effort.
  • Pruning.
    • Removing 2 to 4 low-ranked features cut intermediate tokens by up to 33.6%. That best case was DeepSeek-Coder with 4 features removed on CoderEval, and Pass@1 even rose by 5.88% (relative).
    • Removing 8 features hurt. For example, CodeContest Pass@1 fell by 36% to 45% (relative).
  • Harder tasks spread importance more evenly (on CodeContest, the standard deviation of FR is 0.1137 to 0.1773).
  • Cost: about 25M tokens and 8 to 12 hours per dataset and model setting.

Stated limitations and future work

  • Threats they list:
    • representativeness (3 models and 4 benchmarks, plus the extensions);
    • subjectivity of the manual rankings (two annotators, disagreements resolved);
    • randomness (temperature 0, checked across three runs).
  • Scope limits to notice yourself: the benchmarks are function-level, and the system is a pipeline of agents, not a repository-level agent like Claude Code. The feature categories come from MetaGPT.
  • Future work they mention:
    • "dynamically selecting backends based on task characteristics detected at runtime";
    • pruning that adapts "based on task complexity".

Relation to your proposal

  • Same core logic as your experiment: change one part, hold everything else fixed, and measure the outcome. Your "rule removed", "rule reworded" and "neutral sentence" versions are interventions on the context file.
  • How you handle deletion. CAM avoided plain deletion because it is not a realistic error. Your design keeps plain removal, because that is what developers really do. You also add a neutral sentence of the same length, so you can separate "the instruction is gone" from "the file got shorter".
  • Watch for interactions. A rule may matter only together with another rule, and removing one rule at a time cannot see this. In CAM, groups of features carried 18.4% of the importance, so interactions are not tiny. Be ready to call this a limit of your design.
  • LLMs are bad at finding causes. Their 34% to 41% accuracy at naming causes supports your script-based compliance checks.
  • Cutting what does not matter. In CAM, dropping low-value parts saved tokens with no loss. The same idea applies to context files, which add over 20% to inference cost [5]. Your Year 2 checker flags rules that agents ignore, and those are candidates to cut.
  • Randomness. CAM used temperature 0 and three runs. With Claude Code and Codex you may not be able to set the temperature, so your 3 runs and the mixed effects model have to handle run-to-run noise. Checked 25 Oct 2026: neither the Claude Code CLI reference (code.claude.com/docs/en/cli-reference) nor the Codex config reference (developers.openai.com/codex/config-reference) documents a temperature setting. Say: "As far as I know, neither CLI lets me set temperature, so I treat each file version as a distribution of runs and use repeated runs."

Likely questions

Q: You remove one rule at a time. What about interactions between rules? A: That is a real limit of my design. In CAM some features mattered only together with others. For Program_Lang, 78.8% of its important groups had more than one feature, and groups gave 18.4% of the total responsibility. My design measures the effect of one rule while the rest of the file stays the same, so it cannot find pairs. If the pilot shows two rules about the same thing, like test location and the test command, I can add a few pair removals. I will not test all pairs, because it costs too much.

Q: Is your experiment causal? What exactly do you intervene on? A: Yes, for RQ1, for wording in RQ2, and for RQ3. I change only the context file. The task, the starting commit, the agent version and the container stay fixed. So the difference in compliance between "rule kept" and "rule removed" is the effect of that rule. Repeated runs and the mixed effects model handle the run-to-run noise. In RQ3 I compare file versions, not runs that happened to follow the rule. The neutral sentence of the same length separates the instruction from the file length. Specificity and linter coverage differ between rules, so for those I only claim associations. The real-PR study is associations only.
